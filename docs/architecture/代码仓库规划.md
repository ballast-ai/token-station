# 代码仓库规划（社区版 / 平台版 / 企业版）

> 场景：[个人本地版开源策略讨论](../features/个人本地版开源策略讨论.md) 的开核（open-core）方向已采纳（2026-07-08 拍板：**个人版改名「社区版」并开源，注册门槛从下载后移到云功能**），本文收口三个商业版本对应的代码仓库规划。
>
> 整理日期 2026-07-08。决定性前提来自两处既有拍板：**「三个交付物共享同一路由内核」**（[业务模式与定价划分 §二](../features/业务模式与定价划分.md)）与**「C1 路由引擎复用服务端 P2 期抽出的路由 crate」**（[V2 开发计划 §四](../planning/token-station-V2开发计划.md)）。

---

## 一、两条规划原则

### 原则一：仓库跟着交付物走，不跟着 SKU 走

社区版 / 平台版 / 企业版是商业称呼，映射到代码上只有两类：**开源交付物**（本地客户端）与**闭源交付物**（网关 + 平台服务端）。

- Team / Enterprise 已拍板「同一个镜像、差异全由 license 开关控制、不维护两套代码」（业务模式 §四）——企业版不需要独立仓库，它是闭源仓的一个构建产物 + license 档位。
- V2 已确定平台服务端由 V1 网关升级而来，平台 SaaS 端点（交付物③）与私有部署网关（交付物②）是同一网关代码库的两种部署形态，同样不分仓。

### 原则二：开源边界 = 仓库边界，依赖只许单向（闭源 → 开源）

不在一个仓里混 license。开源仓必须能被任何人独立 clone、独立编译出完整的社区版——一旦开源代码 import 任何闭源模块，「可自行构建」即为假，开源的信任价值归零。闭源仓引用开源仓的 crates（git dependency 或私有 registry 固定版本），永不反向。

## 二、仓库结构（双 monorepo）

| 仓库 | License | 内容 | 产出 |
|------|---------|------|------|
| **`token-station`（开源 monorepo）** | Apache-2.0 | `crates/router-core`（规则 + hint + 启发式 + 分类器加载）、`crates/protocol`（稳定 Canonical IR + AgentHint + 基础协议类型）、`crates/plugin-api`（Agent / Provider 双端 WASM Component ABI、SDK、WIT、manifest schema）、`crates/plugin-runtime`（安全加载与 host functions）、`crates/conformance`（双端协议适配验收套件）、`crates/metrics`（指标库）、`plugins/official/agent-*` / `plugins/official/provider-*`（官方开源 adapter 插件）、`apps/cli`（社区版客户端本体，**含云同步与设备码授权的客户端侧代码**） | 社区版 |
| **`token-station-server`（闭源 monorepo）** | 专有 | 网关内核（多租户、计费、license 开关模块）、平台服务（账号、下载分发、云同步接收、远程配置服务、报表网页）、插件安装/签名校验/灰度启用、签名发布流水线、分类器训练管线 | 平台版（SaaS 部署形态）+ 企业版（私有部署形态，Team / Enterprise 由 license 区分） |

### 2.1 Adapter 插件是否拆独立项目

结论：**P1-P2 阶段不把 `agent-adapter` / `provider-adapter` 拆出主开源仓，但必须建立插件级审计边界。**

理由：

- `Canonical IR`、`AgentHint`、`plugin-api`、`plugin-runtime`、`conformance` 在早期会一起演化，过早拆仓会造成 ABI 与 fixture 版本漂移；
- 官方样板插件必须跟 conformance 同步变更，否则第三方插件无法判断哪个版本才是权威行为；
- 真正上线的是签名后的插件 artifact，不是 git repo 本身；审计边界应落在「插件包 + ABI 版本 + conformance 报告 + 签名」上；
- 单独 repo 对第三方生态有价值，但只有在 `agent-adapter-v1` / `provider-adapter-v1` 稳定后才值得付出跨仓版本管理成本。

阶段策略：

| 阶段 | 仓库策略 | 审计与迭代机制 |
|------|----------|----------------|
| P1-P2 ABI 成型期 | 官方 adapter 保留在 `token-station/plugins/official/*` | 每个插件独立 manifest、fixtures、conformance CI、CODEOWNERS、SBOM、签名、权限声明 |
| v1 ABI 稳定后 | 可新增 `token-station-adapters` 社区插件仓 | 社区插件独立 PR / release，依赖固定版本 `plugin-api` 与 conformance suite |
| 插件生态成型后 | 可新增 `token-station-plugin-registry` 元数据仓 | 只收录已审核插件 manifest、checksum、签名、公钥、conformance 报告，不承载业务代码 |

硬边界：`crates/protocol`、`crates/plugin-api`、`crates/plugin-runtime`、`crates/conformance` 仍留在主仓；它们是平台、企业部署版和社区版共用的 ABI 根，不跟具体第三方插件一起外拆。

## 三、平台 SaaS 与企业部署版的 release 控制

平台 SaaS 与企业部署版能力不同，但**不因此拆仓**。它们共享 `token-station-server` 闭源 monorepo 与核心网关代码；差异通过 artifact、部署 profile、license entitlement 和运行时配置控制。

### 3.1 能力差异归类

| 差异类型 | 平台 SaaS | 企业部署版 | 控制方式 |
|----------|-----------|------------|----------|
| 部署位置 | token-station 自有云环境，多租户共享运营 | 客户私有环境，单客户或客户内多租户 | `deployment_profile = saas / self_hosted` |
| 计费与支付 | credits、订阅、在线支付、平台运营报表 | license 授权、离线激活、合同/人工续费为主 | runtime billing mode + license entitlement |
| 运维能力 | 平台内部灰度、统一监控、统一插件 registry | 客户侧 Helm/docker-compose、离线包、版本锁定 | 不同 release artifact / bundle |
| 身份与治理 | 平台账号体系、平台级风控 | OIDC、管理审计、PG/Redis/K8s、高可用 | license entitlement + 配置 |
| 插件分发 | 平台 registry 托管、按租户灰度 | 签名插件包导入、可离线启用 | 同一插件格式，不同分发通道 |

### 3.2 Artifact 切分

同一个 commit 可以产出多个 artifact，但不维护多套代码：

| Artifact | 用途 | 是否共用核心 |
|----------|------|--------------|
| `token-station-gateway` image | SaaS 与私有部署共用的数据面网关 | 是 |
| `token-station-platform` services | SaaS 控制面：账号、支付、下载、云同步、报表、平台运营 | 共用部分 domain/crate，SaaS 部署启用 |
| `token-station-enterprise-bundle` | 企业部署包：Helm chart、docker-compose、迁移脚本、离线 license 校验、签名插件导入 | 是 |
| `token-station-admin` tools | 内部运维 / 企业离线运维工具 | 共用 API 与 schema |

关键点：**artifact 可以不同，源码仓库和核心网关不能分叉**。否则安全补丁、迁移脚本、插件 ABI、路由行为都会出现双线漂移。

### 3.3 开关层级

能力差异按以下顺序控制，禁止随手加编译期 feature 造成代码分叉：

1. **部署 profile**：区分 `saas` / `self_hosted` / `managed_hosting`，决定默认配置、外部依赖、运维入口。
2. **license entitlement**：区分 Team / Enterprise 能力，如 OIDC、审计、PG+Redis/K8s、air-gap、插件离线导入。
3. **runtime config**：控制计费模式、插件 registry 来源、远程配置、同步开关、限流后端。
4. **tenant rollout flag**：平台 SaaS 内部灰度、canary、design partner 开关。
5. **compile-time feature**：只用于确实不能随包分发的依赖或内部调试能力；不得用于产品分档。

### 3.4 Release 策略

| Release 线 | 节奏 | 来源 | 规则 |
|------------|------|------|------|
| SaaS continuous | 高频，小步灰度 | `main` → staging → canary tenant → prod | 可提前启用 runtime flag，但必须保持 schema 向后兼容 |
| Enterprise stable | 低频，建议月度/季度 | 受保护 tag，如 `server-v2.3.0` | 发布签名镜像、Helm/docker-compose、SBOM、迁移脚本、离线插件包、release notes |
| Patch / LTS | 安全与严重缺陷回补 | `release/v2.3` 分支 | 只接受安全修复、数据修复、兼容性修复，不引入新产品能力 |

版本号使用同一条主版本线，例如 `server-v2.3.0`。SaaS 可以先跑 `2.3.0-rc.N` 或 commit SHA，Enterprise 只拿稳定 tag。不要做 `saas-v2.3` / `enterprise-v2.1` 两条长期分叉线；那会把平台现网验证结果变成企业版不可复用。

### 3.5 迁移与兼容约束

- DB migration 必须可在 SaaS 先灰度验证，再进入 Enterprise stable 包。
- Enterprise stable 支持从最近若干稳定版本直接升级，具体窗口按商业支持策略定。
- 插件 ABI 的 breaking change 必须走 `agent-adapter-v2` / `provider-adapter-v2` 并允许 v1/v2 并存一段时间。
- SaaS-only 表或服务可以存在于同一仓，但网关核心不得 hard require SaaS 控制面；私有部署必须能离线启动。

## 四、关键设计判断与理由

1. **路由内核必须在开源侧——依赖方向决定，非偏好**。社区版要开源，而路由引擎 + 上游适配正是「内容不出设备」信任承诺的代码载体，不开源它们等于没开源。闭源产品依赖开源库成立，反向不成立（社区版将编译不出来）。内核即 P2 计划抽出的路由 crate 的正身。**附带推广叙事**：「你本地跑的路由内核，和平台、企业网关跑的是同一份开源代码」——[路由透明三件套](../features/路由透明与用户信任.md)的可信度从「可看」升级为「可读源码」，可写进 README 首段。

2. **客户端与内核同一开源仓，不拆小仓**。C1 与服务端 P2 并行共建，crate 接口在演化期，拆仓意味着每次内核改动跨仓联动发版；团队规模小时 Cargo workspace 单仓是唯一不自我折磨的选择。待 router-core 出现独立生态需求（他人只想引用路由库）再拆不迟。

3. **云同步 / 设备码授权 / 远程配置的客户端侧代码与协议 schema 定义在开源仓**。这些恰是最需要被审查的部分——白名单字段 schema 公开可查，「同步路径中内容结构性不可达」从断言变为任何人可验证的事实。服务端接收侧闭源无碍，协议公开即可。

4. **小分类器：推理开源、训练闭源**。ONNX 加载与推理代码在开源仓，权重文件随 release 发布（不进 git）；蒸馏训练管线与数据飞轮留在闭源仓。与「学习型路由器云端训练不在客户端范围」的既有口径（[智能路由能力](../features/智能路由能力.md) §③）天然吻合。

5. **签名私钥与发布流水线永远在闭源侧**。开源仓提供可复现构建脚本，官方安装包由闭源流水线签名——二者配合才成立：社区可验证「官方二进制 == 公开源码编译产物」，但只有平台能签出官方包。

6. **Agent 接入和 Model Provider 两端都必须插件化，但公共的是 ABI 不是业务代码堆。** token-station 的两侧接触面都会高频变化：北向要适配 Cursor、Claude Code、Codex CLI、Continue、Cline 等 Agent 工具和入口协议；南向要适配 OpenAI 兼容变体、Anthropic、Gemini、Bedrock、Azure OpenAI、本地模型等 provider/model API。开源仓提供稳定 Canonical IR、`agent-adapter-v1` / `provider-adapter-v1` WASM Component ABI、SDK 与 conformance 套件；官方和第三方 adapter 以插件包形式发布，社区版与闭源服务端都通过同一 `plugin-runtime` 动态加载。详细设计见 [双端 adapter 插件架构](./protocol-provider-adapter插件架构.md)。

## 五、必须避开的坑：「内部开发、定期导出」

主开发在闭源 monorepo、定期把客户端部分同步到公开仓的做法**禁止采用**。社区能立刻识别 code dump（commit 历史断裂、PR 无人理、issue 与实际开发脱节），会把开源换信任的目的反噬——「假开源」比闭源观感更差。开源仓必须是客户端与内核的**开发主战场（upstream-first）**：内部开发者直接在公开仓提 PR、跑公开 CI，闭源仓只做消费方。

## 六、被否掉的替代方案

| 方案 | 否决理由 |
|------|---------|
| Grafana / GitLab 式单仓双 license（`ee/` 目录） | 适用于「开源产品和商业产品是同一个程序」的场景；本项目闭源部分是服务端网关，与客户端是不同产品形态，同仓无共享收益，反而让开源仓躺着编译不了的目录 |
| 按三个版本切三个仓 | 企业版与平台版分仓立刻违反「不维护两套代码」拍板，网关内核改一个 bug 要同步两处 |
| 闭源主仓 + 导出开源镜像 | 见 §五，假开源反噬信任 |
| SaaS 仓 + Enterprise 仓 | 能力差异会演变成 release 差异、schema 差异和安全补丁差异；正确做法是同仓同核心、多 artifact、多 profile、多 release channel |

## 七、配套决定事项

| # | 事项 | 建议 | 状态 |
|---|------|------|------|
| 1 | 贡献协议 | **CLA**（Apache 个人 CLA 模板）而非 DCO：开源 core 会被闭源产品复用，且将来可能调整个别模块的 license 形态，无 CLA 则外部贡献者保留完整版权、手脚被锁死 | 待拍板 |
| 2 | GitHub org 与仓名 | 尽早占位；开源仓用主名 `token-station`（主名给开源本身是姿态），org 下预留 server 侧私有仓 | 待执行 |
| 3 | 可复现构建 | 列入开源仓首发要求（开源信任价值的成立前提，见开源策略讨论 §四） | 待排期 |
| 4 | Adapter 插件 ABI | 采用 WASM Component / WASI 作为默认插件机制，分 `agent-adapter-v1` 与 `provider-adapter-v1` 两套 ABI；原生动态库只允许内部可信插件，不作为生态接口 | 待实现 |
| 5 | 插件准入 | 插件包必须带 manifest、签名与对应 kind 的 conformance fixtures；平台安装时先跑验收，未通过不得启用 | 待实现 |
| 6 | Release 分支策略 | SaaS 从 `main` 持续灰度；Enterprise 从稳定 tag / `release/vX.Y` 分支出签名包和补丁线 | 待实现 |
| 7 | Adapter 项目拆分 | P1-P2 官方 adapter 留在主开源仓，靠插件级 manifest / fixtures / conformance / CODEOWNERS / 签名建立审计边界；v1 ABI 稳定后再评估拆 `token-station-adapters` 与 `token-station-plugin-registry` | 待复核 |
