# 数据库设计：V1 基线与 V2 增量

> 场景：把 V1（cloud_ai_gateway）的**业务模块 → 数据库表**对应关系整理为基线，再按 [V2 阶段需求清单](../planning/V2阶段需求清单.md) 与 [V2 开发计划](../planning/token-station-V2开发计划.md) 的分期（P1–P4 + C2 配套），推导 V2 需要**新增的表与改造的字段**。V1 部分为源码事实（非文档转述）；V2 部分为概要级 schema 设计，进入各期前需按详细设计复核（对齐开发计划 §六风险 6）。
>
> 整理日期 2026-07-08。V1 schema 提取方法：克隆 [cloud_ai_gateway](https://github.com/second-state/cloud_ai_gateway) 源码，按 `src/db/migrations.rs` 顺序应用 `sql/migrations/` 全部 **64 个迁移**，对最终 SQLite 库做 `.schema` 导出。
>
> **2026-07-09 详细设计复核修订**：三线复核（需求覆盖对照全部上位文档 / V1 源码写路径核实 / schema 一致性审查）后修订——V1 侧补入结算事务、继承语义、会话存储等源码事实；V2 侧补 8 张漏设的表（client_releases、sso_identities、sessions、invitations、model_perf_stats、consent_records、llm_router_configs、fallback_chain_items）、budgets 对齐七层预算、routing 域补租户维度、修正多处唯一键与幂等键设计。遗留拍板点见 §五。

## 零、通用约定（V1 已有，V2 延续）

| 约定 | 内容 |
|------|------|
| 金额 | 一律**微美元（microdollars）整数**（`balance`、`total_cost`、各 `*_price_*`），不用浮点 |
| 时间 | `TEXT`（RFC3339 字符串），除 `provider_credentials.expires_at` 为 INTEGER 时间戳（历史遗留） |
| 布尔 | `INTEGER` 0/1 + CHECK 约束 |
| 主键 | 业务实体（users/api_keys/teams）用 TEXT id；流水/配置表用 `INTEGER AUTOINCREMENT` |
| V2 新增 | P3 起 rusqlite → SQLx，SQLite/Postgres 双后端同一代码路径；JSON 字段存 `TEXT`（PG 侧可映射 JSONB）；主键写法不用 SQLite 专有 `AUTOINCREMENT`（迁移按后端分写 `INTEGER PRIMARY KEY` / `BIGSERIAL`） |
| 高写量流水表 | routing_decisions / client_usage_records 等每请求一行的表：**保留期 ≥ 账期**（「本月省 $X」等账单口径依赖），PG 侧按月分区、SQLite 侧定期裁剪归档 |
| 空集语义 | 白名单/策略类字段禁止依赖「空集合」表达含义（V1 个人白名单空=全允许、团队空=全拒，语义相反是既有事故源）；一律用显式 `default_action` 枚举 |
| 不入库的数据 | 请求日志（`request_logs/{user}/{key}/requests.jsonl` 文件）、WASM 模块（文件，表中仅存文件名）、license（Ed25519 签名**文件**，支持 air-gap）、限流/熔断计数器（内存态，Enterprise 档外置 Redis） |

## 一、V1 业务模块 → 数据库表总览

模块定义沿用 [V1 需求清单与业务模块](../planning/V1需求清单与业务模块.md)。V1 最终 schema 共 **18 张表**（不含迁移记录表 `schema_migrations`）。

| 模块 | 职责 | 涉及的表 |
|------|------|---------|
| M1 协议接入 | 三协议入口 + 互译 + 多模态端点 | （无表，纯代码路径） |
| M2 路由与容灾 | 供给侧路由 | `routing_groups`、`routing_channels`、`model_aliases`、`channel_health` |
| M3 上游与凭证 | 35 种 provider + 平台凭证池 + 模型目录定价 | `providers`、`provider_credentials`、`models` |
| M4 鉴权与账号 | key/会话/管理员/团队 | `users`、`api_keys`、`teams` |
| M5 计费与计量 | 分桶计量 + 三模式计费 | `usage_records`、`balance_transactions`、`system_credit_transactions`、`models`（定价）、`users`（balance/markup） |
| M6 配额与准入 | 花费配额窗口 + 模型白名单 | `user_quotas`、`team_quota_rules`、`user_allowed_models`、`team_allowed_models` |
| M7 WASM 插件 | 两级插件链 | （无独立表：`users.admin_wasm_file`、`api_keys.wasm_file`、`teams.wasm_file` 存文件名） |
| M8 可观测与日志 | 请求日志 + 用量统计 | `usage_records`（+ 文件日志，不入库） |
| M9 用户画像 | 画像派生与离线分析 | **已无表**：`user_profiles`/`profile_runs` 在迁移 0051 创建、**0057 删除**（画像转由独立 profile-analyzer 维护） |
| M10 控制台与 i18n | Web UI + 五语言 | （无表） |
| M11 部署与运维 | 单二进制 + 迁移 | `gateway_state`（通用 KV）、`schema_migrations` |

> 迁移史上昙花一现的表（做 V2 设计时不要从旧文档误引）：`user_profiles`、`profile_runs`（0051→0057 删）、`team_allowed_providers`（0060→0064 删，团队 provider 白名单方案被放弃，保留的是 `team_allowed_models`）。

### 2.2 计量与计费域

**usage_records** — 每请求用量流水（M5/M8 共用）

| 字段 | 类型 | 说明 |
|------|------|------|
| id | INTEGER PK AUTOINCREMENT | |
| api_key_id / user_id | TEXT → | |
| model / endpoint | TEXT | |
| input_tokens / output_tokens | INTEGER | token 分桶细项（cached 等）计价后只落 total_cost |
| total_cost | INTEGER | 微美元 |
| upstream_status | INTEGER | 上游 HTTP 状态 |
| request_id | TEXT | ⚠️ 列存在但**生产写入路径从不填此列，恒为 NULL**（billing.rs 两处 INSERT 均不含它）——V2 的 request_id 语义要从零建，无历史可继承 |
| duration_ms | INTEGER | |
| routing_channel_id | INTEGER → routing_channels（删 channel 时触发器置 NULL） | 路由归因 |
| usage_unit / usage_quantity | TEXT / INTEGER | 多模态计量单位（秒/字符/张/信用点）与数量 |
| team_id | TEXT | 团队归因（0062） |
| created_at | TEXT | |

结算写路径事实（V2 拆表时必须保留的不变量）：
- **单事务写三处**：`deduct_balance_and_record` 在同一 IMMEDIATE 事务内更新 `users.balance/total_spent` + INSERT `usage_records` + INSERT `balance_transactions`（credits 模式再加 gateway_state 积分池）——V1 唯一的结算原子性来源。markup 在事务内读取，加价后金额同时进三处。
- **一次请求一条记录**：failover 内部无论重试多少 channel/credential，成功收尾只结算一次；失败请求不写 usage_records。**但异步任务对账会追加修正行**（`record_billing_adjustment`）——「一请求多行（原始+修正）」的模型 V1 已存在。
- **分桶明细丢弃**：cached/cache_creation/cache_read 按桶精确计价后，落库时合并进 input_tokens 与 total_cost；分桶明细只进文件型 request_logs 的 detailed_usage。V2 若要缓存命中率/成本审计报表需加分桶列，且无历史数据可回填。

### 2.3 配额与准入域

**user_quotas** / **team_quota_rules** — 结构相同的花费配额窗口（超限 429）

| 字段 | 类型 | 说明 |
|------|------|------|
| id | INTEGER PK；user_id / team_id → 归属 | |
| label | TEXT | |
| limit_amount | INTEGER | 窗口内花费上限（微美元） |
| window_seconds | INTEGER | 滑动窗口 |
| is_active | INTEGER；created_at / updated_at TEXT | |

**user_allowed_models** / **team_allowed_models** — 模型白名单（复合主键 `(归属id, model_name)` + created_at）

继承解析事实（teams.rs，V2 收敛进 budgets/governance_policies 时必须保留的语义）：
- **两个 override flag 独立且不对称**：`quota_override` 是「替换规则集」（true 读个人 user_quotas，false 读团队 team_quota_rules）；`models_override` 是「替换白名单」且**两侧空集语义相反**——个人白名单空 = 全允许（`__deny_all__` 哨兵才是全拒），团队白名单空 = **全拒**。用户可以只覆盖配额不覆盖模型。
- **dormant rows**：关闭 override 后个人的 quota/白名单行**保留不删**，重新入队时按「行当前是否生效」决定是否恢复 override——收敛后的表必须有独立生效开关，不能用「有无记录」替代 flag。
- **未入队用户**：配额走个人规则（无规则=不限额），模型走个人白名单（空=全允许）。

### 2.5 系统域

**gateway_state** — 通用 KV（key PK、value、updated_at）。⚠️ 生产实际只写**一个 key**：`system_credits_balance_microdollars`（信用池余额）；admin 页注释提到的 `config_version` 全仓无读写实现。V2 可安全收敛，仅需迁移这一个 key。
**schema_migrations** — 迁移记录（name PK、applied_at），由迁移 runner 维护。

## 三、V2 数据库增量设计（按开发分期）

原则：**V1 的 18 张表全部保留、经 migration 平滑演进**（开发计划 §一原则 2，主干渐进、不迁库重导）。以下每期分「新表」与「改造既有表」两类，字段为概要设计口径；`〔编号〕`回指 V2 阶段需求清单。

> P0 期无 schema 变更（纯加固；session/凭证改哈希与 secrecy 包裹只改内容与代码，不改列）。

### 3.1 P1 — 决策链路 + BYOK

**新表 routing_decisions** — 每请求决策记录〔V2-P1-1〕。⚠️ 字段从第一天就按 P4 训练特征需求设计（开发计划风险 3），features 仅元数据〔V2-NF-8〕。

| 字段 | 类型 | 说明 |
|------|------|------|
| id | INTEGER PK | |
| request_id | TEXT UNIQUE | 决策可按 request_id 查询（验收项） |
| trace_id | TEXT | 与结构化日志关联〔V2-P1-3〕 |
| user_id / api_key_id | TEXT | P3 补 org_id / team_id 列 |
| requested_model | TEXT | 用户请求原文（含后缀） |
| model_suffix | TEXT | `-thinking`/`-high` 解析结果〔V2-P1-10〕 |
| candidates | TEXT JSON | 候选集（进入决策的端点列表） |
| decision_path | TEXT JSON | 逐层决策：`[{layer, rule_id/score, outcome}]`，P2 起有内容 |
| final_model / final_provider | TEXT | |
| credential_id | INTEGER → provider_credentials | 凭证归因（不落 key 内容） |
| credential_owner | TEXT | `platform` / `byok`（BYOK 归因） |
| reason_code | TEXT | 原因码，写响应头 `X-Routed-Reason` |
| actual_cost | INTEGER | 微美元，写 `X-Cost` |
| counterfactual_cost | INTEGER NULL | 反事实价（P2 三件套用「本月省 $X」；P1 建列即可）〔V2-P2-10〕。口径约束：① 聚合来源=本表，故保留期 ≥ 账期（§零）；② 默认只对平台代采购/转卖账路计算节省，`byok_fee` 请求不计入「省 $X」，仅另列「路由服务费」与「用户自付上游费不可见」说明 |
| features | TEXT JSON | 请求元数据特征（token 数/代码块/tool 等，飞轮训练输入） |
| created_at | TEXT | |
| 索引 | | request_id UNIQUE；(user_id, created_at)；(api_key_id, created_at) |

两点设计约束：① `request_id` 由**网关生成并保证唯一**（V1 的 request_id 列从未被写入，无语义可继承）；决策一请求一行，usage_records 的修正行（对账）多对一挂同一 decision_id。② `credential_id` 存**快照值、不建 FK**——BYOK 凭证可被用户删除，决策是审计数据，不能因删凭证级联或阻塞（V1 对 routing_channel_id 用触发器置 NULL 的先例说明硬 FK 在流水表上是负担）。

**改造 provider_credentials** — BYOK 归属维度〔V2-P1-4/5/6/7〕：

| 新增字段 | 说明 |
|------|------|
| owner_type TEXT | `platform` / `user`（P3 扩 `org` / `team`）；存量行 migration 补 `platform` |
| owner_id TEXT NULL | 归属主体 id |
| byok_mode TEXT NULL | `always_use` / `fallback` / NULL（默认回退）；`always_use` 时平台凭证不参与该用户派单 |

### 3.3 P3a/P3b — 多租户 + 计费产品化 + Enterprise 基座（schema 大改与 SQLx 迁移同窗口）

计划口径已拆分：**P3a = Team 商业闭环**（组织/成员/key/预算/计费/license/单机 SQLite/C2 配套），**P3b = Enterprise 基座**（PG/Redis 多副本、OIDC、审计、K8s/Helm）。本节仍按同一 schema 窗口描述，因为多租户主表、license、C2 配套与 Enterprise 表之间存在共享迁移；实施时按 P3a/P3b 分批开功能开关。

| plugin_packages | id；name；version；api_version；kind CHECK(`agent-adapter`/`provider-adapter`)；artifact_path；manifest TEXT JSON；signature；sha256；status CHECK(`uploaded`/`verified`/`failed`/`yanked`)；conformance_report TEXT JSON；created_at/updated_at | 插件包元数据；实际 `adapter.wasm` 走文件/对象存储，DB 只存路径和校验 |
| plugin_enablements | id；plugin_package_id → plugin_packages；scope_type/scope_id（`global`/`org`/`team`/`key`）；binding_kind CHECK(`agent_protocol`/`agent_tool`/`route_path`/`provider`/`model_family`)；binding_key；is_active；rollout_pct；created_at/updated_at | 插件启用与灰度；`agent-adapter` 绑定入口协议/工具/path，`provider-adapter` 绑定 provider/model_family；解析顺序 key > team > org > global；UNIQUE(scope_type, scope_id, binding_kind, binding_key, plugin_package_id) |

约束：未通过 conformance 的 `plugin_packages.status != verified` 不得写入 active enablement；`agent-adapter` 不得声明 secret 权限；`provider-adapter` 的密钥权限只存 manifest 声明，真实 secret 仍由 provider_credentials / secret store 管理。

### 3.4 P4 — Preset + 学习型路由 + 数据飞轮

**新表 presets / preset_versions** — `@preset/xxx` 命名别名〔V2-P4-1〕，建在 P3 config_profile 之上（拍板点：版本机制与 config_profile_versions 复用还是独立，进 P4 详细设计时定；本文按独立表列出）：
presets：id、scope_type/scope_id（org/team/user/平台公共）、name、UNIQUE(scope_type, scope_id, name)（`@preset/` 命名空间按 scope 唯一）、current_version_id、min_plan（套餐差异化门槛）、created_at/updated_at；
versions：id、preset_id →、version、config TEXT JSON（模型 + 参数 + provider 偏好 + 路由策略）、created_by、created_at。

**改造 api_keys**：+ `preset_id → presets`（Virtual Key 绑定 preset，列随被引用表同期加）。

**新表 feedback_events** — Feedback 采集与元数据飞轮〔V2-P4-3，受 V2-NF-8 约束仅元数据〕：id、user_id/api_key_id、request_id（关联 routing_decisions）、kind CHECK(`retry`/`regenerate`/`rating`)、value、metadata TEXT JSON、created_at。

**新表 consent_records** — 飞轮 opt-in 同意记录（复核发现缺失：V2-NF-8「条款预留 opt-in 口子」+「opt-in 换折扣」需要**谁、何时、按哪版条款**同意可追溯，布尔列不满足合规要求）：id、user_id →、kind CHECK(`flywheel_metadata`)、terms_version、granted_at、revoked_at。折扣应用落 subscriptions.discount_pct（P3 已建列）。

**新表 llm_router_configs** — 第③层 LLM-as-Router 配置〔V2-P4-2〕（复核发现缺失：智能路由 §一④「prompt 即策略，**用户能自己改路由 prompt**」= 需持久化、需 scope；routing_heuristic_configs 只管第②层）：id、scope_type/scope_id、judge_model、prompt TEXT、is_active、created_at/updated_at、UNIQUE(scope_type, scope_id)。

**第③层判官与学习型分类器的决策**〔V2-P4-2/4〕：写入 routing_decisions 的 `decision_path`/`features`（P1 已按此设计），「读了哪些特征」可查；ONNX 模型工件走文件/签名分发通道，不入库。

**错误目录**〔V2-P4-7〕：code→status→message_key 为**代码内静态单表**（唯一性由 CI 保证）+ Fluent 本地化资源，不入数据库。

**P4 详设遗留（可延后，不阻塞 P4 主交付）**：① 内容 guardrail 配置表（拦截/异步记录/切模型的 action 配置，按租户/套餐）〔V2-P4-8 自带可延后标注〕；② 级联兜底〔V2-P4-6〕的多次上游调用计费——「失败的那次便宜调用谁付」（智能路由 §一⑤）需要 usage_records 一请求多行 + attempt 序号（V1 对账修正行已开此先例，见 2.2）。

### 3.5 客户端本地库（C1，非服务端 schema，简列）

客户端指标库为本地 SQLite（默认开启、可关、仅本地），与服务端库物理隔离。概要设计已声明「表结构全量另起详细设计」，此处只列构成：逐请求明细（ts、model、上游类型、token 数、延迟、路由决策与命中规则、错误、成本估算——即 client_usage_records 白名单字段的本地超集）+ 聚合缓存。它同时是本地对账命令（C3）的计量底账与云同步数据源。
