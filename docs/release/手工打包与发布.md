# 手工打包与发布

release workflow（`.github/workflows/release.yml`）只是在四台机器上各跑一遍
`scripts/build-release.sh`——没有任何 CI 私有魔法。所以手工打包永远可行，
它的两个正当用途：

- **验证**：不信任 CI 产物时，自己重建并比对（这正是可复现构建存在的意义）；
- **兜底**：CI 不可用时照常发版。

日常发布仍建议走 workflow：矩阵替你凑齐四平台，`reproducibility` job 每次
发布把确定性自证一遍。信任链设计与标准发布手册见
[可复现构建与发布验证.md](可复现构建与发布验证.md)。

## 一、前置条件

| 平台 | 需要 |
|------|------|
| 任何 | rustup（脚本自行安装钉死的发布工具链与 target）、git 检出 |
| macOS | `brew install gnu-tar`（bsdtar 无确定性归档选项，脚本会明确报错） |
| Linux | `libdbus-1-dev`、`pkg-config`（keyring 的构建期依赖） |

正式发版必须在发布 tag 的检出上进行：

```bash
git checkout v0.1.0
```

在别的 commit 上打的包，字节不会（也不该）和官方一致。

## 二、单平台打包

```bash
scripts/build-release.sh aarch64-apple-darwin
```

产出 `dist/token-station-cli-<ver>-<target>.tar.gz` 并打印其 SHA-256。
包内结构：

```
token-station-cli-<ver>-<target>/
  token-station-cli            # CLI 二进制
  plugins-dist/
    agent-openai/              # manifest.json + adapter.wasm
    provider-openai-compatible/
  example-config.json
  LICENSE
```

版本号取自 `apps/cli/Cargo.toml`，时间戳取自当前 commit——脚本内没有任何
「现在几点」的输入，这是同一 tag 上人人打出同样字节的前提。

## 三、凑齐平台矩阵

配方不做跨 OS 交叉编译：

| target | 在哪打 |
|--------|--------|
| `aarch64-apple-darwin` | 任一 mac |
| `x86_64-apple-darwin` | 任一 mac（arm64 机器可直接交叉） |
| `x86_64-unknown-linux-gnu` | x86_64 Linux |
| `aarch64-unknown-linux-gnu` | aarch64 Linux |

手工凑齐四平台至少需要一台 mac + 两台 Linux。把各机器打出的 tar.gz 收拢到
一处的 `dist/` 再进入下一步。

## 四、清单、签名、上传

```bash
# 1. 汇总清单 + 校验和（任何机器）
cargo run --locked -p token-station-release --bin ts-release -- \
  manifest --version <ver> --out dist/manifest.json dist/*.tar.gz
(cd dist && shasum -a 256 *.tar.gz > SHA256SUMS)   # Linux 用 sha256sum

# 2. 签名（私钥所在的离线机器；私钥保管纪律见发布验证文档 §二）
ts-release sign --key <seed 文件> dist/manifest.json
#    -> dist/manifest.json.sig

# 3. 自查再上传
ts-release verify --pubkey <官方公钥 hex> dist/manifest.json
gh release create v<ver> --verify-tag \
  --title "token-station-cli v<ver>" \
  dist/*.tar.gz dist/manifest.json dist/manifest.json.sig dist/SHA256SUMS
```

注意顺序：**签名永远是最后一道人工步骤**，签之前把 manifest 里的产物清单
逐项过目——签名的意义就是「持钥者对这份清单负责」。

## 五、验证别人打的包（含官方包）

```bash
git checkout v<ver>
scripts/verify-release.sh <target> <待验证的 tar.gz 路径>
```

先比归档字节；若因 tar/gzip 环境差异不一致，自动退到逐文件 SHA-256 比对
——「二进制由此源码编出」的实质命题在文件层，归档只是信封。两道都过不了
才是真不一致，此时值得公开追问。

## 六、常见问题

- **`GNU tar required`**：macOS 装 `brew install gnu-tar`；脚本按名字找
  `gtar`。
- **首跑很慢**：脚本要下载钉死的发布工具链（与你日常的 stable 相互独立）
  并全量编译，属预期；同机第二次起走增量。
- **哈希和官方不一致**：先确认三件事——检出的是不是发布 tag、脚本是不是
  tag 里那份（配方变更随 tag 走）、比对的是不是同一 target。都确认后仍不
  一致，用 §五 的逐文件比对定位到具体文件再报告。
