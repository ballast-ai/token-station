# 可复现构建与发布验证

C1#7 的信任链设计与操作手册。核心命题一句话：**签名证明发布者，重建证明源码**——
两者合起来，官方二进制才是可验证的；缺一个都只是声称。

## 一、信任链

```
公开源码（发布 tag）
   │  scripts/build-release.sh（钉死工具链/依赖/路径/时间戳/归档）
   ▼
产物 tar.gz ──sha256──▶ manifest.json ──Ed25519──▶ manifest.json.sig
                              ▲                          │
                              │      公钥内嵌客户端        │
                              └────── upgrade 验证 ◀──────┘
```

- **manifest.json**：本次发布全部产物的 SHA-256 清单（格式版本化，
  `crates/release` 是唯一实现——签名侧与校验侧共用，无从分叉）。
- **manifest.json.sig**：Ed25519 签名，覆盖 manifest 文件的**精确字节**，
  没有规范化步骤可出错。
- 签名**只**证明「持钥者发布了这些字节」。这些字节是否忠于公开源码，
  由任何人按 §三 重建来证明。

## 二、密钥保管

- 私钥（32 字节种子）由 `ts-release keygen` 生成，**只存在于离线环境**：
  不进本仓、不进 CI、不进任何联网机器。泄露即换钥：换钥 = 新公钥入库 +
  发布说明公告 + 旧签名依旧可验但不再续用。
- 公钥（hex）内嵌在 `apps/cli/src/upgrade.rs` 的
  `OFFICIAL_RELEASE_PUBKEY_HEX`，随源码公开。
- 自行构建的二进制没有官方公钥（常量为空）：`upgrade` 仍可查版本，但拒绝
  代验下载——从源码构建的人本来就该用 §三 验证，而不是信任我们的钥匙。

## 三、验证官方二进制（任何人）

```bash
# 1. 验签名：manifest 确实出自官方钥匙
cargo run -p token-station-release --bin ts-release -- \
  verify --pubkey <官方公钥 hex> manifest.json

# 2. 验哈希：下载的包确实在清单里
sha256sum token-station-cli-<ver>-<target>.tar.gz   # 与 manifest.json 比对

# 3. 验源码：在发布 tag 上重建，字节必须一致
git checkout v<ver>
scripts/verify-release.sh <target> <官方 tar.gz 路径>
```

第 3 步先比归档字节；若 tar/gzip 环境差异导致归档层不一致，自动退到逐文件
SHA-256 比对——「二进制由此源码编出」的实质命题在文件层，归档只是信封。

## 四、配方的组成（改哪一项都等于换配方）

| 项 | 钉在哪 | 消除的非确定性 |
|----|--------|----------------|
| 编译器版本 | `RELEASE_TOOLCHAIN`（build-release.sh） | rustc 版本间代码生成差异 |
| 依赖版本 | `--locked` + 入库的 Cargo.lock | 依赖漂移 |
| 构建路径 | `--remap-path-prefix` → `/build`、`/cargo` | 路径嵌入二进制 |
| 时间戳 | `SOURCE_DATE_EPOCH` = 发布 commit 时间 | 墙钟 |
| 归档 | GNU tar `--format=ustar --sort=name` + `gzip -n` | 目录序/属主/mtime |
| 编译单元 | `codegen-units = 1`（workspace profile） | 并行代码生成的排布抖动 |

每次发布，CI 的 `reproducibility` job 用同一配方从零重建两遍并逐字节比对——
确定性不靠声称，靠每次发布自证。

## 五、发布运行手册（维护者）

1. **首次**：离线机器上 `ts-release keygen --out <离线目录>`；把打印出的公钥
   填进 `apps/cli/src/upgrade.rs::OFFICIAL_RELEASE_PUBKEY_HEX`，提交。
2. 版本号提升（`apps/cli/Cargo.toml`），合入 main，打 tag：`git tag v<ver> && git push --tags`。
3. Release workflow 自动：四平台构建 → 确定性自证 → 未签名 manifest +
   SHA256SUMS → **草稿** release。
4. 下载 manifest.json 到离线环境：
   `ts-release sign --key <seed 文件> manifest.json` → 得 manifest.json.sig。
5. `gh release upload v<ver> manifest.json.sig`，人工核对资产清单后
   `gh release edit v<ver> --draft=false` 发布。
6. 升级路径即刻生效：老版本 `token-station-cli upgrade` 匿名查到新版，
   显式确认后下载并用内嵌公钥验证。

## 六、边界与已知取舍

- **插件包签名**：`ts-release sign-plugin` / `verify-plugin` 工具与格式已就绪
  （包内 `signature.sig`，覆盖除自身外全部文件的 name+sha256 摘要）。当前
  官方插件随 CLI 包分发，已被 release manifest 的归档哈希传递覆盖，故首发
  不重复签；插件独立分发渠道（A5+）启用时按此格式逐包签名。
- **macOS 归档**：配方要求 GNU tar（`brew install gnu-tar`）；bsdtar 无
  确定性选项。
- **版本检查端点**：GitHub Releases API（2026-07 拍板）。将来切自建分发只
  改 `upgrade.rs::DEFAULT_ENDPOINT` 一个常量——信任在内嵌公钥，不在通道。
- **升级不自动安装**：`upgrade` 下载并验证到当前目录为止；替换二进制永远
  是人的动作。
