## 1. 结论与范围

本轮只覆盖用户确认的三个 Agent：

- Codex：OpenAI Responses，`POST /v1/responses`，
  `agent-openai-responses`。
- OpenCode：OpenAI-compatible Chat Completions，

## 3. 实现门禁

### Responses 插件

`agent-openai-responses` 五族 fixture 覆盖 normalize、hint、render、stream 和
error。最终独立插件结果：

```text
agent-openai-responses: agent-protocol-v1 16/16
agent-openai:           agent-protocol-v1 16/16
provider-openai-compatible: provider-protocol-v1 22/22
```

Responses 实现覆盖：

- instructions、字符串/消息 input、文本与图片 URL；
- function tool、function call、function call output；
- 非流式 Responses 输出和 Responses 错误；
- `response.created`、`response.output_item.added`、
  `response.content_part.added`、文本/参数 delta、output item done 和 completed；
- 按 `stream_id` 隔离和清理流状态。
- `text.format.type = "text"` 继续允许；`json_schema`、`json_object` 和未知格式
  在入站适配器内返回 HTTP 400 capability error，不再静默丢弃后路由到上游。

共享 Chat Completions 适配器 `agent-openai` 同步执行相同的诚实能力边界：
普通文本格式允许，`response_format` 的结构化输出类型在进入路由前明确拒绝。
两个 agent manifest 和三份 M4 配方均不再声明 `json_schema` 已受支持。

### JSON Schema 能力边界复测

本轮另起三套隔离实例，使用端口 8891–8893；没有停止或修改用户原有 8787 服务。
每个 Agent 都先验证结构化输出在适配器内失败，再验证普通文本和工具链仍然可用：

| Agent | 结构化输出请求 | 适配器结果 | 普通文本 | 工具闭环 |
|---|---|---|---|---|
| Codex | Responses `text.format.type = "json_schema"` | HTTP 400 `unsupported_capability`，未访问上游 | `CODEX_SCHEMA_OK` | 实际执行 `cat`，返回 `CODEX_SCHEMA_TOOL_OK` |
| OpenCode | Chat `response_format.type = "json_object"` | HTTP 400 `capability`，未访问上游 | `OPENCODE_SCHEMA_OK` | 实际执行 `cat`，返回 `OPENCODE_SCHEMA_TOOL_OK` |
| OpenClaw | Chat `response_format.type = "json_schema"` | HTTP 400 `capability`，未访问上游 | `OPENCLAW_SCHEMA_OK` | `read` 调用 1 次，返回 `OPENCLAW_SCHEMA_TOOL_OK` |

三套 metrics 中对应拒绝记录均为 `status = 400`、`error_code = capability`、
`attempts = 0`；普通/工具请求均为 HTTP 200、`attempts = 1`。OpenClaw 新
workspace 的第一次普通提示因其自身 bootstrap 规则返回 `NO_REPLY`；bootstrap
完成后复测返回精确标记，随后工具闭环也通过。该现象发生在 HTTP 200 的 Agent
行为层，不是 Token Station 的协议或路由失败。

### Responses output_index 复测

Canonical 文本 delta 的 `index` 是 choice index，tool-call delta 的 `index` 是工具
调用 index；两者属于不同命名空间。Responses adapter 现在为每个 output item 按
首次出现顺序分配唯一、连续的全局 `output_index`，后续 delta/done 稳定复用，并按
该编号生成最终 `response.output`。

自动化红—绿证据：

- 修复前真实 WASM 测试得到工具 `output_index = 0`，正确期望为 1；测试失败。
- 修复前 CLI 完整管线得到 `[(0, message), (0, function_call)]`；测试失败。
- 修复后混合 fixture 16/16、真实 WASM official 14/14、CLI proxy 23/23。
- 测试同时覆盖文本先出现、工具先出现、两个工具、文本/工具续传、最终 done 事件
  和 `response.completed.response.output` 顺序。

真实 Codex `0.144.5` 使用确定性 mock upstream 复测同一首轮同时包含文本和
`exec_command` 的响应。Codex 正确显示首段文本、执行
`cat /tmp/token-station-m4-index-20260716-2/codex/work/marker.txt`，mock 第二轮确认
收到 tool result，最终返回 `CODEX_INDEX_MIXED_OK`，退出码 0。对应 metrics 为
2 条 HTTP 200、`attempts = 1`。

## 6. 已知边界

- Responses reasoning item、reasoning summary、computer/hosted tool、file-id 图片、
  namespace tool 和完整 Responses 事件全集尚未支持。
- Responses `text.format` 和 Chat Completions `response_format` 的
  `json_schema` / `json_object` 尚未进入 Canonical IR，也没有获批 provider 映射；
  当前行为是明确返回 capability error，而不是生成结构化输出。
- Codex 当前配方必须关闭上述 hosted/namespace 工具；适配器对不支持项返回明确
  capability error。
- Codex 的文本 + 本地 function tool 通过，不等价于“完整 Responses 兼容”。
- Responses 混合文本与工具流的全局 `output_index` 已由 adapter 局部分配解决，
  不需要也没有修改 Canonical IR 或 provider；该结论只覆盖 message 和 function
  call 两类已支持 output item。
- OpenCode/OpenClaw 只验证本地 Chat Completions Agent 主链；其 MCP、远程 channel、
  浏览器、用户插件或用户 skills 不在本轮结论内。
- token usage 和价格以 token-station metrics 与上游账单为准；Agent 自己的兼容
  模型元数据不能作为计费依据。
