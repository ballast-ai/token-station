> 验收范围：单模型价格编辑、追加版本、历史 Receipt 不回算、显式零价、Agent/入站协议来源过滤

## 1. 验收结论

任务 #9 已形成闭环：Desktop 可添加、修改、删除单模型的输入、输出、缓存读、缓存写和可选推理价格；每次实际变化生成 `price_version+1`，陈旧 `expected_version` 被拒绝。编辑器明确提示历史回执不重算，运行中的代理需重新应用配置。

跨版本真实运行态 fixture 已证明：首个请求使用 price v1 并落成本 3；应用新价格后，第二个请求使用 price v2 并落成本 6；重新读取第一个 Receipt 时仍是 v1 / 3。价格编辑命令没有历史成本更新路径。

用量查询已支持 Agent namespace 和入站协议来源精确过滤，两个条件可组合；CLI、只读 HTTP 数据面、Desktop IPC 和前端均已贯通。

## 5. 契约修正记录

旧测试 `unknown_or_zero_cost_is_persisted_as_null` 与价格领域公开文档“0 是真实免费价格”冲突。按先扫描旧契约再进入 RED 的策略，本阶段没有机械迎合旧测试，而是以既有领域语义和任务的成本透明要求为准：

- 显式 `Estimated + 0 + price_version` 现在按免费价格落库；
- 缺模型仍为 unknown；
- 负值或 Estimated 缺版本仍归一化 unknown；
- v3 迁移对带版本零价采用同一规则。

这避免编辑器允许输入 0、但 Receipt 又把它显示成未知的端到端矛盾。

## 6. 安全与边界

- HTTP 管理面仍然只读；价格写操作只通过结构化 Tauri IPC。
- Renderer 只能提交模型 ID、五类数值价格和 expected version，不能提交任意配置 patch/path/content。
- 过滤只读取 Agent、protocol、token、成本和路由元数据，不读取 prompt/response。
- 保存价格不会自动热更新运行代理；界面明确提示重新应用配置。
- 删除价格只影响未来请求：该模型未来成本变为未知，历史 Receipt 保持原值。
