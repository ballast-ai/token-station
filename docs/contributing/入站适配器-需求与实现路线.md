# 入站适配器(Agent Adapter)需求与实现路线

- 工作流:入站侧(agent adapter)
- 状态:草案
- 变更请求 / IR 契约对接人:项目负责人(本任务分配人)
- 提交方式:全部经 Pull Request 合入,不直接向主分支提交

---

## 1. 背景与目标

token-station 是本地回环 LLM 代理:agent 工具把原本发往某个大模型 API 的请求
改发到本机代理,代理在本机将请求路由到某个上游模型,取得响应后翻译回 agent
所用的协议返回。

系统将三件事解耦为独立部件:入站协议翻译、路由、出站协议翻译。本工作流负责其中
**入站协议翻译**——即 agent 侧适配器。

**目标:** 使主流 coding agent 无需改动自身逻辑,仅将请求地址指向本代理即可接入,
并保证请求与响应在其协议与系统内部规范类型(Canonical IR)之间被无损翻译。

---

## 2. 范围

**范围内**
- `plugins/official/agent-*` 下各入站协议适配器的实现与维护。
- 新协议适配器的一致性测试用例(fixtures)。
- 各目标 agent 的接入配方与端到端兼容性验证。

**范围外**
- `crates/router-core`(路由内核)、`crates/protocol`(共享 IR 契约)、
  `crates/release`(发布信任链)。其中 IR 的调整通过变更请求由对接人处理(§9)。
- 出站(provider)适配器与路由策略。

---

## 3. 系统上下文

### 3.1 分层

Cargo workspace。与本工作流相关的部件:

| 部件 | 与本工作流的关系 |
|---|---|
| `crates/protocol` | 输入输出契约(`ChatRequest`/`ChatResponse`/`StreamEvent`/`AgentHint` 等) |
| `crates/plugin-api` | 需实现的 adapter ABI:WIT world + `manifest.json` schema |
| `crates/conformance` | 适配器进入请求路径前的一致性关卡,亦即隔离自测手段 |
| `plugins/official/agent-openai` | OpenAI Chat Completions 入站适配器,参考实现 |
| `apps/cli`(`gateway`) | 编排者,按数据流调用各适配器与路由 |
| `crates/plugin-runtime` | WASM 宿主,施加沙箱与资源约束 |

### 3.2 请求数据流

数据面全同步,入口 `Gateway::chat`
([apps/cli/src/gateway.rs](../../apps/cli/src/gateway.rs))。网关是唯一编排者;
各适配器之间无直接调用关系,适配器亦不调用路由。

```text
入站 JSON
  → ① agent.normalize_inbound        → ChatRequest        [入站侧]
    ② agent.extract_agent_hint       → list<AgentHint>    [入站侧]
  → ③ router.route                   → Decision
  → ④ provider.build_http_request    → HTTP
  → ⑤ 注入凭证、发送、取回上游响应
  → ⑥ provider.parse_response        → ChatResponse
  → ⑦ agent.render_response          → 出站 JSON          [入站侧]
    (流式:逐事件 agent.render_stream_event → 出站分块)    [入站侧]
  → 返回 agent
```

入站侧承担 ①②⑦及流式渲染。答案由被选中的上游模型生成;路由只做选择,入站适配器
只做协议与 IR 之间的双向翻译。

### 3.3 运行约束(由平台强制)

- 适配器编译为 WASM 组件,运行时无网络、无文件系统、无法获取明文凭证。因此入站
  适配器不涉及任何安全边界,只做纯翻译。
- 跨边界传参均为 JSON 字符串;每个参数的 WIT 文档注释标明其承载的 protocol 类型,
  该类型名即契约,schema 见 `crates/protocol`。

## 4. 接口契约

### 4.1 ABI:`agent-adapter-v1` world

定义见 [crates/plugin-api/wit/adapter.wit](../../crates/plugin-api/wit/adapter.wit)
的 `interface agent-adapter`。每个适配器须完整实现下列函数:

| 函数 | 输入 → 输出 | 说明 |
|---|---|---|
| `metadata` | → `AdapterMetadata` | 身份;`api_version` 必须为 `agent-adapter-v1` |
| `healthcheck` | → `AdapterHealth` | 存活状态 |
| `supported_agent_protocols` | → `list<AgentProtocolCapability>` | 声明所说协议及使用它的 agent 工具 |
| `match_inbound` | `{method,path,headers}` → `MatchResult` | 依请求头判定协议归属 |
| `normalize_inbound` | `AgentRequestEnvelope` → `ChatRequest` | 入站请求归一为 IR |
| `extract_agent_hint` | `AgentRequestEnvelope` → `list<AgentHint>` | 抽取路由提示,遵循 §4.3 |
| `render_response` | `ChatResponse` → 出站响应 | IR 响应翻回入站格式 |
| `render_stream_event` | `StreamEvent` → 出站分块 | 逐事件渲染,禁止缓冲整条流 |
| `map_inbound_error` | `ErrorEnvelope` → 出站错误 | 错误翻回入站格式 |

参考实现:[agent-openai/src/lib.rs](../../plugins/official/agent-openai/src/lib.rs)。

### 4.2 IR 契约类型(`crates/protocol`)

- `AgentRequestEnvelope`([envelope.rs:112](../../crates/protocol/src/envelope.rs)):
  `protocol`、`agent_tool`、`headers`(凭证值已抹除)、`principal`、`body`(原始
  入站 JSON)。
- `ChatRequest` / `ChatResponse`(chat.rs):归一目标与源。
- `StreamEvent`(stream.rs):`Delta` / `ToolCallDelta` / `Usage` / `Done` / `Error`。
- `AgentHint` / `HintKind`([hint.rs:11](../../crates/protocol/src/hint.rs))。
- `ErrorEnvelope` / `ErrorCode`(error.rs)。

IR 契约当前视为稳定。若某协议存在 IR 无法表达的语义,按 §9 提出变更请求,不得
自行修改 `protocol`。

### 4.3 Hint 契约(v1)

`extract_agent_hint` 的输出是路由输入。路由是否采纳取决于 `HintKind` 与 value
是否在契约内。v1 仅约定一项:

| HintKind | 约定 value |
|---|---|
| `StepType` | `planning` / `edit` / `summarize` |

- 抽取到契约外的 kind/value 不报错,但当前无路由效果。
- v1 为最小集,后续扩充由对接人更新本表。适配器可在此约定下,尽力从入站协议
  自带的模式/角色/字段中映射出上述 `StepType` 值。

## 5. 功能需求

- **FR-1 协议适配器完整性。** 每个入站协议对应一个 WASM 适配器,完整实现
  `agent-adapter-v1`(§4.1)全部函数,并具备合法 `manifest.json`
  (`kind: "agent-adapter"`、`api_version: "agent-adapter-v1"`、`agent_protocols`、
  `agent_tools`、`permissions` 全禁用/空、`conformance` 段)。

- **FR-2 Anthropic Messages 适配器(最高优先)。** 新增 `agent-anthropic`,覆盖
  Anthropic Messages 协议。已知需处理的协议差异:
  - system 消息为顶层字段,不在 messages 数组内;
  - content 为 block 数组(text/image/tool_use/tool_result),非字符串;
  - 工具调用 `tool_use` 为对象,而 IR `ToolCall.arguments` 为字符串;
  - 流式为 Anthropic SSE 事件(`message_start`/`content_block_delta`/
    `message_delta`/`message_stop` 等),结构不同于 OpenAI;
  - 可能存在 thinking 块等 IR 暂不表达的语义——按 §9 处理。

- **FR-3 目标 agent 覆盖。** 首批目标:Claude Code、Codex、opencode、openclow。
  逐一确定其所用协议、落到哪个适配器、接入方式。注意部分工具使用较新的 OpenAI
  Responses API,其形状不同于 Chat Completions,可能需独立适配器。除首批外,自行
  调研并提出其他主流 coding agent 的支持方案。

- **FR-4 协议盘点。** 产出 `agent → 协议 → 接入方式` 盘点表,作为 FR-3 的输入,
  据此确定需实现的适配器数量。

- **FR-5 Hint 抽取。** 各适配器按 §4.3 抽取 hint。

- **FR-6 一致性测试覆盖。** 每个新适配器提供覆盖以下族的 fixtures:
  `agent.normalize` / `agent.hint` / `agent.render` / `agent.stream` /
  `agent.error`。

- **FR-7 接入配方。** 每个目标 agent 产出接入文档:如何将其指向本代理、所需配置、
  已知兼容性注意事项。

## 6. 约束与非功能需求

- **NFR-1 无损翻译。** 请求/响应经 IR 往返不丢关键信息(工具、system、多模态、
  用量统计、错误码等)。
- **NFR-2 流式增量。** `render_stream_event` 必须逐事件产出;一致性套件会在每个
  字节边界重切流并要求解析结果一致,故流式解析需有状态缓冲,不得假设分块边界。
- **NFR-3 确定性。** 同一输入两次产出一致。
- **NFR-4 向前兼容。** 容忍未知字段。
- **NFR-5 边界。** 不修改 §2 范围外部件;IR 调整走变更请求。

## 7. 实现路线

分阶段推进,每阶段有明确出口。M1–M2 属隔离开发,仅依赖一致性套件,不需真实上游
或路由;M3 起需集成物料(§8)。

- **M0 · 环境与理解**
  出口:本地编出 `token-station-cli`(`cargo build --release -p
  token-station-cli`,`rustup target add wasm32-wasip2`);通读参考实现与 WIT;
  产出 FR-4 协议盘点表初版。

- **M1 · `agent-anthropic` 非流式 MVP**
  以 `agent-openai` 为模板建包(注意:`plugin new` 生成的是 provider 适配器,
  agent 适配器应复制 `agent-openai` 目录)。实现 `normalize_inbound` /
  `render_response` / `map_inbound_error` / 元数据类函数,补 `agent.normalize`、
  `agent.render`、`agent.error` fixtures。
  出口:`plugin test` 上述族全过。

- **M2 · 流式与工具调用**
  实现 `render_stream_event`(Anthropic SSE)、`tool_use` 双向映射、
  `extract_agent_hint`(§4.3)。补 `agent.stream`、`agent.hint` fixtures。
  出口:五族 fixtures 全过,满足 NFR-2。

- **M3 · Claude Code 端到端集成**
  用集成物料(§8)`serve` 起代理,将 Claude Code 请求地址指向本代理。
  出口:正常对话、工具调用、流式、错误回传均正确,满足 §9 验收。

- **M4 · 覆盖扩展**
  按盘点表推进 Codex / opencode / openclow:能复用现有适配器的产出接入配方,
  需新协议的按 M1–M3 流程新增适配器。并入自行调研补充的主流 agent。

各阶段命令:
```bash
token-station-cli plugin build plugins/official/agent-<name>   # 编 WASM 并就位
token-station-cli plugin test  plugins/official/agent-<name>   # 跑一致性套件
```

## 8. 依赖与所需物料

- 仓库访问权(已提供)。
- 集成阶段(M3 起)所需:示例配置(`plugins.agent` 指向被测适配器 + 配置一个
  可用上游)与至少一个可真实调用的上游(便宜模型凭证或本地 Ollama)。将另行提供。
- IR 变更请求的评审:见 §9。

## 9. 协作与变更流程

- **提交:** 所有改动经 Pull Request 合入,不直接向主分支提交。每个官方适配器为
  独立审计边界,按 `.github/CODEOWNERS` 落位。
- **IR 变更请求:** 遇到 IR 无法表达的协议语义(如 thinking 块、Responses API
  的 reasoning item、工具调用流式差异),不自行修改 `protocol`;向对接人提出
  变更请求,写明协议、缺失字段、建议方案,评审后统一调整。
- **Hint 契约扩充:** 需要新增 `HintKind`/value 时,同样向对接人提出,由其更新
  §4.3。

## 10. 验收标准(每个适配器 / 目标 agent)

1. 一致性:五族 fixtures 齐全且全过(NFR-1~4)。
2. 端到端:目标 agent 指向本代理后,对话、工具调用、流式、错误回传均正确。
3. 无损:IR 往返不丢关键信息。
4. 文档:接入配方齐备。

## 11. 自主决策范围

以下由实现者判断,不作硬性规定:协议适配器粒度(一器覆盖几个 agent、何时拆分)、
fixtures 用例设计、agent 怪癖是在适配器内兼容还是记入接入配方、接入配方形式、
调研的深度与顺序、以及首批之外支持哪些 agent 的取舍。有价值的改进欢迎经 PR 提出。
