# Cursor 兼容只读调研与分阶段设计

## 结论先说

可以按 WorkBuddy 的方式接入 Cursor，但只能复用“Agent Registry、独立连接器、命名空间、备份和 ownership”这层工程骨架，不能把 Cursor 当成另一个普通 OpenAI Chat Completions 客户端。最小可行方案是给 Cursor 建独立 Agent 身份和独立协议适配层：Ask 模式先走标准 Chat Completions，Agent 模式识别并转换 Cursor 当前实测的 Responses 形请求体，同时把回包和 SSE 重新渲染成 Cursor 仍然能消费的 Chat Completions 形状。

本次只做资料和本地代码审计，不修改代码，不写 Cursor 配置，不启动服务，不占用 8787，也不安装 App。Cursor 的桌面自定义 Provider 配置文件位置没有在官方公开文档中形成稳定契约，因此第一阶段不应该盲写配置文件。

### 实现状态补充（2026-08-04）

后续已完成真实 Cursor SQLite 配置备份、写入和代理请求验收，因此本设计中的“只读、不写配置”是历史审计边界，不再是当前实现状态。为避免专用一键接入与通用路由互相冲突，Cursor 注册表现已纳入 `supported` 和 `agent-openai/origin_v1`，保留专用 SQLite 备份写入逻辑；仍不复用 WorkBuddy 的本地 connector。

### 运行中接入实验（2026-08-04）

按 Codex 的用户语义，曾尝试在 Cursor 运行时直接写入 SQLite。实测启动后 Cursor 出现解密异常和 `SQLITE_CORRUPT`，Dock 闪退，说明运行中写入不能作为安全方案。已恢复较早的已验证备份并撤销该实验；当前回到运行中拒绝写入，保留手动填写 TS API 或用户自行退出后接入的路径。

## 1. 问题、目标、范围和非目标

### 目标

1. 评估 Token Station 是否能像 WorkBuddy 一样在 Agent 页面管理 Cursor。
2. 明确 Cursor 自定义 Provider、OpenAI-compatible、Responses、工具调用和 Agent/Ask/Plan 模式的协议边界。
3. 给出 develop 已合入 WorkBuddy 后的最小实现架构、公开测试边界和真实 Cursor 验收清单。

### 范围

- Cursor Desktop 的自定义 OpenAI-compatible/Base URL 使用场景。
- `/v1/chat/completions`、`/v1/responses`、流式 SSE、工具调用和图片能力声明。
- Cursor Agent、Ask、Plan 三种模式在 Token Station 侧的适配边界。
- Agent Registry、Connector、入站 Adapter、Canonical IR、Receipt 和模型能力声明。

### 非目标

- 不把 Cursor Cloud Agents API 当成 Token Station 的模型 Provider。官方文档明确说 Cloud Agents API/SDK 是完整 Agent 工作流接口，不是裸模型推理或 Chat Completions API。
- 不接管 Cursor 账号、Cursor Router、MCP OAuth、Cloud Agent 仓库权限或 Cursor 的内置模型目录。
- 不假设 Cursor 的本地 JSON/SQLite/IndexedDB 配置格式。未完成真实版本取证前，不写入 Cursor 配置。
- 不把 MCP 工具伪装成模型原生工具。Cursor 官方 MCP 是独立工具和数据连接协议，和模型 HTTP wire protocol 是两条边界。

## 2. 证据分层

### 官方事实

Cursor 官方 Agent 文档把 Agent 拆成 instructions、tools 和 model，并说明 Agent 能搜索代码、访问网页、编辑文件和执行终端命令。官方 CLI 文档还说明 CLI 与编辑器共享模式，支持 Agent/Ask/Plan、MCP 和 ACP。来源：[Agent overview](https://cursor.com/docs/agent/overview)、[Using Agent in CLI](https://cursor.com/docs/cli/using)。

Cursor 官方 MCP 文档确认 MCP 支持 tools、prompts、resources、roots、elicitation 和 MCP Apps，工具默认需要批准，并按 Run Mode 执行。MCP 的 stdio、SSE 和 Streamable HTTP 连接配置也有公开格式。来源：[MCP](https://cursor.com/docs/mcp)。

Cursor 官方 API 文档明确区分 Cloud Agents API/SDK 与裸模型 API，前者运行带工作区、工具、命令和编辑能力的 Agent，不是通用 chat-completions endpoint。来源：[Cursor APIs](https://cursor.com/docs/api)。

### 实测/社区观测事实

Cursor 社区在 2026 年的公开请求抓包中报告：使用 Override OpenAI Base URL 时，Cursor Agent 仍请求 `/v1/chat/completions`，但 Agent 模式的 body 可能使用 Responses 形状的 `input`、`reasoning`、`text`、`include`、`previous_response_id` 等字段。工具可能是 Responses 风格的扁平 `{type:"function",name,...}`，也可能出现 `{type:"custom",name,format}`，而不是 Chat Completions 的 `tools[].function` 嵌套结构。来源：[Cursor Agent sends Responses API format to /chat/completions](https://forum.cursor.com/t/cursor-agent-sends-responses-api-format-to-chat-completions-endpoint/153019)、[Override OpenAI Base URL mismatch](https://forum.cursor.com/t/override-openai-base-url-sends-responses-api-payload-to-chat-completions-but-expects-chat-completions-output/159298)。

同一组报告指出，Cursor 仍按 Chat Completions 流式回包解析，因此只把请求转发到 `/v1/responses` 还不够，Responses SSE 必须转换回 `choices[].delta`、工具增量和 `[DONE]`。Ask 模式被报告为更接近标准 Chat Completions，但这不是官方稳定协议承诺。来源：[Custom Model Provider Error](https://forum.cursor.com/t/custom-model-provider-error/153948)。

### 推断

1. WorkBuddy 的普通 `agent-openai` 入口足以覆盖 Cursor Ask 模式的基础文本和标准 function tool，但不能覆盖 Cursor Agent 模式的全部请求。
2. Cursor 需要“协议探测 + 专用转换”的适配层，而不是仅新增一个 Agent ID。
3. `/agents/cursor/v1/chat/completions` 是比改公共 `/v1/chat/completions` 更安全的第一落点。这样可以隔离 Cursor 的非标准字段，避免影响 WorkBuddy、OpenCode、OpenClaw 和 Hermes。
4. Cursor 的 `type:custom` 工具不能在未经语义确认时强行降级为普通 function。若 Token Station 无法保留 grammar/schema 语义，应返回清晰的 capability 错误，让 Cursor 回退或提示用户。

## 4. 最小架构建议

### 阶段 A：协议入口，不改 Cursor 配置

新增 `cursor` Agent descriptor 和 `cursor-v1` connector，但 connector 初期只提供“发现、诊断、导出/手动复制 Base URL”能力，不写入 Cursor 配置文件。固定建议入口为：

```text
http://127.0.0.1:8787/agents/cursor/v1/chat/completions
```

此 URL 仅作为设计目标，不在本次调研中启动或占用端口。

新增 `agent-cursor` 或 `agent-openai-cursor` 专用插件更稳妥。它应先做严格形状探测：

- `messages` 存在且工具是标准嵌套 function：按 Chat Completions normalize。
- `input` 存在，或出现 Responses 专属字段：进入 Cursor Responses-compat normalize。
- 出现未知顶层字段时保留到受控 extensions，不能静默丢弃。

### 阶段 B：Cursor 请求转 Canonical IR

Responses-compat normalize 至少要覆盖：

1. `input` 中的 message、text、image、tool call、tool result 顺序还原成 Canonical IR。
2. `reasoning.effort` 映射到 Canonical reasoning effort。
3. `text.format` 仅在已有批准的结构化输出映射时放行，否则返回 capability 错误。
4. `previous_response_id`、`store`、`prompt_cache_retention`、`truncation` 等 Cursor/OpenAI 状态字段不得假装被 Token Station 持久化。能安全透传的放入 extensions，不能实现的明确拒绝。
5. 标准 function 工具保留 name、description、parameters 和 strict 语义。
6. `type:custom`、grammar 工具和 namespace 工具先建立 capability 状态。没有一一对应的 Canonical IR 时 fail closed，不把它们粗暴改成普通函数。

### 阶段 C：双向流式渲染

公共 Canonical stream event 已有 delta、tool call delta、thinking、usage、done 和 error。Cursor 专用 renderer 需要再定义：

- Chat Completions SSE 输出，供 Cursor 当前 `/chat/completions` 解析器消费。
- Responses SSE 输入事件到 Canonical stream event 的映射。
- 工具调用的稳定 call id、index、arguments 增量和结束顺序。
- usage、finish reason、错误事件和 `[DONE]` 的一致收尾。

不能只做 HTTP path rewrite。公开抓包已经显示“请求像 Responses、响应仍期待 Chat Completions”会造成上游成功但 Cursor 空白。

### 阶段 D：真实配置连接器

只有在锁定 Cursor 版本、桌面平台和配置格式后，才按 WorkBuddy 方式实现写入：读取配置、创建备份、只拥有 Token Station 记录、拒绝同 ID 冲突、写后复验、断开时按 ownership 过滤。若 Cursor 只通过 UI 或加密存储管理自定义 Provider，就保留“复制 URL/API Key”而不是猜测文件格式。

## 5. 冲突公共区域与隔离策略

| 区域 | 当前风险 | 设计决定 |
| --- | --- | --- |
| `/v1/chat/completions` | Cursor Agent 非标准 body 可能撞到普通 OpenAI 适配器 | 首期使用 `/agents/cursor/v1/chat/completions`，公共路径不改语义 |
| `agent-openai` | WorkBuddy/OpenCode/终端客户端依赖标准 Chat Completions | 保持现有插件行为，Cursor 先独立插件或独立 dialect |
| Canonical IR | Responses input、custom tool、server state 可能无对应字段 | 只做有明确映射的转换，未知能力 fail closed |
| 图片能力 | WorkBuddy 当前记录声明支持图片，纯文本上游未必支持 | Cursor 不复制 `supportsImages: true`，依赖 capability 和现有媒体降级 |
| 8787 本地端口 | Cursor MCP/OAuth 文档也提到 localhost:8787 回调 | 本次不启动服务，不调整端口；实现时确认 Token Station Gateway 与 Cursor MCP 回调不会复用同一路径 |
| UI 图标 | Cursor 官方图标授权和来源未确认 | 先用文本/占位，不从网络抓取或伪造官方商标 |

## 6. 公开测试边界和验收标准

### 协议测试

1. 标准 Chat Completions 文本、流式文本、单工具和多轮工具结果保持现有输出。
2. Cursor Responses 形 `input` 能还原 system/user/assistant/tool 顺序。
3. Responses `reasoning.effort`、`text.format`、`previous_response_id` 分别验证放行、明确拒绝或受控透传结果。
4. 扁平 function tool 能转换成 Canonical IR，并渲染回稳定的 Chat Completions tool delta。
5. `type:custom`、grammar、namespace、server-side tool 在未实现时返回 typed capability 错误，不返回假成功。
6. Responses SSE 的 text、reasoning、tool call、usage、done、error 全部有 fixture，且能回放成 Cursor 可消费的 Chat SSE。

### 路由和安全测试

1. `/agents/cursor/v1/chat/completions` 只匹配 Cursor connector，公共 `/v1/chat/completions` 行为不变。
2. 缺少或错误虚拟 Key 返回 401，错误格式符合 Cursor 的 parser。
3. 所有 Cursor 请求都进入 Receipt，记录协议转换阶段和失败原因，不记录 API Key、完整 prompt 或图片 base64。
4. 图片请求按现有视觉能力门处理。没有视觉能力时使用统一媒体降级，或返回明确“不支持照片”的 assistant 文本，不能伪造模型看到了图片。
5. 超大 body、非法 JSON、未知 namespace、重复工具 call id、异常 SSE 顺序均 fail closed。

### 真实 Cursor 验收

在实现阶段锁定并记录 Cursor 版本、macOS/Windows 平台和模型名后，使用隔离配置完成：

1. Ask 模式纯文本往返。
2. Ask 模式一次标准 function tool 调用和工具结果续轮。
3. Agent 模式文本请求，记录真实 path、顶层 keys、是否为 `messages`/`input`、工具形状和流式事件。
4. Agent 模式工具调用、工具结果、连续两轮工具调用。
5. Plan 模式只生成计划，不误触发写工具。
6. 图片输入：视觉模型正常处理；纯文本模型返回清晰不支持照片提示或按媒体降级设计继续处理文字。
7. reasoning effort、结构化输出和停止/取消行为。
8. Cursor 重试、网络错误、401、429、上游 5xx 时，UI 能看到可行动错误，Receipt 与实际尝试次数一致。

本次不执行上述真实验收，因为用户明确要求只读调研、不得启动服务、不得改 Cursor 配置。

## 7. 分阶段计划（WorkBuddy 合并后）

1. **取证阶段**：锁定 Cursor 版本和平台，使用隔离日志代理只观察请求，不改用户配置；建立 request/response/SSE fixture。若版本间差异大，按版本能力目录分层。
2. **协议阶段**：实现 Cursor dialect 的形状探测、Responses-compat normalize、Chat SSE renderer 和 typed capability 错误。先不做自动写配置。
3. **路由阶段**：新增 Cursor 命名空间与 adapter binding，验证不影响 WorkBuddy 和公共 OpenAI-compatible 路径。
4. **工具阶段**：先支持标准 function tool，再按实测需求实现 custom/grammar 工具。每种工具都要有 Canonical IR 映射和回包 fixture。
5. **媒体阶段**：复用全 Agent 媒体降级，不把 Cursor 的 `supportsImages` 声明当成能力证据。
6. **连接器阶段**：只有配置格式稳定且可安全 ownership 时，才新增 Cursor connector。否则产品只展示“复制 Base URL/API Key”的手动接入卡片。
7. **发布阶段**：依次完成设计文档、公开行为测试、实现、全量测试与构建、真实 Cursor 验收，再按仓库要求更新本机 App。若只是本设计文档，不执行 App 安装流程。

## 8. 当前判断和遗留问题

当前判断是“能兼容，但必须把 Cursor Agent 当成独立协议方”。WorkBuddy 兼容层证明了 Agent 级命名空间和配置 ownership 可行，不能证明 Cursor 的请求体和工具协议相同。最大未知数有三个：Cursor 当前版本在不同模型和模式下的实际 wire shape、桌面自定义 Provider 的持久化位置、`type:custom` 工具是否要求 grammar 执行语义。

在这三个问题被真实取证前，最安全的交付形态是独立 Cursor endpoint 加手动配置说明，不是猜测 Cursor 配置文件并自动覆盖。
