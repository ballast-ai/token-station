# 评测中心设计

> 本文沉淀 token-station「智能路由 + 评测」这条工作流的核心设计与讨论结论。
> 目标读者:负责路由内核与评测的人。范围:为什么要评测中心、它如何工作、
> 标签怎么来、回放怎么跑、参数怎么迭代。标注了「已定 / 待定 / 规划中」。

---

## 0. 一页纸速览

- **产品定位:** 与 agent 无关的智能路由代理。按每条请求的难度,把它路由到
  **在不降质前提下最便宜**的模型,给企业省 token。
- **路由的本质:** 它是一个**任务分类器**——但**不是** LLM/ML 在线分类器,
  而是一个**廉价、本地、确定**的函数,判断"这条请求该走哪一档"。
- **评测中心的本质:** 一把**尺子**。离线、确定、免费地回放带标签的数据集,
  量出一套路由配置的**降级率 / 省钱率**,指导迭代。
- **两种打标签(全文的解结点):**
  - **离线(训练时)**:调多档真 API + 裁判 → 得"正确档位"标签。贵,但在固定
    数据集上**只做一次**。
  - **在线(请求来时)**:**不调大模型 API**,只用训练好的本地函数**预测**档位。
- **两个产物,一场实验:** 同一场离线实验(请求 × 多模型 × 裁判),既产出
  **请求标签**(训练分类器),又产出**模型能力画像**(给模型定级/校准阈值)。

## 1. 背景:为什么规则路由不够,而 LLM 在线分类又不行

### 1.1 现状与问题

现有路由第3层是**手工加权 + 关键词表**的线性打分器(`router-core`)。它用"字面
信号"(关键词计数、token 估算、结构特征)去猜"语义难度"。问题:关键词表天然
不懂语义,加 case 就得加关键词、调权重,越加越脆、还分语言。**规则路由会越来越
臃肿,是死路。**

### 1.2 但"每请求调 LLM 当分类器"会撞四堵墙

一个直觉是:用一个模型 API 给每条请求分类。直接这么做撞四堵墙:

1. **延迟** —— coding agent 一个任务连发几十请求,每条先等一次分类 LLM,体感崩。
2. **成本悖论** —— 加一次 LLM 调用去省 LLM 成本;若跑在完整 payload 上(coding
   的 payload 动辄几万 token),分类这一下可能比省下的还贵。
3. **隐私承诺** —— 内容不出机是命根子;分类器若调外部 API,承诺当场死。
4. **确定性不变量** —— `router-core` 建立在纯函数(client/gateway 结果一致、
   决策可回放)之上;一次外部 LLM 调用非纯、非确定、要联网,与地基冲突。

### 1.3 解法:两个时间尺度

> **离线,用大模型定义真值 + 训练;在线,跑一个便宜、快、(尽量)本地的分类器。**

- **离线层**(用大模型,不在请求路径):即评测 Oracle,同时是训练数据工厂。
- **在线层**(便宜、快、本地)分三版渐进:
  - **v1**:线性打分,但权重用回归在标签集上**拟合**,不再手填。零延迟,仍是
    纯整数函数,不破不变量。
  - **v2**:本地 **embedding** 模型(几十 MB)把语义压成向量再分类。~10–50ms
    **本地**,破"纯整数"但仍本地、近确定,懂语义。
  - **v3**:本地**小 LLM(1–3B)**当分类器,**只对 v1/v2 判不准的模糊带**启用
    (级联),模糊带才 ~100ms,仍本地。

**级联是成本控制的关键:** 便宜的 v1/v2 把 70–80% 明显简单/明显难的请求直接定了,
只有 20–30% 卡中间的才升级到小 LLM。针对 coding agent 还有一条:**分类器只看
"任务信号"(最后一条指令 + 工具名 + 结构特征),不看几万 token 的文件上下文**
——同时解决成本墙和延迟墙。

**与架构和解:** 把 embedding/小 LLM 的分类结果当成**网关层算好的一个"特征"**
喂进 `router-core`;内核仍是纯函数、仍确定、仍可回放,非纯部分隔离在网关侧。

### 1.4 行业参照(见《路由策略调研》)

- **Claude Code 没有难度分类器**:只按任务类型选 Haiku + 人工/模式切换;难度路由
  是它未做的空白。
- **RouteLLM(LMSYS)** 是唯一"学出来"的难度路由器,也是最可借鉴的:预测
  `P(强模型胜 | query)`,> 成本阈值 α 就走强模型。训练数据 = 偏好数据 + LLM-judge
  扩充。这套框架天然映射到现有 `heuristic.threshold`。

## 2. 两个核心心智模型(务必内化)

### 2.1 两种打标签,两个时间(全文的解结点)

| | 离线打标签(训练时) | 在线分类(请求来时) |
|---|---|---|
| 何时 | 事先,在**固定**数据集上 | 实时,在每条**活**请求上 |
| 做什么 | 调多档真 API + 裁判 → "正确档位" | 直接**预测**档位 |
| 调大模型 API? | **调**(这就是 Oracle) | **绝不调** |
| 做几次 | 一次(几千条,固定) | 每条一次,只跑廉价本地函数 |

**在线时我们不"打标签",我们"预测"。** 那个廉价本地函数是离线时用 Oracle 标签
**训练**出来的,它"吸收"了大模型/裁判的判断力,之后在线不再问任何模型。

> **医生类比:** 训练阶段研究几千个已确诊病例(确诊靠活检/随访 = Oracle,慢而贵);
> 看新病人时不重做活检,只看廉价症状**预测**,因为训练教会了"症状→诊断"的映射。
> 在线分类器 = 这个训练好的医生。

**所以没有无限循环:** 花 API 钱的打标签只在离线固定集上做一次;在线没有打标签,
只有训练好的廉价函数在预测。「本地跑 ≠ 调 API」:embedding/小 LLM 在本机跑,
只加几十毫秒,不花钱、不出网。

### 2.2 两个产物,一场实验

系统需要**两个不同产物**,别混:

| 产物 | 回答的问题 | 形态 |
|---|---|---|
| **请求分类器** | "**这条请求**有多难?"→ 需要哪档 | 一个函数(v1/v2/v3) |
| **模型能力画像** | "**这个模型**多强、多贵?"→ 谁坐哪档 | 一张表(模型 × 任务类型 × 质量 + 价格) |

二者在路由那刻会合:「请求需要 X 档(分类器)+ 能达 X 档质量的最便宜模型是 Y
(画像)→ 派给 Y」。

**优雅之处:它们来自同一场离线实验。** Oracle 给一条请求打标签时,做的就是"把它
发给各档 + 裁判判谁够好":
- 从**请求**看 → 得到"正确档位"(请求标签);
- 从**模型**看 → 得到"这些模型在这条题上表现如何"(画像的一个数据点)。

**一场实验(请求 × 多模型 × 裁判),同时产出两样东西。**

## 3. 分类器不是"难题→档位",而是"升档值不值"

### 3.1 档位的两个含义(易混点)

- **槽位**:上/中/下只是用户往里丢模型的槽。丢什么、强弱顺序由用户定。
- **质量水平**:上/中/下是真实能力台阶。

用户填槽(供应商 + key + 型号,对应现有 `upstreams` + `pools`)**只给了"顺序"
(上≥中≥下),没给绝对能力,也没给档间差多少**。

### 3.2 正确问法

> **分类器不问"这题多难",也不问"这模型多强"。它只问:"这条请求,往上升一档,
> 到底能不能换来更好的答案?" 能 → 升;不能 → 省钱待在下面。**

这一句化解所有卡点:
- **三个模型都弱、来道难题**:升到"上"也好不了(上也弱)→ 升了白花钱 → 待在下档。
  相对框架**天生处理了"模型都弱"的情况**。
- **"上"真强、来道难题**:升档能换质量 → 升。
- **来道简单题**:升档换不来改善 → 待在下档省钱。

**"升一档有没有用",正是第5节 Oracle 里"强模型有没有比弱模型有意义地更好"的
相对比较。** 硬把难度对死到某档,是错误设计。

### 3.3 诚实边界

若用户三个模型全弱,产品极限是**"不为无用升档花冤枉钱"**——它变不出任何一个
模型里都不存在的质量。这是物理限制,不是缺陷。

## 4. 全局难度预测器 vs 每用户校准

把"判断升档值不值"拆成三件事:

| 事情 | 谁做 | 要不要单独实验 |
|---|---|---|
| 给用户的模型排强弱顺序 | 用户填槽时定 | **不用**(用户给了顺序) |
| 判"这条请求升档有没有用"(难度信号) | 训练一个**难度预测器** | 要,**一次,随产品出厂** |
| "线画在哪"(阈值) | 每个用户的模型组 | **给默认值**,可选做**校准** |

- **难度信号基本模型无关**("修并发死锁"内在就比"改变量名"难,不管用什么模型)
  → 难度预测器可**全局训练一次、出厂内置、开箱即用**。
- **"线画在哪"高度依赖具体模型组** → 阈值给默认值就能跑;想榨干省钱,就跑一小轮
  Oracle **校准**(拿用户自己三个模型 + 一批代表请求,判在哪些请求上升档真有用)。

**每用户校准 = 第5节 Oracle,缩小规模、跑在用户自己的模型上。** 同一台机器,两个
用途(全局难度预测器 / 每用户阈值)。校准**顺带产出**用户这组模型的能力画像
(可在界面展示,是副产品)。边界:①不校准也能用(默认阈值);②换模型要重跑;
③一次性/定期,绝不是每条活请求。校准题来源:出厂标准集(立刻能校)→ 用户真实
流量(更贴合)。

## 5. 标签怎么定:Oracle 的判定标准(最硬的一步)

> **量是必要非充分。** 决定成败的是:①题目**分布**是否代表真实流量;②**判定
> 标准**是否可信。垃圾标准 × 海量 = 系统性垃圾标签。

### 5.1 根本定义:相对,锚定强模型

> `needs_strong` ⟺ 强模型的答案比便宜模型的答案「**有意义地更好**」;否则 `weak_ok`。

锚定强模型,因为"降质"是相对**用户本来会用的强模型**说的(对应"不降质"承诺)。
简化成:**"便宜模型这次的答案,是不是好到——换强模型也帮不上忙?"**

### 5.2 怎么量"有意义地更好":两个家族,按任务类型分流

**家族 A · 客观判分(有标准答案,最可靠,首选)**

| 任务 | 客观标准 |
|---|---|
| 写代码 / 修 bug | 能否编译、单测是否跑过 |
| 数学 | 最终答案精确匹配 |
| 结构化抽取 | 是否符合期望 schema/值 |

"够好" = 便宜模型的答案**通过检验**。裁判是测试用例,无主观成分。coding 大量属此。

**家族 B · LLM 当裁判(无客观标准:改写/解释/设计/闲聊)**

- **成对比较(首选)**:同一问题 + 便宜答案 A + 强答案 B,问"A 是否不差于 B?"。
  A 胜或平 → `weak_ok`;B 明显胜 → `needs_strong`。比绝对打分稳定。
- 各自 rubric 打分(次选):差值超阈值才 `needs_strong`。

### 5.3 裁判的已知偏见 + 对策(家族 B)

| 坑 | 对策 |
|---|---|
| 位置偏好 | 两种顺序各跑,结论一致才算数,否则记平 |
| 自我/风格偏好 | 裁判选与候选不同家族的强模型;抹身份标记 |
| 啰嗦偏好 | 提示要求别被长度影响 |
| 非确定性 | 多次投票取多数,温度 0 |
| 裁判不如题难 | 用最强模型当裁判;能走 A 就别走 B |

**铁律:能用家族 A 就绝不用家族 B。**

### 5.4 最深的一点:"够好"里藏着政策旋钮

即使有完美裁判,"有意义"四个字是**商业容忍度**,不是客观事实:
- **严格**:强模型稍好就判 `needs_strong` → 多走强 → 省得少、几乎不掉质。
- **宽松**:强模型明显好很多才判 → 多走弱 → 省得多、掉质风险大。

**这个旋钮 = RouteLLM 的 α = 路由的 threshold。** 完整标准 = **客观/裁判测出的
质量差(事实)+ 政策旋钮(容忍度)**。

两种建模视角:
- **硬二分标签**:Oracle 直接吐 `weak_ok/needs_strong`(旋钮打标签时定死)。简单。
- **概率 + 阈值(RouteLLM 版,推荐)**:Oracle 只记成对偏好,训练预测
  `P(强胜)` 的模型;**α 留到路由时再拧**。好处:同一份数据集,拧 α 就滑动
  省钱/降级,不必重跑昂贵 Oracle。

### 5.5 给一条请求打标签的完整流程

```
输入:请求 Q(带 task_type)
 1. Q → 便宜模型 W → A_w   (记 token/成本/延迟 → 喂模型画像)
    Q → 强模型   S → A_s   (同上)
 2. 按 task_type 选裁判:能客观检验→跑测试/精确匹配(A);否则→成对比较(两序×多投)(B)
 3. 定标签:A_w 达标(过检验/判定不差于 A_s)→ weak_ok;否则 → needs_strong
 4. 存:标签 + 原始比较 + 裁判类型 + 置信度(投票差距/检验是否干脆)
```

**置信度很重要:** 裁判五五开的样本是噪声,训练时标记出来、降权甚至剔除,别让
模棱两可的标签教坏分类器。

### 5.6 标签绑定模型组

标签依赖具体的便宜/强模型对;换模型池标签可能变,厂商更新版本可能要刷新。**数据
集标签绑定在"某组模型的某个快照"上**——所以模型画像/校准是活的、要定期更新。多档
时干净的推广:标签 = "答案达标的最便宜那一档"(依次过各档找最便宜过关者)。v1 先
二分,多档用 `bands` 叠。

## 6. 回放机制:评测在"跑"什么

### 6.1 回放 = 循环调纯函数

```
for 每条样本 in 数据集:
    决策 = Router::route(样本请求, 样本hints, 模型池)   # 纯函数,瞬间,零 API
    预测 = 决策.pool
    对比(预测, 样本.label)
累计 → 指标
```

**回放全程纯函数、零 API、可复现。** 它测的是"派得对不对",不是"答案好不好"。

### 6.2 一次回放要造三样

调 `Router::route`([route.rs:97])需三个输入:

| 输入 | 评测时怎么来 |
|---|---|
| 配置好的 `Router`(由 `RouterConfig`) | **被测对象**:一套权重/阈值/α |
| `ChatRequest` | 从样本 `input.messages` 拼 |
| `&[Candidate]`(模型池) | 造代表用户各档模型的候选;能力填真实值;**健康度一律 Healthy**(别让摘除逻辑搅局) |

### 6.3 深水区一:回放的模型池必须与标签绑定的模型组一致

一条 `weak_ok` 意为"在 {DeepSeek, Opus} 上弱够用";用配成 {GLM, Gemini} 的路由器
回放它**毫无意义**。铁律:**回放装进 Router 的池 = 标签绑定的那组模型。** 换模型 =
换数据集 = 重校准。

### 6.4 深水区二:`Decision` 给的不止预测

- `decision.pool` → 预测(对标签)。
- `decision.decided_by` → **哪层拍的**(rule/hint/heuristic/default),定位错误在哪层。
- `decision.features` → 当时的特征,看"为啥错"(token 估低了 / 关键词没命中)。

**评测不只出准确率,还留下"每条错在哪层、因何特征"——这才是能迭代的东西。**

### 6.5 什么钉死,什么在变

```
钉死:  数据集 + 标签 + 模型组
在变:  Router 配置(权重 / 阈值 / α) —— 每换一套就回放一遍(瞬间)→ 一套指标
```

**搜索更优路由 = 在钉死的数据集上不停换配置回放,挑指标最好的。** 回放免费又瞬间,
一晚能试几百上千套。

### 6.6 测单层还是整链

- **整链(端到端)**:四层一起跑,回答"整个产品路由得好不好"(验收用)。
- **单层(第3层难度打分)**:临时关掉规则/提示层,专调分类器,不被短路干扰(调参用)。

工具要能一键切换。顺带:**确定性自检**(同样本回放两次须字节一致,不一致即报警
有人破了纯函数不变量);**快**(几千条毫秒级)。

## 7. 因果闭环:回放不是收尾,是把分类器调出来的引擎

**常见误解:** "分类器做好后,接真 API 跑任务存数据,再回放迭代参数。" —— 顺序
倒了,数据也混了。

**正解:** 第一批标签**不来自成品分类器,来自 Oracle**;回放吃的是**带标签**数据,
**裸流量不够**(它没有"正确档位"标签,得先过 Oracle)。

```
① 拿到请求      ← 种子集(合成/公开)或上线后真实流量
② Oracle 打标签 ← 离线,调各档真 API + 裁判 → "正确档位"    【调真 API】
③ 回放 + 调参   ← 离线,纯函数,零 API,反复换参数找最优       【回放,不调 API】
④ 部署          ← 调好的分类器上线,每条活请求只调 1 档        【调真 API】
⑤ 回到 ①        ← 真实流量喂回,定期抽样重打标签(②)、重调参(③)
```

- 调真 API 只在 ②(离线打标签)和 ④(线上服务);**回放(③)永不调 API**。
- 真实流量的作用是 ⑤——喂回让数据集越来越贴合实际,是**循环燃料**,不是回放直接输入。

### 7.1 "迭代的参数"到底是什么

| 参数组 | 具体 | 谁调 |
|---|---|---|
| **难度预测器权重** | v1:`tokens_per_point`/`per_tool`/`per_reasoning_marker`/`per_technical_term`/`per_code_keyword`/`per_multi_step_point`… 一整排;v2/v3:小模型学出的权重 | 全局,出厂前拟合 |
| **阈值 / α / bands** | `threshold`(二分切点)、`bands`(多档切点) | 每用户,校准集上定 |

v1 迭代 = 在带标签数据上搜这排 `Weights` + `threshold`(网格搜索/坐标下降,或
逻辑回归拟合后**量化成整数**)。**量化成整数是为守住"整数打分"不变量。**

---

## 8. 指标(第5步 · 规划中,待展开)

把回放结果变成可读结论:

- **混淆矩阵**:真值 {weak_ok, needs_strong} × 决策 {弱, 强}。
- **降级率**:needs_strong 里被派了弱的比例(掉质,最该压低)。
- **省钱率**:总请求里派了弱的比例(以及换算成 token/钱)。
- **α 权衡曲线**:扫 α/threshold,画出"省钱 ↔ 降级"曲线,选运营点。

> 详细指标定义与展示,待第5步专章展开。

  评测集是离线内部产物,不受线上"决策记录不含 prompt"红线约束)。

## 11. 必须守住的不变量

任何路由/评测改动都要遵守(详见《设计不变量》记忆):
1. **路由是纯函数**(无时钟/随机/IO);非纯的分类隔离在网关层,当"特征"喂进内核。
2. **决策记录装不下 prompt**(`RequestFeatures` 是 `Copy`)。评测集是另一回事,
   可含原文。
3. **打分全整数运算**(拟合出的浮点权重要量化回整数)。
4. **插件沙箱**(与本工作流关系较小)。
