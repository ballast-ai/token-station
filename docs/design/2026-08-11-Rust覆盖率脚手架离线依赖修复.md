# Rust 覆盖率脚手架离线依赖修复

## 问题

`develop` 合并提交 `c4ea817` 触发的 CI 中，`rust-coverage` job 在运行
`apps/cli/tests/plugin_devchain.rs` 时失败。测试生成第三方 Provider 脚手架并强制使用
Cargo 离线模式，但该 job 没有像 `rust` 与 Windows 门禁一样预取官方 Provider 的锁定依赖，
干净 runner 因找不到 `wit-bindgen` 而中止。日志中的覆盖率步骤名称具有误导性；实际并未进入
覆盖率阈值判断。

## 目标与范围

- 让所有会运行 `plugin_devchain` 的 CI job 在测试前准备同一份锁定脚手架依赖。
- 增加静态回归门禁，确保未来新增或调整 workspace 测试 job 时不会再次漏掉该准备步骤。
- 保持脚手架测试离线运行，避免将临时 crates.io 故障变成产品回归。

本修复仅调整 CI 依赖准备和对应静态检查，不改变业务代码、桌面界面、用户数据、配置、凭据、
发布签名或版本号。

## 安全与数据红线

- 不允许关闭离线模式来掩盖缓存准备缺失。
- 不允许降低覆盖率阈值、跳过 `plugin_devchain` 或把失败改成可忽略。
- 不读取、生成、上传或记录任何用户配置、密钥和本地数据。
- 不修改用户未跟踪的调研文档。

## 预期行为与失败处理

- `rust`、`rust-coverage` 与 Windows workspace 测试 job 都必须在执行测试前运行同一条
  `cargo fetch --locked --target wasm32-wasip2` 命令，并指向官方
  `provider-openai-compatible` manifest。
- 静态检查发现任一 job 缺失、顺序错误或命令漂移时，以明确英文错误指出具体 job 和缺失项。
- 依赖准备完成后，`plugin_devchain` 仍以离线方式构建生成的脚手架；真实依赖缺失继续硬失败。

## 测试与验收

1. 先运行新增静态检查，确认它能在当前 `develop` 上稳定失败并指出 `rust-coverage`。
2. 只向 `rust-coverage` 增加与既有 job 完全一致的预取步骤，再确认静态检查通过。
3. 运行 `cargo test -p token-station-cli --test plugin_devchain`、Rust 格式检查和相关 CI 策略测试。
4. 推送 PR，等待全部 GitHub CI；合并后再次确认 `develop` 的 `rust-coverage` 通过。
