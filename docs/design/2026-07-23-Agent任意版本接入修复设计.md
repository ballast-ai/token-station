# Agent 任意版本接入：Claude Code、Hermes、OpenCode 修复设计

> 日期：2026-07-23
> 范围：Desktop Agent Discovery、Compatibility、Connector 运行时输入与接入 UI
> 触发证据：Claude Code 多安装无法继续、Hermes 版本探测失败、OpenCode 报“接入缺少虚拟 Key”

## 1. 背景与契约澄清

Token Station 已取消 Agent 最低版本/白名单准入：内置 compatibility blocklist 为空，SemVer、预发布版本、无法解析版本和无版本号均可进入接入流程。

“任意版本可接入”不等于“发现任意路径后直接写配置”。以下安全条件继续保留：

1. 安装路径必须来自最近一次服务端扫描；多安装时必须由用户选择精确 canonical path。
2. 入口必须能以只读、无副作用方式证明可运行。
3. Connector、平台、配置格式和入站适配器必须唯一且可用。
4. 连接计划必须绑定运行实例、精确安装路径、扫描版本（若存在）和确认令牌。

本次问题不是版本限制回归，而是上述安全条件与 UI/Connector/探测命令之间的契约不一致。

## 2. 目标

1. Claude Code 在多安装场景中必须先选择精确路径，选择后可以进入服务端计划与配置投影预览。
2. Hermes 发现只执行本地、只读、无网络依赖的可运行性探测；版本缺失不得成为阻断条件。
3. OpenCode 运行时必须向 Connector 提供本地虚拟 Key，真实计划不再因 Key 缺失被拒绝。
4. 不恢复任何最低版本、白名单或“必须解析出 SemVer”的限制，也不削弱路径、适配器、Connector、确认令牌等安全边界。

## 3. 根因

### 3.1 Claude Code：选择没有转化为 UI 准入

本机同时存在 `~/.local/bin/claude` 和 NVM 下的 Claude Code。服务端为每条扫描记录设置同一个 `conflict_group`，列表状态因此为 `MULTIPLE_INSTALLATIONS`。

服务端 `ScanSnapshot::selected` 已能通过精确路径查询唯一记录、清除该记录的冲突标记并重新执行 compatibility 判断；但前端仍只接受 `DETECTED_VERIFIED`，所以用户选择后按钮继续禁用，计划入口根本没有被调用。

### 3.2 Hermes：版本命令包含网络更新检查

Registry 使用 `hermes version`，超时为 2 秒。Hermes 的该命令会同步调用更新检查，其中 Git/网络操作单次可等待 10 秒。因此网络波动会被误报成 `VersionProbeTimeout`，发生在版本准入之前。

### 3.3 OpenCode：能力声明与配置补丁矛盾

OpenCode Connector 声明 `requires_virtual_key=false`，`AgentProxyRuntime` 因此传入 `token=None`；但 `connect_patch` 和 `validate_projected` 又要求虚拟 Key，导致所有真实接入都稳定失败。

## 4. 执行步骤

### 4.1 先建立失败回归测试

- OpenCode：证明运行时传给 `opencode-v1` 的 token 为空，补丁无法生成。
- Claude Code：证明两份安装选择精确路径后按钮仍禁用。
- Hermes：用假入口证明 `version` 阻塞会触发超时，而本地 `--help` 可以立即成功。

### 4.2 Claude Code 精确选择

- 当 Agent 有多份安装、用户已选择一条精确路径且该记录状态为 `MULTIPLE_INSTALLATIONS` 时，前端将该选择视为可预览接入。
- 调用 `planAgentConnection` 时继续提交精确 canonical path 和扫描到的版本。
- 后端仍以最近一次服务端扫描为事实源；未知、重复或过期路径继续拒绝。

该方案只解除“已由用户精确选择”的冲突，不放宽服务端路径、版本、Connector 或配置预检。

### 4.3 Hermes 本地成功探测

- Registry 将 Hermes 探测命令改为无网络副作用的 `hermes --help`。
- `VersionOutputMatcher` 新增 `SUCCESS_ONLY`：只要求进程在时限内成功退出，不保存 stdout 为 `version_raw`，不要求 SemVer，也不产生“版本无法解析”诊断。
- Hermes 保留“可运行”事实，但版本字段为空；这符合无版本号也可接入的总契约。

### 4.4 OpenCode 虚拟 Key

- 将 OpenCode `requires_virtual_key` 改为 `true`。
- `validate_preconditions` 同时校验入站适配器和虚拟 Key。
- 从运行时生成的 `ConnectInput` 必须能直接通过 OpenCode `connect_patch`，防止元数据与消费者再次分叉。

### 4.5 回归与交付

- 运行三条目标回归、Desktop Rust 全量测试、前端覆盖率、前端生产构建、格式、Clippy 和静态 diff 检查。
- 显式运行默认忽略的本机 Agent 只读 smoke test，验证 Hermes 真实安装可被发现。
- 写入最终验收记录；未达到退出条件时继续修复，不以“代码已改”作为完成依据。

## 5. TDD 验证 seam

1. **OpenCode runtime → Connector**：运行时为 `opencode-v1` 生成的输入包含虚拟 Key，且配置补丁可生成。
2. **Claude UI → plan command**：两份安装初始禁用；选择精确路径后按钮启用，并用该路径和版本调用连接计划。
3. **Hermes Registry → real probe**：模拟 `version` 会阻塞而 `--help` 本地成功的入口；Discovery 必须快速返回 runnable，且不产生版本文本/误导诊断。
4. **真实本机只读冒烟**：扫描当前安装的 Hermes，不安装、不更新、不写配置，结果必须 runnable。

## 6. 通过条件

- Claude Code 多安装选择后能进入配置投影预览，未选择时仍禁止接入。
- Hermes 扫描不执行网络更新检查，不因版本为空而阻断。
- OpenCode 连接计划不再报“缺少虚拟 Key”，虚拟 Key 仍不进入可序列化计划或日志。
- 相关 Rust/React 定向测试、Desktop 全量测试、Clippy、格式、前端覆盖率和生产构建全部通过。

## 7. 退出条件

成功退出必须同时满足：

1. 三个用户可见故障均有独立的先失败、后通过回归测试。
2. Desktop Rust 与前端全量门禁无失败，Clippy 不允许 warning，生产构建成功。
3. Hermes 本机只读 smoke test 通过，期间不安装、不升级、不写 Agent 配置。
4. 设计与验收 Markdown 均已落盘，内容可追踪到代码、测试命令和结果。

若任一条件不满足，Goal 保持进行中；只有需要用户授权的破坏性操作、外部系统不可用且没有安全替代路径时，才允许以阻塞状态退出。
