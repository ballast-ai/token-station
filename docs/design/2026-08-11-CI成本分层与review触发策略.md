# CI 成本分层与 review 触发策略

## 问题、目标、范围和非目标

当前 PR 已经运行完整 Rust 测试、桌面 Rust 测试、前端测试、依赖安全检查和桌面 Rust 覆盖率。`desktop-coverage` 会再次执行桌面 Rust 测试，造成覆盖率计算与功能测试的重复 runner 成本。MSRV 检查也属于合并后兼容性巡检，不需要在每个 PR 重复执行。

目标是降低日常 PR 的 CI 成本，同时保留合并后和发布前的跨平台、覆盖率和最低 Rust 版本验证。

范围仅包括 `.github/workflows/ci.yml` 及其 CI 触发策略检查。非目标包括 release、Desktop Release、Linux Desktop 的正式产物构建、业务代码和测试实现。

## 安全与数据红线

- 不关闭 PR 上的完整 Rust 测试、桌面 Rust 测试、前端测试、依赖来源与安全检查。
- 不让未审查的 PR 代码在 `pull_request_target` 中执行。
- 不改变签名密钥、发布密钥、正式产物或 GitHub Release 权限。
- 不把安装器真实生命周期测试移到普通 PR。

## 用户可见交互、状态变化和失败处理

- 普通 PR：运行 `rust`、`desktop-rust`、`frontend`、`deny`、`audit` 和 `desktop-security`。
- `main`/`develop` push：在 PR 门禁之外运行 Rust 覆盖率、桌面覆盖率、MSRV、macOS 编译检查和 Windows 全 Rust/桌面门禁。
- 已发布 Release 或手动 `workflow_dispatch`：保留上述主干门禁，并按现有条件运行 Windows MSI 生命周期测试。
- 覆盖率、MSRV 或跨平台检查失败时，主干 CI 失败，但不改变 PR 的基础门禁结果。

## 响应式、键盘操作和可访问性要求

本变更不修改应用界面、键盘操作或可访问性行为。GitHub Actions 页面中的 job 名称和失败信息保持清楚、稳定。

## 公开测试边界、验收标准和真实 App 检查项

公开测试边界是 workflow 事件与 job `if` 条件。验收标准如下：

1. `desktop-coverage` 和 `msrv` 不在 `pull_request` 事件执行。
2. `rust-coverage`、macOS 编译检查和 Windows 全门禁继续不在 `pull_request` 执行。
3. PR 的 Rust、桌面 Rust、前端、安全和策略检查仍然存在。
4. Windows MSI 仍然只允许已发布 Release 或手动验证触发。
5. `scripts/check-ci-msi-trigger-policy.mjs`、`scripts/check-ci-scaffold-prefetch.mjs` 和新的触发策略检查通过。

本变更不需要真实 App 检查，因为不修改可执行文件或应用界面。发布前仍由现有 release workflow 和 Windows MSI 生命周期测试负责真实产物验收。

## 实现落点、已知遗留项和发布要求

实现落点是 `.github/workflows/ci.yml` 中 `msrv` 与 `desktop-coverage` 的事件条件，以及 `scripts/check-ci-review-trigger-policy.mjs` 的静态策略检查。覆盖率和 MSRV 仍可通过 `workflow_dispatch` 手动验证，并会在 `main`/`develop` push 上执行。

已知遗留项：GitHub Actions 的实际计费分钟数需要在仓库的 Actions usage 页面观察一个合并周期后确认，本设计不虚构节省金额。若主干 push 过于频繁，下一步可以再把覆盖率改成定时或仅 `develop`，但那会降低主干反馈及时性，暂不默认开启。

发布要求：这是 workflow 和检查脚本变更，不需要重装桌面 App。合并前必须通过本地策略检查和相关 YAML 静态检查。
