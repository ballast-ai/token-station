## 为什么单独归档

分类器（把请求分到高/中/低档、预测强模型胜率）是一条**独立的、重的技术线**，有自己的数据采集、标注、训练、评测、版本管理流程，已经在 `orion-shield-train` 单独推进。它不应该和「配置写坏、Agent 接管、响应说谎」这类工程可靠性问题混在同一批需求里做——那些是发布红线，分类器是产品差异化的中期投资。

因此本次把 PR 里所有分类器相关项**从落地队列移出**，集中记在这里，等可靠性红线清完、真实流量数据到位后再单独立项。

## 一、这几份 PR 对分类器提出的核心判断（值得采纳的认知）

### 1. 现状是一个真实缺陷：路由器在测「请求有多大」，不是「任务有多难」（R5 / F8 / 洞察 5）

- `RequestFeatures` 统计**全部历史 token、消息数、声明工具数**；`Heuristic::score` 对每个工具**线性加分**。
- Claude Code 每次固定携带约 25 个工具定义，仅工具项就约 **+500 分**，导致「你好」「改一句文案」也稳定被判成高档。
- **合理性：成立，且是一手实测**（真实流量已证实合成特征全爆表、常数特征问题——与我们记忆里"合成 v1 全爆表"一致）。这不是纸面推测。

### 2. 特征必须拆开，脚手架不能算难度（F8 `RoutingInput`）

建议把输入拆成互不混淆的几组：

```
task         当前用户任务 + 明确 task hint      → 参与难度判断
requirements 必需能力/隐私（tools/json/vision/context/region）→ 只做硬过滤
context      上下文容量/预计传输/成本          → 影响窗口、延迟、费用，不等于难度
scaffold     系统提示 / 工具目录               → 只用于识别与能力过滤，不直接算难度
runtime      健康 / 价格 / 延迟 / 缓存          → 候选排序
```

- 25 个声明工具 = 「候选模型必须支持 tools」，不是「+500 难度分」。
- 历史 token 影响窗口/延迟/费用，不自动等价难度。
- **合理性：高。这是修正上面缺陷的正确方向。**

### 3. 质量路由的正确范式：预测胜率，不是关键词打分（F8）

- RouteLLM 的有价值思路是**预测「强模型相对弱模型的胜率 P(strong wins)」**，而不是手写复杂度分。
- 落地路径：真实 coding-agent 任务集 → 强/弱模型各跑 → 任务测试结果+人工偏好+离线 LLM judge 打标 → 训练本地低延迟分类器 → `α` 表示可接受的质量-成本边界 → 先 shadow（旧路由执行、新路由只记录建议）→ 达非劣效门槛再逐步启用。
- **合理性：与我们北极星（抄任务类型 + RouteLLM 胜率分类器）完全一致**，可作为分类器线的工程规格补充。

### 4. 若干必须坚持的约束（和我们的红线一致）

- 分类器**热路径不得远程调用 LLM judge**；judge 只用于离线标注。
- 分类器读取内容只在内存；持久化只存**数字、模型版本、决策结果**，不存 prompt/response 正文。
- 分类器 artifact 要**版本化、签名、可回滚**；每个路由决策可重放（策略版本、分类器版本、数值特征、候选快照、阈值完整）。
- 显式指定模型**永远绕过分类器**（override 最高优先级）。

## 二、需要注意的边界：哪些看起来像分类器、其实要留在主文档

PR 把「选档」和「容灾」经常写在一起（洞察 32 / TS-ROUTE-003），但这是**两道题**，只有前半属于分类器：

| 事项 | 归属 | 说明 |
|---|---|---|
| 按难度选高/中/低档 | **本文档（分类器，暂不做）** | 需要训练与评测 |
| 三档都配了但每档只有一个模型、坏了不跨档 = 没有容灾 | **主文档（现在就做）** | 这是 `RecoveryPolicy` 与选档解耦的工程问题，不依赖分类器，是发布前要澄清的误导性承诺 |
| 「不降质省成本」「下档自动兜底」的对外话术 | **主文档的"诚实边界"动作** | 分类器就绪前，产品/文案不得宣传"简单任务自动走便宜且不降质"；这一步是**改文案，不写分类器代码**，所以放主文档 |

## 三、分类器线单独立项时的最小规格（备忘，不排期）

当决定重启分类器时，直接从这里接：

1. **数据**：真实 coding-agent 任务集，覆盖简单问答、改文案、单文件修改、跨文件重构、测试修复、工具循环、长上下文、总结、失败恢复。（真实流量已采足：脚本 92 题 425 样本 + 真实交互 2670 条，可进打标签阶段。）
2. **标签**：同任务强/弱模型各跑，用任务测试结果 + 人工偏好 + 受控 LLM judge 形成标签；Oracle 存答案 + 多裁判。
3. **模型**：本地低延迟分类器预测 `P(strong wins)`；artifact 版本化/签名/可回滚。
4. **上线**：先 shadow → 非劣效门槛 → 灰度启用。
5. **对外声明纪律**：宣称「质量保持率」前必须报告样本分布、基线、置信区间、成本变化；没有证据时只写「目标」，不写「事实」。
6. **回执字段**（与主文档 Request Receipt 对接）：`decided_by / task_type / classifier_version / score / threshold / selected_pool / candidate_count / exclusion_counts`，全部无正文。

## 四、结论

- 这几份 PR 对分类器的**认知判断是对的、且是一手实测支撑的**，尤其"固定工具表污染打分"这个缺陷值得记牢。
- 但它是独立重线，本次**不排期**；仅保留两件低成本动作到主文档：①`RecoveryPolicy` 与选档解耦（工程，不含分类器）；②分类器就绪前的**话术诚实边界**（改文案）。
- 分类器本体在 `orion-shield-train` 继续，按上面「最小规格」推进。
