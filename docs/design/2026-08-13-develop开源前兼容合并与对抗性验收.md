## 安全与数据红线

- 原工作区未暂存/未跟踪内容均是用户数据，不得 stash、clean、移动、覆盖或纳入提交。
- Agent 写入继续使用边界计划、revision 校验、所有权记录、私有备份与原子替换；断开不得删除非受管数据。
- 网关保持 loopback、默认本地鉴权、出站目标与凭据绑定、严格本地路由 fail-closed。
- 插件不得获得网络、文件、环境、继承标准输入输出或明文凭据能力。
- 模型限制与价格只能来自可证明来源；零值、部分价格、冲突候选和过期目录不得伪装成可信事实。
- 本地安装只替换 bundle id 为 `com.tokenstation.desktop` 的 `/Applications/token-station.app`；失败保留旧 App。
- 不强推或绕过 `develop` 保护；最终使用合规中文 squash 提交，等待 required checks 后再合入。

## 远端 Linux 门禁回归（2026-08-13）

PR #86 首轮 `desktop-rust` 在 Ubuntu 的严格 Clippy 暴露平台条件编译缺口：macOS 状态栏安装、按 generation
启动/停止及 Dock reopen 只在 macOS 调用，但对应模块和闭包局部变量在非 macOS 目标仍参与编译，因而被
`-D warnings` 判为 dead code / unused variables。本机 macOS Clippy 无法发现该类目标相关缺陷。

修复边界限定为条件编译与 lint 可见性，不改变运行时契约：只在 macOS 声明仅供状态栏调用的函数和变量；
跨平台保留纯状态策略测试。`desktop_shell` 模块在非 macOS 仍需编译无操作的刷新入口并承载单元测试，因此
只对该模块在非 macOS 允许 dead code，且不放宽 unused、Clippy 或其他模块警告。修复后必须重跑本机
Desktop fmt/Clippy/test/rustdoc，并以新的 GitHub CI 全绿作为 Linux 验收证据。

本机复验结果：Desktop fmt、`clippy -D warnings`、rustdoc、350 单测与 21 集成测试全部通过。干净工作树
首次安装因尚未执行 `npm ci` 而在 `npx tauri` 解析阶段停止，事务安装未删除旧 App；补齐锁定前端依赖后，
`scripts/install-local-desktop.sh` 完成 release 构建、artifact audit、签名校验、固定路径替换和启动。

PR #86 第二轮 Ubuntu Clippy 将错误收敛到最后一个仅由 macOS snapshot 与跨平台单元测试使用的
`desktop_shell_applying_phase`。该纯策略函数调整为仅在 macOS 或测试构建声明；未新增全局 lint 豁免，
也未改变任何目标平台的可执行分支。

PR #86 第三轮 Ubuntu 前端覆盖率运行在 235 秒后失败：Agent 显示偏好测试的默认 IPC mock
未处理 App 每 500 ms 执行的 `get_runtime_state`。本机快速运行时用例在首次轮询前结束，慢速 CI 则会
额外生成轮询错误 toast，导致“只有一个 alert”的隐式时序假设破裂。产品实现已按稳定 ID 去重，
该失败是默认测试替身不完整，不是产品重复通知。修复为默认 mock 返回初始 `serve` 快照，保留专项
轮询失败测试对真实错误去重的覆盖。

同一轮 `desktop-rust` 与 `desktop-coverage` 均在
`ensure_serve_running_joins_starting_and_rejects_a_failed_apply` 的首次 Starting join 等待 30 秒后超时。
该路径中等待方通过 `spawn_blocking` 占用 Tauri/Tokio blocking pool 循环读取状态，而启动准备和完成发布
也需要同一 blocking pool。这一结构在慢速、覆盖率或高并发环境存在等待者挤压完成者的资源饥饿
风险，不应通过扩大 30 秒超时掩盖。修复边界为：状态检查仍只短时持有 App mutex，轮询间隔改用
Tokio 异步定时器，不占用 blocking 工作线程；保留 generation 中断、Applying 失败闭合和有界超时错误码。
验收需要 Desktop 定向/全量测试、Clippy/rustdoc、本地 App 事务安装与代理启停复验，最终以 Ubuntu 两个任务均通过为准。
本机以 `--nocapture` 复验还暴露了测试装配缺口：发布 Running 后的 Agent 模型元数据刷新会读取
`AgentCommandState`，而四个真实启动测试的 mock App 只注册了 `AppStateManaged`，导致后台完成任务在状态
发布后 panic。这些测试必须使用现有 `manage_test_agent_state` 装配真实必需状态，不得在生产路径改为
缺状态时静默跳过刷新。

修复后定向 Starting/Applying join 用例约 0.5 秒通过且 `--nocapture` 无后台 panic；Desktop
350 单测、10 更新集成测试、2 本地安装测试、9 YAML 回归测试全部通过，2 项显式入口按设计忽略；
Desktop fmt、`clippy -D warnings` 与 rustdoc 通过。`scripts/install-local-desktop.sh` 重新完成 release 构建、插件
实装自检、artifact audit、ad-hoc 签名、固定路径替换与启动。真实 App 从 stopped 启动后仅监听
`127.0.0.1:8787`，无鉴权 `GET /v1/models` 返回 401；通过真实 UI 停止后恢复 stopped 且端口关闭。

第四轮 Ubuntu 中 `desktop-coverage` 已完整通过同一套生命周期测试与两个覆盖率门槛，但普通
`desktop-rust` 仍在同一 Starting join 用例超时；失败捕获中没有 `prepare_server` 的任何阶段日志。
这说明测试夹具中额外创建的“sleep 30 ms 后发送 channel” OS 线程没有在普通并行调度下及时释放
启动准备。用例在 `started_rx` 已证明状态处于 Starting/Applying 后，由主测试线程直接发送释放信号；
`ensure_serve_running_with` 调用时仍会 join 正在完成的 generation，但不再把测试成败绑定到第三个线程的
任意调度时机。不放宽产品超时，不降低并行测试数。

第五轮将 gate 改为主测试线程直接释放后，覆盖率任务仍在相同 30 秒点超时，因此否定了“额外
OS 线程未调度”这一假设。真正的资源窗口在生产 `begin_serve_start_inner`：它先等待一次
`spawn_blocking(prepare)` 完成，再发起第二次 `spawn_blocking(complete_serve_start)`。高并发时第一个
worker 已释放，完成发布却需重新排队，生命周期可长时间停在 Starting/Applying。修复为单个
blocking 任务内连续执行 prepare 和 complete，使已获得 worker 的 generation 能原子地推进到发布结果；
prepare panic 必须捕获并转换为 `startup_task` 失败，不得将生命周期永久留在 Starting。

第五轮修复后的公开回归验证通过：Starting/Applying join 定向用例约 0.44 秒完成，连续重复 50 次
零失败；新增 prepare panic 场景证明生命周期会进入 Error、保留稳定 `startup_task` 诊断且可再次启动。
Desktop 并发全套 350 项通过、2 项显式入口按设计忽略，更新 10、安装 2、YAML 9 项集成测试通过；
fmt、`clippy -D warnings` 与 rustdoc 通过。`scripts/install-local-desktop.sh` 再次完成官方插件实装自检、
release 构建、artifact audit、ad-hoc 签名、固定路径替换和启动健康检查。最终真实 App 通过 UI 从 stopped
