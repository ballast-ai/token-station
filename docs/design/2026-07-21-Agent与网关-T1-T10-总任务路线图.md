## 1. 文档用途

本文是 T1–T10 的执行索引和长期 Goal 操作手册，不替代权威任务书，也不承载所有子系统的详细设计。

长期 Goal 必须用本文确定：

- 当前应该做哪一个任务；
- 任务开始前依赖是否满足；
- 缺少详细规格时应进入哪个设计周期；
- 哪些测试构成当前任务或 Gate 的完成证据；
- 哪些情况可以转向独立任务，哪些情况必须暂停等待用户或接口负责人；
- 何时才允许把整个 Goal 标记为完成。

要求优先级从高到低为：

1. 用户在当前任务中的明确决定和已确认勘误；
2. 权威任务书及其最新 Contract A/B；
3. 已批准并提交的子规格；
4. implementation plan；
5. 现有代码惯例。

发现冲突时不得自行选择低优先级规则覆盖高优先级规则。

## 2. 长期 Goal Objective

创建 Goal 时使用以下 objective：

```text
在 /Users/liuwenhao/Desktop/公司/token-station 中，严格依据 docs/design/2026-07-21-Agent与网关-开发任务书.md 与 docs/design/2026-07-21-Agent与网关-T1-T10-总任务路线图.md，按依赖和 Gate 顺序完成 T1–T10 的设计、实施、测试、验收记录和本地提交，所有新 commit message 使用中文。每个尚无批准规格的子项目必须先完成 brainstorming、规格审阅和 implementation plan，再写实现；不得另立 Contract A/B 同名类型。持续推进所有不受阻塞的任务，保留用户未跟踪文件，不执行 push、合并 PR、发布、真实凭据操作或其它外部写操作，除非用户另行明确授权。只有 T1–T10 全部达到各自验收标准、全量门禁通过、无未解决范围项时，才能将 Goal 标记为 complete。
```

创建 Goal 不等于授权 push、合并、发布、删除文件、调用真实付费上游或跳过设计审批。

## 3. 启动前检查

Goal 第一次运行必须按顺序完成：

1. 确认工作目录和当前分支，读取 `git status --short --branch`。
2. 记录所有既有未跟踪和未提交文件，视为用户资产，不暂存、不覆盖、不删除。
3. 拉取远端引用，确认当前工作基于已合入 PR #40 的 `develop`。
4. 读取权威任务书、本文和当前任务的已批准子规格。
5. 检查 Contract 骨架是否已落地：

   ```bash
   rg -n "struct RequestContext|enum StreamOutcome" apps crates plugins
   ```

6. 检查任务书是否更新；若 Contract 签名或任务顺序变化，先同步规格，不直接实现旧设计。
7. 确认 Rust、WASM 与前端工具链可用：

   ```bash
   rustup target list --installed
   cargo --version
   node --version
   npm --version
   ```

8. 只在依赖缺失时安装 `wasm32-wasip2` 或运行 `npm --prefix apps/desktop ci`，不得无原因升级依赖。
9. 规格批准后使用 Codex 内置 Plan 能力创建并维护 implementation plan，不依赖外部 `writing-plans` skill。

## 4. 总体依赖与执行顺序

```text
Baseline：PR #40 已合入 develop
│
├─ Contract 对齐：Contract A/B 骨架与取消时序确认
│
├─ Gate A：T1 → T2
│
├─ 独立安全通道：T4（可在等待 Contract 时推进）
│
└─ Gate B：T5 → T6 → T3
    │
    └─ Gate D：T8 → T10 → T7 Phase 0/1 → T9
```

强制顺序：

- T2 依赖 Contract B。
- T5、T6 依赖 Contract A 的唯一 settle 出口和 fixtures。
- T6 必须在 T5 的错误终态语义稳定后完成。
- T3 使用稳定后的能力与错误表达，排在 T5/T6 后。
- T10 依赖稳定的 attempts/settle 语义与 T5 分类。
- T9 依赖 T5 的 `ErrorCode` 扩展。
- T4 不依赖 Contract A/B，可在等待外部骨架时作为独立进度通道。
- T7 本轮只交付 Phase 0/1；Phase 2 Agent 挂载不擅自提前扩入范围。

## 6. 子规格拆分

每个条目独立完成 spec → plan → implementation → verification 周期：

1. Gate A：T1 + T2，使用现有 Gate A 规格。
2. Gate B-1：T5 + T6，围绕 Contract A、错误终态和 SSE 完整性共同设计。
3. Gate B-2：T3，单独设计能力诚实、最终 URL 与拒绝边界。
4. Gate C：T4，单独设计 EgressPolicy 和安全 E2E。
5. Gate D-1：T8，Provider 生命周期与目录版本化。
6. Gate D-2：T10，Receipt 数据模型、隐私和成本语义。
7. Gate D-3：T7 Phase 0/1，Profile 数据层与最小 UI。
8. Gate D-4：T9，错误到用户动作的映射。

不得把所有任务塞入一个详细规格。总路线图只负责跨任务依赖和完成状态。

## 7. 每个子项目的执行循环

### 7.1 设计门

如果当前子项目没有已批准规格：

1. 检查当前代码、相关文档和近期提交。
2. 使用 brainstorming 提出 2–3 个实现方向。
3. 分节确认架构、数据流、错误处理和测试。
4. 写入 `docs/design/`，自审后本地提交。
5. 请求用户审阅；未批准前不得开始实现。

长期 Goal 可以在等待某个设计审批时整理证据或推进不依赖该设计的任务，但不得绕过审批实现该子项目。

### 7.2 计划门

规格批准后：

1. 使用 Codex 内置 Plan 能力，生成逐文件、逐测试的 implementation plan。
2. 明确 Contract 类型来源，禁止重复定义。
3. 把计划写入仓库并本地提交。
4. 计划必须包含红灯测试、最小实现、回归和 Gate 验证顺序。

内置 Plan 必须持续更新步骤状态；不能只在开始时生成清单，随后脱离计划实施。

### 7.3 实施循环

每个计划步骤执行：

1. 写或启用能复现目标行为的测试。
2. 运行测试，确认失败原因与目标一致。
3. 实现最小改动。
4. 运行目标测试直到通过。
5. 运行受影响模块测试。
6. 检查 diff，排除无关重构和用户文件。
7. 形成语义完整的本地提交。

遇到测试失败或意外行为，先定位根因，不用扩大改动范围掩盖失败。

### 7.4 验收循环

任务退出前：

1. 逐条执行权威任务书的验收场景。
2. 把真实命令、通过数量、失败数量和关键证据写入 `docs/verification/`。
3. 对照本文任务表确认依赖方可以安全消费当前结果。
4. 只有 fresh verification 通过后才能更新任务状态。

## 9. Contract A/B 操作规则

1. 实现前从代码确认类型真实位置和最新签名。
2. `StreamOutcome` 与 `RequestContext` 只存在一个权威定义。
3. T2 负责 server/serve lifecycle 侧的 RequestContext 创建、注入和 drain 编排。
4. T5/T6 负责错误分类、预算消费和 StreamOutcome 映射，不直接写成功状态。
5. Contract A 的 `settle` 是唯一终态状态写入口。
6. 用户已确认的勘误是“先 grace 5 秒，超时后 cancel”。任务书旧段落仍写“立即 cancel”，因此 T2 开始前必须由接口负责人把该语义同步到 Contract B 骨架或明确确认；若骨架仍冲突，停止 T2，不得伪造兼容层绕过签名。
7. Contract B 必须提供 server 创建 `RequestContext`、注入父 token 和绑定客户端断开的公开入口；文本只有私有字段与查询方法时不满足实施前置。

## 10. Git 与工作区规则

- 在同一个仓库目录和专用本地分支工作。
- 每次暂存都使用显式文件路径，不运行 `git add .`。
- 不覆盖、移动、暂存或删除任务开始前存在的未跟踪文件。
- 不使用 `git reset --hard`、`git checkout --` 等破坏性命令。
- 每个提交只表达一个完整意图，测试与实现尽量同提交。
- 所有新提交的 subject 和必要 body 使用中文，保留代码标识符、协议名和命令原文。
- 未经用户授权，不 push、不创建或合并 PR、不发布。
- 未经用户明确要求，不创建 sub-agent 或把任务委派到其它任务线程。
- 上游 `develop` 变化时先检查重叠和冲突，再 rebase；不得静默丢弃本地提交。

## 11. Goal 持续运行规则

每个 Goal turn 开始时：

1. 读取 Goal 状态和剩余预算。
2. 读取本文任务状态与最新 git 状态。
3. 选择依赖已满足的最靠前未完成任务。
4. 执行一个可以验证并提交的闭环，而不是同时铺开多个半成品。
5. 更新验证证据和路线图状态后再进入下一闭环。

遇到阻塞时：

- 缺 Contract A/B：优先推进 T4 或尚未依赖 Contract 的规格工作。
- 等待设计审批：可以准备其它子项目的上下文和设计，但不能实现未批准方案。
- 缺 CI 专用工具：完成其它验证并明确记录未运行项。
- 需要 push、合并、真实账号、真实 Key 或外部系统写操作：停止该动作并请求授权。
- 只有同一阻塞连续出现、且所有独立工作都已耗尽时，才能按 Goal 规则标记 blocked。

不得因为任务困难、运行较久、测试较慢或预算接近耗尽而虚假标记 complete。

## 12. 全任务完成定义

只有同时满足以下条件，Goal 才能标记 complete：

1. T1–T10 全部达到第 5 节退出条件。
2. 每个子项目均有批准规格、implementation plan 和可追溯提交。
3. Contract A/B 没有重复定义或未解决签名分歧。
4. 任务书要求的 fixtures、红线 E2E 和真实切换验收全部通过。
5. 第 8 节 Gate 门禁与最终覆盖率门禁获得 fresh passing evidence。
6. `docs/verification/` 包含每个 Gate 的真实验收记录，且不声称未运行的检查已通过。
7. `git diff` 不包含无关改动，用户既有未跟踪文件保持未提交。
8. 没有 TBD、TODO、已知失败或被静默移出范围的任务书要求。
9. 最终报告列出任务状态、提交、验证命令、通过结果和仍需用户授权的外部动作。

push、PR 合并和发布不属于本 Goal 的默认完成条件，除非用户后续明确加入目标。
