# 首页最近请求刷新设计

> 日期：2026-07-31
> 状态：已实现并通过真实 App 验收
> 范围：首页「最近 5 次请求」的读取时机、刷新反馈与失败处理
> 基线：`28073ee`

## 1. 问题、目标、范围与非目标

### 1.1 问题

`RecentReceipts` 当前仅在组件挂载时读取一次。用户停留在首页继续发起请求时，
列表不会变化，必须离开页面、重启 App 或重新挂载组件才能看到新回执。这会让用户
误判请求没有经过 Token Station，削弱路由回执作为操作反馈的价值。

### 1.2 目标

1. 首页可见时，每 10 秒读取一次最新 5 条终态回执。
2. 用户切回 Token Station 窗口时立即读取一次。
3. 用户可随时通过明确的「刷新」按钮主动读取。
4. 同一时间最多存在一个读取请求；重复触发只合并为一次后续读取。
5. 后台刷新不清空旧列表、不回到首屏 loading，也不破坏仍存在回执的展开状态。
6. 一次后台刷新失败时保留最后一次成功数据，并清楚标记数据可能陈旧。

### 1.3 范围

- `RecentReceipts` 的前端读取调度和公开状态。
- 标题区域的自动刷新说明、最近成功更新时间和手动刷新按钮。
- 对应组件公开行为测试、响应式样式和真实桌面 App 验收。

### 1.4 非目标

- 不展示请求进行中状态；回执仍只在请求终结并写入 SQLite 后出现。
- 不新增 WebSocket、SSE、SQLite 文件监听或 Tauri 事件协议。
- 不修改 `/admin/receipts`、Tauri IPC、数据库结构和隐私数据模型。
- 不新增可配置刷新间隔；首页固定使用 10 秒，避免为单一列表增加设置负担。
- 不把首页改造成实时流量图表或监控大盘。

## 2. 安全与数据红线

1. 继续只读取结构化无正文回执，不新增 prompt、response、原始 header、明文 Key
   或可承载自由正文的字段。
2. 刷新只访问现有本机管理 API 或 Tauri IPC，不产生公网请求。
3. 管理 API 鉴权和 HTTP → IPC 回退行为保持不变。
4. 自动刷新不得绕过现有最多 5 条的前后端硬限制。
5. 失败信息只展示现有读取错误，不拼接或输出敏感请求内容。
6. 组件卸载后不得提交异步结果，也不得启动已排队的后续读取。

## 3. 用户可见交互、状态与失败处理

### 3.1 标题区

标题右侧使用一个紧凑工具组：

```text
最近 5 次请求       每 10 秒自动刷新 · 10:42:08 更新   5 条   [刷新]
```

- 首次成功读取前显示「每 10 秒自动刷新」。
- 成功后显示本地时间，例如「10:42:08 更新」。
- 手动刷新期间按钮显示「刷新中…」并禁用，避免重复点击。
- 条数仍表示当前展示数量，不表示累计请求数。
- 刷新按钮遵循项目采用的 shadcn/ui 组件语言：等价于 `Button`
  的 `variant="outline"`、`size="sm"`，加载时在文字前放置等价于
  `Spinner` 的 16px 状态图标。由于当前桌面前端尚未安装 shadcn/Tailwind，
  本次使用现有 `.btn` 与设计 token 实现等价行为，不引入第二套运行时组件依赖。

### 3.2 状态机

```text
未加载 ──首次读取──> 已加载
   │                   │
   └──失败──> 首次错误  ├──定时/聚焦/手动刷新──> 后台刷新
                       │                         ├──成功──> 已加载
                       │                         └──失败──> 陈旧数据警告
                       └──列表为空──> 空态
```

- 首次读取：保留现有居中 loading。
- 后台读取：旧列表保持可读，不降低整体透明度，不收起已有详情。
- 后台失败：旧列表保持；标题工具组下方显示弱错误「更新失败，当前显示上次数据」。
- 后续成功：清除弱错误并更新成功时间。
- 初次失败且没有旧数据：继续使用显著错误态。

### 3.3 刷新调度

1. 挂载后立即读取。
2. 页面 `visibilityState` 为 `visible` 时，每 10 秒触发一次。
3. `window` 获得焦点时立即触发一次。
4. 页面不可见时，定时器可继续计时但不得访问数据接口。
5. 读取进行中再次触发时，不并发读取，只记录一个待执行刷新。
6. 当前读取结束后，若组件仍挂载且存在待执行刷新，则只补读一次。
7. 新结果的 5 个 `request_id` 与当前列表完全一致时，不替换列表状态；
   终态回执不可变，因此无需因相同结果重渲染列表。

## 4. 响应式、键盘与可访问性

1. 刷新按钮使用原生 `button`，可通过 Tab 聚焦并用 Enter/Space 触发。
2. 按钮具有稳定的可访问名称「刷新最近请求」，刷新时暴露 `aria-busy=true`。
3. 自动刷新说明和更新时间不使用持续 `aria-live`，避免屏幕阅读器每 10 秒播报。
4. 错误提示使用合适的 status/alert 语义；后台失败不夺取键盘焦点。
5. 窄屏下标题与工具组允许换行，按钮保持至少 32px 高，文本不与计数徽标重叠。
6. 刷新旋转动效仅作用于按钮图标；`prefers-reduced-motion: reduce` 时关闭。
7. 既有回执摘要的键盘展开、详情内容和可访问名称保持不变。

## 5. 公开测试边界与验收标准

测试只通过渲染后的 `RecentReceipts` 和浏览器公开事件观察行为，不测试私有函数。
`getRecentReceipts` 作为本机数据边界允许 mock，时间作为系统边界使用假定时器。

### 5.1 公开行为测试

1. 挂载立即读取，成功后展示回执、更新时间和可用刷新按钮。
2. 点击「刷新最近请求」读取新结果，旧列表在等待期间保持显示。
3. 页面可见时经过 10 秒自动刷新；页面隐藏时经过多个周期也不读取。
4. 窗口获得焦点时立即刷新。
5. 慢读取期间的多个定时/聚焦触发不重叠，结束后只执行一次合并刷新。
6. 初次读取失败展示显著错误；已有数据后的失败保留旧列表并展示陈旧数据警告。
7. 组件卸载后忽略迟到结果且不启动排队刷新。
8. 后端异常返回超过 5 条时仍只显示 5 条。

### 5.2 真实 App 检查项

1. 在 1040×720 桌面窗口首页完成一次真实代理请求，10 秒内出现新回执。
2. 连续完成至少两次请求，列表顺序与终态一致且不闪空。
3. 点击刷新按钮，按钮 busy 状态与更新时间可见。
4. 展开一条仍在最新 5 条内的回执，后台刷新后保持展开。
5. 切换到其他应用后返回，列表立即更新。
6. 缩窄窗口检查工具组换行、按钮焦点和回执摘要无水平遮挡。
7. 验证请求/响应正文仍未出现在界面、日志和回执数据库中。

- 如果未来需要展示流式请求进行中状态，必须另行设计请求生命周期记录，
  不能把当前终态回执伪装成进行中事件。

## 7. 实现与验收记录

### 7.1 实现状态

已完成：

1. 首页挂载立即读取，前台每 10 秒读取，窗口聚焦立即读取。
2. 手动刷新采用 shadcn/ui `outline + sm + spinner` 等价实现。
