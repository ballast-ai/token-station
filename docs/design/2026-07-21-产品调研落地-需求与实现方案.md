## 1. 优先级总览

| 级别 | 主题 | 为什么是这个级别 |
|---|---|---|
| **P0** | 状态绝不能写坏 | 会写坏用户配置、劫持宿主 Agent、泄露路径——发布红线，也直接触碰我们四条设计红线 |
| **P1** | 响应绝不能说谎 + 请求生命周期 | 核心结果错误：空成功/半句成功、取消不生效、保存不应用——违背"响应不说谎"与"整数打分/纯函数"之外的可靠性底线 |
| **P2** | 产品闭环（配置分层 / Provider / 回执） | 有绕法但影响体验与可信；前端在此，需克制 |
| **P3 / 远期** | 异步作业 / 多模态 / 发布系统 / UX 打磨 | 需求未验证或非阻塞 |

发布门槛（四道门，取自 #38，去掉分类器那道）：
1. **状态安全门**：任意失败/崩溃后，配置、Key、Agent 接入都能对账或恢复。
2. **协议正确门**：任何响应都有明确终态；不可表达的语义明确失败，绝不静默丢。
3. **产品事实门**：UI 的状态、费用、错误、路由解释都来自带 revision 的运行事实。
4. ~~路由可信门~~ → 移交分类器专项。

## 2. P0：状态绝不能写坏（发布红线）

### P0-1　Agent 接入必须事务化、可逆、可恢复 ★最高优先，命中已知 footgun
- **来源**：洞察 12/27/31、F2、TS-AGENT-001（第五轮事故）。
- **问题**：点首页 Codex 接入直接覆盖 `~/.codex/config.toml` 顶层 `model/model_provider`；两次真实 Responses 请求经 `:8787` 落到本机 `qwen3:4b`；固定 `.token-station.bak` 被接管配置污染，无法回到接入前；stop 不恢复；动态端口可能写 `:0`；用户接入后手改会被整文件恢复覆盖。
- **合理性/必要性**：**最高**。真实发生、有时间线+metrics 证据；且形成自依赖死锁（用 Codex 开发 TS，TS 把 Codex 接管了）。直接违反我们的"CC 接入 footgun"安全闸假设——安全闸只挡了 CC，Codex 侧仍是活的。
- **方案要点**：
  - `AgentEnrollmentManager` 状态机：`Detected→Prepared→BackupDurable→ManagedPatchApplied→Verified→Active`，失败→`RollbackPending`。
  - 「添加 Provider」与「设为全局默认」**分开**；默认只加可选 Provider，不改顶层默认模型。
  - 全局切换需：结构化 diff + 影响范围 + 短期**接入租约**（首请求失败/到期未确认自动回滚）。
  - **不可变 original 快照**（只写一次）+ 污染检测（待备份已指向 TS 就标 contaminated）。
  - 恢复用**三方合并**（Base/Ours/Theirs）：只撤回 Ours，不覆盖用户后续手改。
  - 先 bind Gateway 拿真实端口再写；端口变更重写 Live。
  - **独立逃生命令** `agent status/disconnect/restore`（不依赖 Gateway/App，即使代理全坏也能撤销）。
  - 检测到"宿主 Agent 正在开发 TS"场景 → 强提醒。
- **验收**：连点接入 100 次原始 hash 仍可恢复；每步 kill -9 可 reconcile；`:0` 最终写真实端口；官方→TS→官方三段 E2E 通过。
- **前端**：仅需把接入状态显示为 `未检测/可接入/接入中/已接入/漂移/代理不可达/待恢复`，主操作按状态变化（待恢复时主按钮=恢复）。**不新增页面**。

### P0-2　统一配置仓库：稳定 UUID + revision + 耐久写入 + Secret Saga
- **来源**：F1、洞察 2、TS-PROVIDER-002、源码疑点 6.13/6.14/6.15/6.23。
- **问题**：Provider **名称当主键**，同名新增/重命名会覆盖；Key 先写 Keychain 后写配置，失败留孤儿凭证；刷新模型等无关操作会顺带保存草稿；固定临时文件名、无锁、缺 fsync，崩溃窗口不完整。
- **合理性/必要性**：**高**，是 P0-1/P0-3 的地基（没有稳定 ID 和事务，接入与运行态都无从谈起）。
- **方案要点**：`ConfigRepository` + `OperationJournal`，所有写走命令不直接覆盖整份 JSON；核心对象用不可变 UUID；提交走 `Begin→Validate→Stage secret→temp+fsync→atomic rename→fsync dir→publish→finalize→journal`；Keychain 用可恢复 Saga（宁留可清理旧 Key，不让配置指向不存在 Key）；软删除 + 引用迁移；模型发现只写目录缓存，不提交 Provider/路由草稿。
- **验收**：同名新增/旧 revision 保存/并发双进程保存不覆盖；每步 kill -9 可 reconcile；取消编辑后 Keychain 无新引用；Provider 重命名后引用仍有效。
- **前端**：无新增；保存按钮语义依赖 P0-3。

### P0-3　draft / saved / running 三态分离 + Runtime Supervisor
- **来源**：F3、洞察 2、TS-STATE-007（第六轮实测）、疑点 6.6/6.16/6.17。
- **问题**：UI 草稿、磁盘配置、运行 Gateway 是三份状态；「保存并应用」实测**只保存没应用**（磁盘改成新模型，下一条请求仍走旧模型）；顶部状态只看内存 `Option<RunningServer>`，不核对真实端口/Codex 是否仍指向代理。
- **合理性/必要性**：**高**。用户被误导以为已换模型（费用/能力/数据路径全判断错）。
- **方案要点**：三个不可混淆版本 `draft_revision / saved_revision / running_revision`；运行更新走 `prepare→preflight→atomic Arc swap→drain old`；Runtime API 只返运行事实（带 running_revision/实例 ID/心跳），不可达时显示"运行态未知"**绝不回退成草稿**；`APP runtime stopped / listener reachable / Agent connected` 是**三个独立字段**，不再压成一个 running 布尔。
- **验收**：运行中 A→B 改并 Apply 后，下一条请求命中 B，Receipt/Runtime API/UI 同一 running revision；apply 失败继续用 A 并显示"已保存但未应用"；runtime 崩溃后 1 秒内 UI 不再显示 running。
- **前端（简洁做法）**：只在保存区显示四态文案——无改动/有未保存更改/已保存尚未应用/运行中 revision N。**这是"让 UI 不说谎"的最小前端改动，值得做**；不引入复杂 diff 视图（可后置）。

## 3. P1：响应绝不能说谎 + 请求生命周期

### P1-1　统一 SSE 字节解析器 + StreamOutcome + pre-commit 检查点
- **来源**：F4、洞察 33、TS-CCS-003~008、TS-PROTO-007/009/017（第六轮）。
- **问题**：CRLF / `data:` 无空格 / 多行 data / 跨 read UTF-8 被错误解析；`event:error`、顶层流错误被吞；上游说半句话后关闭被当成功，甚至触发 `observe_success`；首个 SSE 事件损坏时 fallback 命中 0。
- **合理性/必要性**：**高**。Agent 拿到半截/空/乱码却当成功——直接违背"响应不说谎"。有双上游隔离实测。
- **方案要点**：共享 RFC 兼容字节级 SSE decoder 先分帧再交 Adapter，网络 chunk 永不 `from_utf8_lossy` 后按字符串切；提交 200/首事件前加**有界 pre-commit checkpoint**（字节/时间上限）；`relay_stream` 必须返回 `StreamOutcome{Complete|FailedBeforeOutput|FailedAfterPartial|ClientCancelled}`，只有 `settle(outcome)` 能写成功；checkpoint 前失败可在预算内换候选，提交后禁止透明重放。
- **验收**：F4 的 12 组 fixture 进 CI（LF/CRLF/中文 emoji 字节拆分/多行 data/event:error/一个 delta 后 EOF/首事件非法 JSON+有 fallback…）；任一出现空成功/半句成功/健康记成功则 CI 失败。
- **前端**：客户端明确显示"上游在输出后中断，内容不完整"+安全重试；无新增页面。

### P1-2　错误分类 / 重试预算 / HalfOpen / cache 计量统一
- **来源**：F6、TS-CCS-001/009/010/011、TS-OR-006/007、N3/N4、TS-PROTO-017。
- **问题**：HTTP 200 内嵌 error 当空成功；半截 body 归 Internal；`200 + 非法 JSON` 归自身 Internal → attempts=1、fallback=0；Retry-After 解析了不执行；无全局 retry budget / HalfOpen 单探针；堆叠 Content-Encoding 不透明 500；cache>input 被接受。
- **合理性/必要性**：**高**。损坏的 200 会阻断已配置的 fallback（用户配了备用却没用上）。
- **方案要点**：统一错误枚举（Auth/PaymentRequired/RateLimit/Capacity/UpstreamUnavailable/TransportTruncated/ProviderProtocolError/Capability/ContextLength/PolicyDenied/Timeout/ClientCancelled/Internal）；处理顺序 transport→HTTP status→2xx body 协议终态→才记成功；`AttemptBudget{max_attempts/max_elapsed/per_attempt_timeout/max_cost}`；按错误类型定重试/换 Provider 表；HalfOpen 每 upstream 单 permit；Content-Encoding 栈按逗号解析、逆序解码、限压缩比，单层 gzip 保持通过；cache 计量带 anomaly 标记。
- **验收**：200+error / 空 choices / 429+Retry-After / 402/404/529 / 半截 / 非法 JSON 全部正确分类；20 upstream 全 503 不超预算；cooldown 后 50 并发只放一个探针。
- **前端**：无。

### P1-3　请求生命周期：RequestContext（取消传播 + 并发准入）
- **来源**：F 第四轮（TS-LIFECYCLE-001/TS-LOAD-001/TS-HEALTH-001/TS-LIMIT-001/002）、洞察 30、R11。
- **问题**：客户端约 1 秒取消后上游继续跑到 5 秒并记成 200；40 并发全部击穿无准入；健康只按 upstream 聚合（一个模型失败摘除同站其他模型）；声明 10MB 实际约 2MB 被框架先拒。
- **合理性/必要性**：**高**。"停止"没止损还记成功——费用与统计双失真。
- **方案要点**：共享 `RequestContext` 绑定客户端断开/总 deadline/当前 attempt/计量终态/取消信号；统一执行器 `admit→route→attempt→stream/collect→settle`；global/Agent/Provider 三级并发许可 + 排队上限 + 协议化 429；健康键改为 `upstream + wire model`，连接级故障才上卷；入站/上游 body 大小各一个事实源，超限进统一失败终态不误记 200。
- **验收**：断开后规定时间内上游观察到连接关闭且 SQLite 不记 200；压测峰值不超配置；模型 A 连续失败后 B 仍可候选。
- **前端**：停止按钮显示"正在取消/已取消/上游是否终止 + 已产生多少消耗"。

### P1-4　故障恢复策略与选档解耦（RecoveryPolicy）—— 不含分类器
- **来源**：洞察 32、TS-ROUTE-003、F8 的**恢复部分**（选档部分见分类器归档）。
- **问题**：桌面每档只生成一个成员，router 又不离开已选 pool → 三档都配了也**没有容灾**；用户被"下档兜底"文案误导。
- **合理性/必要性**：**高，且不依赖分类器**，可独立落地。这是纠正一个误导性可靠性承诺。
- **方案要点**：把"选哪个质量档"和"选中的坏了怎么办"建成两个对象；`RecoveryPolicy{Strict|Degrade|Escalate|Ordered}`；跨档前重做硬能力/上下文/隐私/预算过滤；每档允许多候选，档内与跨档顺序分开配。
- **验收**：Strict 无候选明确失败；Degrade/Escalate/Ordered 按配置跨档并记录质量变化；每档只有一个模型时 UI 显示"备用 0"。
- **前端（简洁做法）**：在现有三档区旁增一个**只读的"故障备用"状态行**（strict / 允许降档 / 备用 N），不新建复杂配置面；未开启容灾时**移除"下档自动兜底"文案**。
- **诚实边界（改文案，不写代码）**：分类器就绪前，暂停"简单任务自动走便宜且不降质""下档自动兜底"的绝对承诺。

### P1-5　能力诚实：Endpoint URL 预览 + Runtime Capability Resolver
- **来源**：洞察 16/17、N1/N2/N5、F5/F7 的能力诚实子集。
- **问题**：完整 endpoint 被重复追加成 `/v1/v1`（404）；`[1M]` 显示后缀泄漏进 wire model id；catalog 宣称 `json_schema=true` 但 Inbound Adapter 真实请求拒绝；工具能力被静默清空。
- **合理性/必要性**：**中-高**，其中 URL 预览是**低成本高价值**（迁移最常见 404）。
- **方案要点**：typed endpoint resolver 统一处理 origin/`/v1`/尾斜杠/完整 endpoint，保存前显示 Chat/Responses/Messages 最终 URL；wire_id 与 display/context marker 分离；同一个 Runtime Capability Resolver 计算有效能力（`模型声明 ∩ Inbound ∩ IR ∩ Provider ∩ 策略`），`/models`/目录/路由过滤/真实请求共用；能力四态 `verified/declared/unsupported/unknown`，unknown 不当 supported；tool arguments 永不变空串。
- **验收**：base URL 三种形态都只生成一个正确路径；display/context 改变不污染 wire id；catalog verified 的能力必须过真实请求。
- **前端**：Provider 编辑页加"最终 URL 预览"一行（低成本）；能力显示四态标签。

### P1-6　出站路径显式：默认不跟随 redirect、不读环境代理
- **来源**：洞察 26、F12 EgressPolicy、本地已存在的 S1/S2 补丁（待进 CI）。
- **问题**：自动 redirect 可能把 Authorization 带到未授权第二跳；自动读 `HTTP(S)_PROXY` 让流量经用户未选择的中间层。直接关系"密钥/请求去了哪"的核心承诺。
- **合理性/必要性**：**中-高**（安全/信任）。本地已有 `max_redirects(0)` / `proxy(None)` 补丁，需补 E2E 并固化。
- **方案要点**：`EgressPolicy` 默认 fail-closed；如需企业代理，产品内显式配置 + 每跳重校验 + 写入回执 + 跨主机不转发原 Authorization。
- **验收**：恶意 302 到其它域/loopback/metadata、同域 redirect、环境代理捕获三组测试进 CI。
- **前端**：无（可选：安全页显示实际出口）。

## 4. P2：产品闭环（前端在此，务必克制）

### P2-1　配置分层：Profile + Agent 挂载（Clash 心智，两档，防下拉爆炸）
- **来源**：R2、洞察 5/6/7/29、F9、配置心智 Clash 专项。
- **问题**：全局只有一套三档，Claude Code / Codex / OpenCode 被迫共用。
- **合理性/必要性**：**中-高**，契合 app 化方向；但**极易过度设计**，必须采纳调研自己给的克制版。
- **方案要点（采纳克制版）**：
  - **只管三样**：节点库（upstreams）/ 策略组（3–5 个，稀缺命名资源）/ 挂载（Agent→策略）。
  - **两档心智**：简单档=全体跟 Global；分流档=策略组+挂载。
  - 继承 `session > project > agent > global`，每层只存 patch。
  - **不发明"每个 Agent 私有策略"**；要特例就建一个场景组。
- **前端（简洁做法）**：**一张"挂载板"**（左策略库 / 右 Agent 拖拽），不给每个 Agent 塞巨型下拉；未拖过的 Agent = 隐式跟默认；策略数超阈值二次确认。分阶段：Phase 0 文案承认"现在等于只有 Global" → Phase 1 可复制 router 为 Profile 托盘切 → Phase 2 按 Agent 挂载。**Phase 0/1 成本低可先上，Phase 2 视需求再做。**

### P2-2　Provider 生命周期闭环 + 可信模型目录
- **来源**：R3、F7、洞察 1/23/34、TS-CAP-004。
- **问题**：新增/Key/发现/测试/定价/能力/删除分散；新模型默认 `tools=true/128k`；刷新只做并集，下架模型残留；删除不提示影响。
- **合理性/必要性**：**中**。
- **方案要点**：Provider 详情页合并 Add/Edit/Test（分阶段 DNS→鉴权→模型→流式→tool→JSON）/Catalog/Usage/Delete（引用预览+软删除）；模型目录版本化（能力四态+来源+last_seen+catalog_state active/stale/removed）；刷新给 diff，不静默删被引用模型。
- **前端**：合并到 Provider 详情页；避免新增独立页。

### P2-3　无正文 Request Receipt（路由回执）
- **来源**：R6、F10、洞察 13/19。
- **问题**：看不到为什么选这个模型、fallback 了谁、真实 Provider、错误在哪；`cost_micros` 无价格表支撑。
- **合理性/必要性**：**中**。是"让路由价值可见"和隐私可验证的关键，但依赖 P0-2/P1 先就位。
- **方案要点**：`requests/decisions/attempts/conversion_reports` 四表，**硬隐私边界**（无 prompt/response/原始 header/明文 Key）；成本三态 `actual/estimated/unknown`，`cost_status=unknown` 不参与"最便宜"承诺（洞察 19）；本地模型不写 0 成本。

**必做的最小前端**（都服务于"不说谎"）：保存区四态文案（P0-3）、接入状态 7 态（P0-1）、故障备用只读状态行（P1-4）、Endpoint 最终 URL 预览（P1-5）、能力四态标签（P1-5）、停止按钮真实态（P1-3）、最近 5 次请求一行回执（P2-3）、人话错误（P2-4）。
