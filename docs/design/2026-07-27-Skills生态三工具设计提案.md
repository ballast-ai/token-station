# Skills 生态三工具设计提案

> 日期：2026-07-27
> 状态：提案（未立项，待评审排期）
> 范围：三个新产品面——Skill 安全审计工具、官方插件市场、Agent 用量分析工具
> 核心边界：三者都不得触碰隐私正典——指标库字段仅限数字 / 闭集枚举 / 配置内名字，请求内容永不落盘；任何一项都不引入代理内的 prompt 内容检测

## 1. 背景

原始想法包含四个方向：监控 skills 使用频度、统计 skills token 用量、skills 安全审计、
精选 skills/MCP/插件市场。评估后收敛为三个可落地的工具，并明确排除一个方向：

- **排除「代理内检测 skill 使用」**。在代理里识别"当前请求在用哪个 skill"需要解析
  请求内容（Claude Code 的 Skill tool_use 块、system-reminder 注入格式），存在三个
  硬伤：①与指标库隐私正典直接冲突（skill 名不是配置内名字，写入即破约束，金丝雀
  测试会失败）；②耦合特定 Agent 客户端的私有格式，客户端升版即碎；③归因口径不
  成立——skill 内容注入上下文后，后续每个 turn 的 input tokens 都包含它，"某 skill
  用了多少 token"无法准确定义。
- **拆分「第三方 skills/MCP 精选市场」为远期项**。该方向是独立产品（策展、托管、
  治理、社区运营），赛道已有 Anthropic 官方 marketplace、smithery、mcp.so 等；唯一
  可行差异化是"经过安全审计的精选源"，即其价值依赖本提案的审计工具先建立话语权。
  不进本提案范围，待审计工具有声量后另行立项。

战略说明：token-station 的既有画像是"BYOK 隐私敏感开发者"，本提案将产品面向
Agent 层（skills / 插件生态）扩展。这是有意的战略决策，不是顺手为之——代理位置
天然适合做本地 AI 可观测性，且三者全部复用既有基建与信任叙事。

## 2. 三个工具总览与优先级

| 优先级 | 工具 | 形态 | 复用的既有基建 | 商业角色 |
|---|---|---|---|---|
| P1 | ② Skill 安全审计 | 本地 CLI，独立可发布 | 信任叙事（签名 / 可复现构建 / 沙箱） | 流量入口，建立「skill 安全」话语权 |
| P2 | ③a 官方插件市场 | 云端目录 + CLI 下载安装 | 三层分发 system 层、Ed25519 manifest、conformance | 注册解锁云功能漏斗的落地触点 |
| P3 | ① Agent 用量分析 | 本地 CLI，读 Agent transcript | 无（独立工具，刻意不进代理） | 免费信任资产，Claude Code 用户获客 |

排序理由：P1 无外部依赖、最贴品牌、可单独发布拉流量；P2 基建现成但依赖云端账号
体系上线节奏；P3 价值确定但差异化最弱，且完全独立，随时可做。

## 3. P1：Skill 安全审计工具

### 3.1 问题

SKILL.md 是给模型的可执行指令，是真实且几乎无人覆盖的攻击面：prompt injection、
诱导数据外传（"把结果 curl 到某域名"）、附带恶意脚本 / 二进制、preamble 里的
静默网络请求。用户从社区安装 skill 时没有任何审计手段。

### 3.2 目标

1. 对本地 skill 目录（`~/.claude/skills`、`.claude/skills`、插件缓存目录）做静态扫描。
2. 检出闭集规则命中：出站网络调用及其目标域名、危险命令模式（rm -rf / curl|sh /
   keychain 访问等）、指令层攻击特征（诱导忽略先前指令、诱导外传上下文）、
   混淆载荷（base64 内联脚本、不可见字符）。
3. 输出分级报告（信息 / 可疑 / 危险），每条命中给出文件、行号、规则 ID 与解释。
4. 完全离线运行，零遥测，与隐私叙事一致。

### 3.3 非目标

- 不做运行时行为监控或沙箱执行（skill 由 Agent 客户端执行，不在我们的运行时内）。
- 不承诺检出全部恶意 skill——静态扫描定位为"供应链卫生检查"，不是杀毒软件。
- 第一版不做 LLM 辅助语义分析（引入模型调用会破坏"完全离线"卖点，远期可作为
  可选项）。

### 3.4 形态与边界

- 独立子命令（如 `token-station skill-audit <path>`）或独立小工具二进制，倾向后者
  以便单独传播；规则库随主仓版本化，规则本身开源可审计。
- 与代理零耦合：不读指标库、不经过路由、不要求 serve 在运行。

## 4. P2：官方插件市场（③a）

### 4.1 问题

插件三层分发（内嵌 / 系统官方签名包 / 本地未签名，B0–B3 已落地）中，system 层
的"官方签名包"目前没有分发渠道——用户无法发现和获取官方插件，最后一公里缺失。

### 4.2 目标

1. 云端插件目录：官方（及后续经审计的社区）WASM 插件列表，含 manifest、签名、
   conformance 通过证明、版本历史。
2. CLI 安装流：`plugin search / install / update`，下载后本地校验 Ed25519 签名与
   manifest 才落入 system 层目录，校验失败拒绝安装。
3. 注册门槛：浏览目录免注册；下载安装需登录云端账号——这是"注册解锁云功能"
   漏斗（2026-07-09 拍板）的第一个非同步类落地触点。

### 4.3 非目标

- 不接受未经签名 / 未过 conformance 的第三方直传（社区投稿走审计流程后由官方签名，
  流程本身另行设计）。
- 不做评分、评论、推荐算法等社区功能——冷启动无量时是空转，留待第三方市场立项
  时再议。
- 不改变本地未签名层（custom）的行为：用户自建插件照常本地加载，与市场无关。

### 4.4 边界

- 下载是显式用户动作触发的出站请求，遵循既有原则（同匿名版本检查：永不后台）。
- 云端只见"谁下载了哪个插件"这一层元数据，与 L2 承诺一致；不上传任何本地配置。

## 5. P3：Agent 用量分析工具（①）

### 5.1 问题

用户想知道"哪些 skills 常用、各花了多少 token"。如 §1 所述，代理内检测不可行；
但 Agent 客户端（Claude Code 等）已在本地留有完整数据：`~/.claude/projects/*.jsonl`
transcript 记录了每次 Skill 调用与逐 turn 的精确 usage。

### 5.2 目标

1. 独立本地 CLI，解析 Agent transcript，输出：skill 调用频度、按会话 / 项目聚合的
   token 用量、模型分布、时间趋势。
2. 归因口径明确声明：报告"skill 激活期间的 turn 用量"，并注明上下文注入导致的
   归因模糊，不假装精确。
3. 只读、完全本地、零上传。

### 5.3 非目标

- 不进代理、不写指标库、不动隐私正典——这是独立工具，与 serve 进程无任何交互。
- 第一版只支持 Claude Code transcript 格式；其他 Agent（Codex 等）格式按需追加。
- 不做实时监控，只做事后分析（transcript 是客户端私有格式，实时 tail 的维护成本
  不值得）。

### 5.4 风险

transcript 是 Claude Code 未承诺稳定的私有格式，升版可能破坏解析。缓解：解析层
独立模块 + fixture 测试锁定各已知版本格式；解析失败明确报"格式不支持"而非静默
出错数据。

## 6. 与隐私正典的关系（三者共同约束)

- 指标库 schema 不因本提案新增任何字段；金丝雀测试无需变更。
- 代理数据面（请求路径）零改动。
- 新增出站仅一处：P2 的目录浏览与插件下载，均为显式用户动作触发。
- P1 / P3 完全离线，可作为隐私叙事的正面案例写入产品文档。

## 7. 开放问题

1. P1 / P3 作为主二进制子命令还是独立小工具发布？（倾向独立，便于传播与独立
   版本节奏，但增加发布工程负担。）
2. P2 依赖云端账号体系的上线时间，需与托管平台开发计划对齐排期。
3. P1 规则库的维护节奏与社区贡献流程（规则误报的反馈渠道）。
4. 第三方精选市场（③b）的立项条件：P1 发布后以什么指标（下载量 / 社区引用）
   判断话语权已建立。
