## 0. 先说清楚范围

**本轮只保证「语言模型」接入。** 视频、语音、embedding 都不接。所以：

- **异步作业系统不做**（submit→poll→通知那套长任务机制），多模态请求只做诚实拒绝（见 T3）。
- **但 SSE / StreamOutcome 要做，而且优先。** 注意别误会：**SSE 不是视频协议**，它就是语言模型流式吐文字 token 的传输格式（你调 OpenAI `stream:true`、Anthropic streaming，上游都是 `data: {...}\n\n` 一帧帧推）。`StreamOutcome` 要挡的是「上游吐半句就断连、我们却记 200 成功」这种纯文字链路的说谎——和视频无关。

## 2. 任务详单

### T1　P0-2 收尾：模型发现缓存不得污染 Provider 草稿
- **做什么**：刷新/发现模型只写「目录缓存」，绝不顺带写进待保存草稿。
- **怎么做**：确认 `model_catalog.rs::discover_with_cache` 只落 `CacheEntry`（`base_url/models/fetched_at_ms`），不 touch `AppInner.draft`；目录缓存与配置草稿两条独立存储路径，发现操作对 `draft_revision`（见 T2）无副作用。
- **验收**：连续刷新 N 次，草稿 revision 不变、保存按钮不亮「有未保存更改」。

### T2　P0-3 运行态三态分离 + Runtime Supervisor　★你这边最大的活
- **做什么**：把「草稿 / 已保存 / 正在运行」彻底分三份，修掉「保存并应用只保存没应用」；顶部状态不再压成一个 `running` 布尔。
- **怎么做**：
  - 三个独立版本号 `draft_revision / saved_revision / running_revision`。`running_revision` 在**服务真正 publish 成功**那一刻打在 AppState 上（`serve_lifecycle.rs::publish`）。
  - 「保存并应用」走 `prepare→preflight→切换→drain 旧`，不是直接改 `router.pools` 或简单重启。⚠️切换与 drain 的时序、取消信号怎么灌进在飞请求，**严格按第 3 节 Contract B**。
  - Runtime API 返回运行事实，拆成独立字段，不许压成一个 bool：
    - `app_runtime: stopped | running`（内核 serve 任务在不在）
    - `listener_reachable: bool`（真去连 `listen` 探一下）
    - `agent_connected: bool`（Codex/CC 等是否仍指向我们代理）
    - 外加 `running_revision` + 实例 id。
  - 运行态不可达时显示「运行态未知」，**绝不回退成草稿态**。
- **验收**：运行中把 A 档改成 B 并 Apply 后，下一条真实请求命中 B，且 Runtime API / UI / 回执三处 `running_revision` 一致；apply 失败继续用 A 并显示「已保存但未应用」；kill 掉 serve 任务后 1 秒内 UI 不再显示 running。
- **前端（最小）**：保存区四态文案 `无改动 / 有未保存更改 / 已保存尚未应用 / 运行中 revision N`。不做 diff 视图。

### T3　P1-5 能力诚实 + 多模态诚实拒绝
- **做什么**：① 修最常见的 `/v1/v1` 404；② 能力四态；③ 非语言请求返回 typed 错误，不超时假装支持。
- **怎么做**：
  - endpoint 已有 `ProviderEndpoint`（`crates/protocol/src/provider.rs`）统一处理 origin/`/v1`/尾斜杠；你补**保存前在 Provider 编辑页显示最终 URL 一行**（Chat/Responses/Messages 各自最终 URL）。
  - 能力四态 `verified / declared / unsupported / unknown`；`unknown` 不得当 `supported`；前端展示四态标签。
  - 多模态能力路由（2026-07-23 决策更新）：image 进入 Canonical IR，只路由到 `vision=declared/verified` 的模型；无视觉候选时在上游前返回 `ErrorCode::Capability`。audio/embedding 继续在 Host 层前置拒绝，不建异步 Task 面。
- **验收**：base URL 三种写法只生成一个正确路径；catalog 标 verified 的能力必须过真实请求；发一条 vision 请求得到明确 typed 错误，不是 60s 超时。

### T4　P1-6 出站路径显式
- **做什么**：默认不跟随 redirect、不读环境代理，避免把 Authorization 带到第二跳或经用户没选的中间层。
- **怎么做**：gateway 构造 `ureq::Agent` 处（`gateway.rs` 约 260 行）显式 `max_redirects(0)` + `proxy(None)`；封 `EgressPolicy` 默认 fail-closed；跨主机重定向不转发原 `Authorization`。本地已有补丁但没进主线，你补 E2E 固化。
- **验收**：恶意 302 跳其它域 / loopback / metadata、以及设了 `HTTPS_PROXY` 三组用例进 CI，全部不外泄。

### T5　P1-2 错误分类 / 重试预算 / Retry-After
- **做什么**：把「200 内嵌 error」「半截 body」「非法 JSON」正确分类成失败而非空成功；补重试预算；让 Retry-After 真生效。
- **怎么做**：
  - 扩 `ErrorCode`（`crates/protocol/src/error.rs`，现有 `InvalidRequest/Auth/RateLimit/Capacity/Capability/ContentPolicy/UpstreamUnavailable/Timeout/Internal`）：新增 `PaymentRequired(402)`、`TransportTruncated`、`ContextLength`、`ProviderProtocolError`（2xx 协议非法）。
  - 处理顺序固定 `transport → HTTP status → 2xx body 协议终态`，最后才允许记成功；200 body 带 error 字段归 `ProviderProtocolError`。
  - `AttemptBudget { max_attempts, max_elapsed, per_attempt_timeout, max_cost }`，在 `dispatch`（`gateway.rs` 约 593）fallback 循环里消费。
  - Retry-After：`error.rs` 已有 `retry_after_ms`、plugin 已解析，但 `gateway.rs` 没按它 sleep——补上（受 `max_elapsed` 约束）。
  - ⚠️**你只负责「分类成 ErrorEnvelope」和「消费预算」。记不记成功不由你写——所有终态交给第 3 节 Contract A 的 `settle`，禁止在 `dispatch/try_upstream` 里直接 `record.status = 200`。**
- **验收**：`200+error / 空 choices / 429+Retry-After / 402 / 404 / 529 / 半截 / 非法 JSON` 全部落到正确 `ErrorCode`；20 个上游全 503 时不超 `AttemptBudget`。

### T6　P1-1 SSE 字节解析器（接口按 Contract A）
- **做什么**：修 `relay_stream`（`gateway.rs:817`）当前对网络 chunk 直接 `String::from_utf8_lossy(&buffer[..read])`（854 行）造成的跨 read UTF-8 截断、CRLF、`data:` 无空格、多行 data 解析错误。
- **怎么做**：
  - 网络字节**先进字节缓冲、按帧（`\n\n` / `\r\n\r\n`）切分**，帧完整了再交 plugin 的 `stream_parser`；跨 read 的半个 UTF-8 字符和半个帧留 tail，不 `from_utf8_lossy`。改 `StreamChunk` 承载字节（或 gateway 侧维护 byte tail）。
  - decoder 主要落在 `plugins/official/provider-openai-compatible/src/lib.rs` 的 `stream_parser`/`parse_chunk`。
  - ⚠️`relay_stream` 的返回类型、以及「什么算收完整 / 什么算半截」由第 3 节 **Contract A（StreamOutcome）** 定义，你按那个 enum 返回；**判定成功/失败的 CI fixture 由我提供**，你的实现要过我那套 fixture。
- **验收**：我给的 12 组 fixture（LF/CRLF/中文 emoji 按字节拆分/多行 data/`event:error`/一个 delta 后 EOF/首事件非法 JSON…）全过；任一出现空成功或半句成功则 CI 失败。

## 3. ★接口对齐规范（硬约束，我定，你按此实现）

> 你的任务里凡标 ⚠️ 的地方都以这里为准。接口如需微调我在此更新并通知你；**不要在别处另立同名类型**。这两个接口是我们唯一会撞车的地方（T2/T5/T6 ↔ 我的 P1-3）。

### Contract A — `StreamOutcome` + 单一 `settle` 出口

**动机**：现在 `dispatch`（`gateway.rs:614`）上游 Ok 时无脑 `record.status = 200`，`relay_stream`（817）即使中途断裂也只返回 `()` 只 set `error_code`——于是半截流照样记 200。这是「响应说谎」的根。

**我定义的类型**（最终位置我给）：

```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum StreamOutcome {
    Complete,           // 上游正常收尾：[DONE] / finish_reason / message_stop
    FailedAfterPartial, // 已发 BeginStream 之后断裂/解析失败：输出不完整
    FailedBeforeOutput, // 提交前失败（0 字节过 checkpoint）：可在预算内换候选
    ClientCancelled,    // 客户端断开 / drain 截止：主动取消
}
```

**`relay_stream` 改为返回 `StreamOutcome`**（不再是 `()`）。

**`settle` 规则（唯一写 status 的地方，我实现在 `chat()` 收尾即现 488 行附近）**：

| outcome | record.status | 健康 | 可 fallback | 备注 |
|---|---|---|---|---|
| `Complete` | 200 | `observe_success` | — | **只有这一档允许 200** |
| `FailedAfterPartial` | 502 或上游状态，`error_code` 必填 | `observe_failure` | 否（禁止透明重放） | 客户端收到「输出后中断」事件 |
| `FailedBeforeOutput` | 由 `ErrorCode` 决定 | `observe_failure` | 是（预算内换候选） | 走 dispatch fallback |
| `ClientCancelled` | 499 | 既不 success 也不摘除健康 | 否 | 取消不是上游的错 |

**对你（T5/T6）的硬约束**：
1. 在 `try_upstream / dispatch / relay_stream` 里**一律不许直接写 `record.status = 200`**。
2. 你的职责是把坏情况**分类成 `ErrorEnvelope`（正确 `ErrorCode`）**、把流收尾**映射成 `StreamOutcome`**，交我的 `settle`。
3. 「200 body 内嵌 error」「半截 body」在 T5 分类完，最终经 `settle` 落库，不得自己判成功。

### Contract B — `RequestContext`（取消传播 + drain）

**动机**：`server.rs:249` 用 `spawn_blocking` 跑 `gateway.chat`，取消只有「下次 `emit` 时 `blocking_send` 失败」这一被动路径；阻塞的 `reader.read()` 不会因客户端断开而返回。于是「客户端 1 秒取消、上游跑到 5 秒还记 200」。你的 T2 drain 旧 server 需要同一套信号。

**我定义的类型**：

```rust
pub struct RequestContext {
    cancel: CancellationToken,     // 触发 = 停止本请求（客户端断开 / drain 截止 / deadline 到）
    deadline: Instant,
    per_attempt_timeout: Duration,
}
impl RequestContext {
    pub fn is_cancelled(&self) -> bool;
    pub fn remaining(&self) -> Duration;
    pub fn child(&self) -> CancellationToken; // 交给 http 客户端做 abort
}
```

**`gateway.chat` 签名新增 `ctx: &RequestContext`**（我改 gateway 侧并消费）。

**归属划分**：

- **你（server 层，`server.rs` + `serve_lifecycle.rs`）负责「创建 + 注入 + drain 编排」**：
  1. `server.rs::chat` 里每个请求 new 一个 `RequestContext`，把 axum 客户端断开绑到 `cancel`。
  2. `RunningServer` 持一个 **drain `CancellationToken`**，作为每个请求 `cancel` 的**父 token**——drain 一拉，所有在飞请求的 cancel 一起触发。
  3. 把 `ctx` 传进 `gateway.chat(..., &ctx)`。
- **我（gateway 层）负责「消费」**：透传 `ctx`；每次 `reader.read()` 前后查 `is_cancelled()`；给上游 socket 设 `per_attempt_timeout` 让 `read` 周期性返回好检查取消；取消时返回 `StreamOutcome::ClientCancelled`。

**T2「保存并应用」drain 时序（你实现，用上面的 drain token）**：

```
1. prepare_server(new_config)   // 构建新 Gateway + 校验，先不占端口
2. preflight(new)               // 新 Gateway 自检
3. 释放旧 listener              // 停止新连接落旧 server；已 accept 的连接不受影响
4. bind 新 listener（同端口）→ publish 新 server；running_revision := new
5. old.drain.cancel()           // 拉旧 server 的 drain token
6. 等待最多 DRAIN_GRACE（如 5s）让旧在飞请求自然收尾
7. 到点仍在飞的：其 RequestContext 已因 drain 被 cancel → 走 ClientCancelled 快退
8. drop 旧 runtime
```

必须满足的性质（无论你怎么实现）：
- 切换中新请求要么落新 server、要么短暂 connection-refused，**绝不落到「已保存但内核还是旧模型」的旧 server**。
- 旧 server 在飞请求要么 grace 内跑完、要么被 drain-cancel，**不许被硬 drop runtime 拦腰截断记成 200**。
- `running_revision` 只在第 4 步 publish 成功后更新；失败保持旧值 + 上报「已保存但未应用」。
- 同端口切换的 bind 空窗尽量小（可用 `SO_REUSEADDR`），记在 PR 说明里。
