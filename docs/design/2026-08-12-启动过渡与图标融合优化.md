# 启动过渡与图标融合优化

- 日期：2026-08-12
- 状态：已实现并验收
- 范围：Desktop 启动 Agent discovery、正常启动过渡、全局路由身份图标、Provider 图标容器
- 不涉及：路由数据面、Provider 配置格式、持久化 discovery 缓存、DMG、远端推送或发布

## 1. 问题与事实基线

用户反馈每次进入 Token Station 都需要长时间停留在“正在进入”页面；主页固定首行的 `TS`
字母标记偏斜且没有产品语义；Direct 供应商行中的 DeepSeek Avatar 又被深色圆角方盒包住，
形成与卡片背景割裂的双层图标。

本机同一安装包连续执行 5 次完整退出后重启，首个可见状态为 0.60—0.66 秒，主页 Ready
为 4.57—5.82 秒，中位数 4.60 秒。3 秒体验门槛稳定为红。只读 profiling 进一步确认：

1. 正常前端在 `get_state + list_agent_registry + scan_agents` 全部完成前只显示居中 loading。
2. `scan_registry` 对 9 个 descriptor 串行处理；本机 6 个实际版本 probe 的串行下界约
   1.8 秒。
3. 每个新进程会重新 SHA-256 三个主要 Agent 二进制，体积约 243 MiB、208 MiB、131 MiB；
   顺序 `shasum` 约 1.18 秒，3 路并行约 0.50 秒。
4. 当前进程内 hash cache 在读取整个文件期间持有全局 Mutex；仅并行 descriptor 仍会让
   hash 串行。
5. 忽略的真实平台 discovery debug test 完成一次扫描需要 33.50 秒，其中 user CPU
   30.51 秒；debug 数字不等同 release 体验，但证明冷哈希是实质成本。
6. Tauri setup 还同步执行 Recovery 检查、配置加载和历史成本回填；本机数据库只有 4 行且
   没有待回填项，不是当前 4.60 秒主因，暂不扩大本轮范围。

视觉根因同样可确定：`.agent-master-item > span:not([data-slot="badge"])` 误命中
`.agent-master-icon`，覆盖其水平居中；普通 Agent 使用 absolute 居中而掩盖了问题，文本
`TS` 直接暴露偏移。ProviderIcon 使用已经包含品牌背景的 `Icon.Avatar`，Direct、Provider
管理和免费供应商页又各自添加 surface、border 与圆角外壳。

## 2. 目标与成功口径

1. 每个进程仍执行一次完整 fresh Agent scan，但不同 Agent 的只读 discovery 最多 3 路
   并行；结果排序、原子提交和安全信息保持确定。
2. hash 文件读取不持有全局 cache 锁；相同 path/fingerprint 并发请求只计算一次，缓存仍只
   在当前进程有效。
3. 同一机器安装后连续 5 次完整退出重启，主页 Ready 中位数目标不高于 3.0 秒，较 4.60 秒
   基线至少降低 35%；若机器负载导致未达标，必须报告实测而不能只宣称“更快”。
4. Recovery 与 State 完成后立即显示稳定 App 壳和真实“正在检查本机 Agent”阶段；不再让
   用户面对数秒静止的居中标记。首个稳定壳目标不高于 1.2 秒。
5. 扫描结果只在完成后一次进入真实主页；启动期间不展示上次缓存的 Agent 名称、不先渲染
   空 Agent 列表、不提前启动首次引导。
6. 删除主页硬编码 `TS`，复用现有无文字 Token Station 站标，固定在 42px 槽内光学居中；
   功能名称继续使用“全局路由 / Global routing”。
7. 官方 Provider Avatar 只保留品牌自身形状和底色，外围布局槽透明；自定义 Provider 的
   首字母 fallback 继续有中性底板与边界。

## 3. 非目标

- 不跳过每进程启动扫描，不把上一进程 snapshot 当成本次发现结果。
- 不建立只依赖 mtime/size 的跨进程 hash cache；它可被同尺寸同时间戳替换绕过。
- 不删除或弱化 plan/apply 内路径、版本、配置指纹、目录和 runtime generation 安全复核。
- 不把 setup 的 SQLite backfill 后移；需要单独评估与运行中 metrics 写入的锁竞争。
- 不增加虚假百分比、伪造 Agent 数量或轮播营销文案。
- 不修改 Provider `brand_id` 数据契约，不按用户可编辑的 Provider 名称猜品牌。
- 不把所有“全局路由”文案改名为“默认路由”，不修改平台原生 App 图标资产。
- 不修改 `crates/router-core/**`、CLI 路由、Gateway、配置版本或发布渠道。

## 4. 安全与数据红线

1. Recovery safe mode 或 Recovery 检查失败时，业务 App 不挂载，`scan_agents` 不调用。
2. `scan_agents` 每进程至多一次展示调用；慢、空、失败必须是三个不同状态。
3. 不同 Agent 可以并发；同一个安装内部继续按原顺序完成候选解析、配置只读预检、版本
   probe 和 binary facts。并发上限固定为 3，避免同时创建过多 probe 与输出 reader 线程。
4. 并行完成顺序不能影响输出；提交前继续按 `agent_id + canonical_path` 稳定排序。
5. hash cache 锁不得覆盖文件 I/O；相同 path、mtime、size 的并发 hash 使用 single-flight。
   文件不可读、锁 poisoning 或 hash 失败继续返回原有 fail-closed/可诊断结果。
6. cache 不写磁盘；mtime 或 size 变化必须重新计算。不能因性能优化接受旧 binary hash。
7. 扫描期间到达的 serve-state 事件保留最新 generation/instance，Ready 时不能被旧 State
   覆盖。
8. 启动 fatal error 持久显示并提供重试，不进入 8 秒 toast；普通运行错误继续使用现有 toast。
9. Provider 官方身份只来自已解析的受控 `brand_id`；自定义端点即使命名为 `deepseek` 或
   `openai` 也只能显示 fallback。

## 5. 启动状态机与交互

```text
Tauri setup
  → Recovery compatibility
    ├─ Safe / failed → RecoveryShell（不启动业务扫描）
    └─ Normal
         → 读取 State ───────────────→ 稳定 App 壳 + 启动阶段
         → Registry + fresh scan ────→ 原子提交 Agent 集合 → Home Ready
                                  └──→ Fatal error + 重试
```

- 最早阶段仍显示“正在检查本地数据兼容性”，因为 Recovery 是硬门禁。
- State 可用后，显示真实顶栏、主页外框和与最终布局同位置的全局路由固定行；Agent 区域只
  显示“正在检查本机 Agent”，右侧显示无百分比的 discovery 轨道和说明。
- 启动状态使用 `role="status"`、`aria-live="polite"` 和 `aria-busy="true"`，不抢焦点。
- 扫描完成后一次 crossfade 为真实主页；`prefers-reduced-motion` 下直接切换，不增加延迟。
- 启动壳中的 Logo、导航、代理和写入动作禁用；主题切换可以继续使用。
- 扫描失败时保留相同壳层，显示明确错误与“重试启动”按钮；不能把失败渲染成 0 Agent。
- 扫描成功但结果为空时正常进入主页空态，首次引导在 Ready 后按完整 State/Agent 判断。

## 6. Discovery 并发设计

`DiscoveryScanner<R>` 的 `ProbeRunner` 增加只读并发所需的 `Sync` 约束。`scan_registry`
使用最多 3 个 scoped worker，通过原子 index 领取 descriptor；每个 worker 只写本地 records，
join 后统一合并并执行现有稳定排序。线程 panic 继续视为内部缺陷，不能静默产生部分扫描结果。

binary hash cache 改为：

1. 短锁检查 `(canonical_path, modified_at_ms, size)` ready entry。
2. 若同 fingerprint 已在计算，Condvar 等待 single-flight 完成后重新检查。
3. 若无人计算，登记 in-flight 后释放锁，读取并 hash 文件。
4. 短锁写入 ready entry、清理 in-flight 并唤醒等待者。

不持锁做 I/O 后，不同 Agent 的大二进制可以真正并行；相同 canonical path 不会重复消耗
CPU。当前 `views`、ownership、compatibility 与前端契约不变。

## 8. 公开测试边界

### 8.1 Rust discovery seam

1. 使用受控 ProbeRunner 证明多个 descriptor 的 probe 会重叠，峰值大于 1 且不超过 3。
2. 即使各 worker 完成顺序不同，records 仍按 `agent_id + canonical_path` 稳定排序。
3. hash single-flight：两个线程请求同 path/fingerprint 时 hasher 只调用一次，且另一路不同
   path 能在第一路 I/O 未完成时进入 hasher，证明全局锁未覆盖 I/O。
4. mtime/size 变化重新计算；缺失 size、hash 错误和 cache poisoning 保持安全结果。
5. 现有完整 fixture tree、真实只读 smoke、timeout/进程组回收和零写入测试继续通过。

### 8.2 React seam

1. pending scan 时先显示稳定 App 壳和 `role=status` 启动阶段；真实主页 Agent、首次引导和
   上次 Agent 名称不可见。
2. scan resolve 后 Home/Agent 一次出现，`scan_agents` 仍恰好一次；期间到达的 serve state
   使用最新值。
3. scan reject 显示持久错误与重试；空数组进入正常空态，两者不能混淆。
4. Recovery safe/error 继续不挂载 App、不调用业务扫描。
5. 全局路由按钮仍是默认首行且可访问名称不变；标记中没有 `TS` 文本，copy 与 icon 是不同
   节点。
6. 官方 Provider 输出已解析 brand identity 且装饰性隐藏；null/未知 brand 输出 fallback，
   自定义同名 Provider 不能冒用品牌。
7. Direct、ProviderList、FreeProviderConfig、AddProvider、Tier 与 Quota 的大小和点击/选择行为
   不因去除外壳改变。
8. reduced-motion 样式取消 discovery 轨道与 crossfade 动画。

## 11. 已知风险与回滚

- 多个 probe 同时运行会提高瞬时 CPU/线程数，因此固定上限为 3，不能直接按 registry 数量
  创建最多 64 个线程。
- 同一 App 的命令行 probe 仍可能有外部副作用；本轮不改变现有 probe 类型，只改变不同 Agent
  之间的时序。真实验收需确认没有意外弹出 GUI。
- App 壳先出现会让启动流程多一个明确状态；必须避免首次引导、写入动作和空 Agent 语义提前
  运行。
- Provider Avatar 来自第三方组件，其内部主题上下文与 Token Station 不同；本轮保留 Avatar
  的自带背景而不依赖其阴影判断，外层完全透明。
- 回滚可整体恢复串行 `scan_registry`、旧 loading 分支和图标容器；不涉及配置迁移或磁盘数据。

## 12. 实现与验收结果

### 12.1 已实现

- `DiscoveryScanner::scan_registry` 使用 3 个 scoped worker 和原子 index 动态领取 descriptor；
  worker 完成后仍执行原有稳定排序。
- binary hash cache 的文件读取已移到锁外；不同 path 可并行，同 path（包括 identity 变化）
  串行 single-flight。RAII owner 在成功、错误与 panic 路径都会清理 in-flight 并唤醒等待者，
  panic 本身继续向上传播。
- `get_state` 返回后先显示稳定 `StartupHome`；Registry 与 fresh scan 成功后才原子发布 Agent。
  扫描失败和空结果保持不同语义，首次引导延后到 Ready，启动壳不播报虚假的 0/0 Agent。
- 新增共享无字 `TokenStationMark`，替换全局路由和 Recovery 的 `TS`；修正误命中图标槽的
  span selector。官方 Provider Avatar 的布局槽透明无边框，未知品牌 fallback 自持中性底板。

- 前端全量：34 files、323 tests passed；生产 `tsc + Vite build` 通过。Vite 只报告既有
  约 1.24 MB chunk 警告。

- 未通过破坏真实配置来制造 scan fatal 或 Recovery safe mode；这两条使用失败注入、边界测试和
  代码级独立审查验收。

### 12.5 已知遗留

- 本轮没有建立跨进程 hash cache，因此每个新进程仍会完整读取并 hash 已发现二进制；这是安全
  红线内的明确取舍。若继续优化，优先单独设计“展示扫描延迟计算单安装 hash”，不能静默改变
  当前 `scan_agents` 完整事实契约。
- Tauri setup 的历史成本回填仍同步执行；本机数据库无待回填项，未进入本轮关键路径。大指标库
  场景需另行评估后台迁移与 SQLite 写锁竞争。
