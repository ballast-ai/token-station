# CC Switch 特殊接口兼容差距：核验、已修与架构决策

- 起草：2026-07-30（首版方向为 fail-closed）
- 改向重写：2026-07-31
- 关联审计：《Token Station 与 CC-Switch 3.19 特殊接口兼容差距修改建议》（测试版协议审计）
- 参考实现：`farion1231/cc-switch`（`src-tauri/src/proxy/providers/transform_codex_chat.rs` 等，逐函数核对过契约）
- 本轮状态：已在本地 `develop` 完成 Codex 工具**翻译 + 双向还原闭环**（custom / namespace，含流式），逐项真实 wasm 测试。**未 commit、未推送。**

## 0. 方向（较首版有变，已拍板）

首版（07-30）把入站边界一律改成 **fail-closed**：把无法用 Canonical function 表达的工具（custom / namespace / hosted）直接返回 capability 400。它诚实，但**让携带这些工具的 Codex 请求整条不可用**。

07-31 拍板改向：**对齐 CC Switch，把这些工具翻译成 function，让 Codex 真正能用**，而不是拒绝。核心原则未变——不自建搜索/沙箱、不把不支持假装成支持——但把「不支持」的范围收窄到确实无法翻译的少数（见 §2），其余全部走「翻译进 + 还原出」的**对称闭环**。

关键约束（决定了实现形态）：

- **normalize 与 render 是分离的无状态 WASM 调用**。CC Switch 是 proxy，请求与响应同作用域，能随手从请求 tools 重建还原图；我们不能。故由 host（`apps/cli/src/gateway.rs`）把调用方**原始 tools 原样**透传进 render 上下文（`render_context.inbound_tools`），插件在 render 时据此重建还原图。**只往一个既有的 JSON 上下文加字段，不改 WIT/ABI。**
- **名字不能靠 `__` 盲拆**：custom / local_shell / 真 function 无法从函数名反推，真 function 名也可能含 `__`。所以还原必须靠请求侧传来的类型信息，纯 stateless 不可行。

## 1. 已修 + 已测（Codex 工具翻译闭环）

### S0 · host 透传原始 tools 进 render 上下文
- `apps/cli/src/gateway.rs`：`normalize_request` 额外返回调用方原始 `body.tools`，沿 `dispatch → try_upstream → translate_{stream,nonstream}_response` 透传，落进 `render_context.inbound_tools`。gateway 只做透明搬运，**不含任何 Codex 语义**。纯加字段，不破 ABI。

### S1 · custom（freeform）工具全闭环
- **请求·工具定义**：`tools_of` 把 `type=="custom"` 翻译成一个**固定 schema** 的 function——`{ properties: { input: string }, required: [input] }`（与 CC Switch `CUSTOM_TOOL_INPUT_FIELD` 一致），原始 description 透传。这样模型总是产出一个可回收的 `input` 串。
- **响应·还原**：`restore_tool_call_item` 把「名字命中 custom 工具」的 `function_call` 还原成 `custom_tool_call { id: ctc_*, call_id, name, input }`，`input` 从 `{ "input": … }` 参数中解包。
- **请求·历史回填**：`normalize_inbound` 接受此前会被拒的 `custom_tool_call` / `custom_tool_call_output` 历史 item（前者还原成带 `{ input }` 参数的 assistant 工具调用，后者成 tool 结果消息）。
- **测试**：`responses_custom_tool_round_trips`。

### S3 · namespace 工具全闭环
- **请求**：`tools_of` 把 `namespace` 子工具展平成 `<namespace>__<child>`（碰撞硬失败，从不静默覆盖）——首版已具备。
- **响应·还原**：`restore_tool_call_item` 把扁平名还原成带 `name=<child>` + `namespace=<ns>` 字段的 `function_call`，Codex 据此匹配自己的命名空间注册表。
- **请求·历史回填**：`function_call_item` 把携带 `namespace` 字段的重放调用重新展平回 `<ns>__<child>`。
- **`tool_choice`**：`namespace` 类型的 tool_choice 已被既有逻辑统一降级为 auto（无需额外改）。
- **测试**：`responses_namespace_tool_round_trips`。

### S4 · 流式还原
- `StreamState` 携带一次性构建的还原图；`render_stream_event` 的 `output_item.added`、参数增量、`stream_done` 三处都按还原图输出：
  - custom：以 `custom_tool_call` item 宣告（`ctc_` id），参数**不**走 `function_call_arguments.delta`，而是在 `stream_done` 缓冲解包后统一发 `custom_tool_call_input.delta`/`.done`（对齐 CC Switch——`{ input }` 的 JSON 增量无法逐片解包）。
  - namespace：仍走 `function_call` 事件族，item 带还原后的 `name` + `namespace`。
  - 普通 function：完全不变（空还原图 = 旧行为，既有流式测试全绿即证）。
- **测试**：`responses_stream_restores_custom_and_namespace_tool_calls`。

### （首版已并入）Anthropic 厂商工具翻译
- `agent-anthropic::parse_tools` 把厂商 server 工具（web_search…）与 client-schema 工具（bash/text_editor…）翻译成 Canonical function tool（对齐 CC Switch），而非拒绝；用户工具仍保留严格 `input_schema` 校验。测试 `anthropic_vendor_tools_are_translated_to_function_tools`。
- 其余首版项未变：`anthropic-beta`/`openai-beta` 头值进 HeaderDigest 白名单（S0 基础，成组转发上游仍待 host carrier）；Anthropic `output_config.effort → reasoning_effort`（`max→high`，因本 provider 是通用 OpenAI-compatible，不吃 xAI 的 `xhigh`）；Gemini hosted 工具仍命名化 capability（见 §2）。

## 2. 有意为之的限制（诚实降级，非假成功）

- **`local_shell` 走普通 function，不发明 `local_shell_call` 还原**。核验：整个 cc-switch 仓库**不处理** `local_shell`——Codex 走第三方 Chat Completions 时，编辑路径用的是 `type=custom`（apply_patch）与 `shell_command`，`local_shell` 是 OpenAI 原生模型专用。我们今天的 custom 闭环恰好覆盖了真实路径。硬造一个 CC Switch 都没定义的 `local_shell_call.action` 重建 = 猜测契约 = 正是要避免的难查 bug。故 `local_shell` 保持为普通 function（诚实降级），不做还原。
- **Gemini hosted 工具**（google_search/url_context/code_execution）仍返回命名化 capability 错误：它们是真·服务端工具，翻译成 function 也无从执行，与 Codex 的 custom（客户端执行）不同。

### S5 · tool_search 与 custom description 元数据（已补齐）
- **tool_search**：`tools_of` 把 `tool_search` 翻译成带 `query`/`limit` schema 的 proxy function；`restore_tool_call_item` 还原成 `tool_search_call { call_id, status, execution: "client", arguments: <对象> }`（客户端执行，无 id/name）；历史 `tool_search_call` / `tool_search_output` 一并接受。测试 `responses_tool_search_round_trips`。流式同族（`function_call_arguments`）复用 S4 路径。
- **custom description 元数据**：custom 工具的原始定义整体嵌进 flatten 后 function 的 description（`Original tool definition:` + JSON code block，对齐 CC Switch `responses_custom_tool_description`），使 Lark grammar / `format` 等无 schema 槽的信息不丢。测试断言已加。
- 注：`tool_search` 返回的动态工具目录再注册（CC Switch `collect_tool_search_output_tools`，会话中途按搜索结果扩充可用工具）未做，属更深的动态注册特性。

## 3. 仍需老板拍板的架构级改造

以下需新 ABI/IR 版本、host 层改动或触及主链，审计与项目自订 IR 变更请求都要求「先评审再发版」：

| 审计项 | 为何需评审 |
| --- | --- |
| Canonical IR v2：工具类型 + 执行方建模 | `ToolDef` 只有 name/desc/params，表达 kind/执行方需破坏闭合枚举、发新 IR/ABI |
| Claude Code 上游错误原样转发 | provider 归一化改写破坏 Claude Code 自愈；需 host 分「客户端可见」与「内部 code」两路且只对 Anthropic route |
| `anthropic-beta` 成组转发上游 | S0 已让值可达 adapter；成组转发需 host opaque carrier |
| `/v1/responses/compact` 子协议 | 需注册多条 compact 路径 + 原生透传/跨协议拒绝/日志脱敏三态 |
| `previous_response_id` 状态链 | 原生 stateful 应透传；跨协议需历史存储 + 完整重放 |
| **reasoning 全链**（响应侧 `reasoning_summary_*` 流式 SSE 家族 + 请求侧 reasoning_content 占位符回填 + provider 侧推理提取） | 这是与工具正交的独立大特性：Canonical IR 在 0.3.0 **有意暂缓** Responses reasoning 渲染（`ThinkingDelta` 目前不渲染），CC Switch 里 reasoning 是横跨 provider 提取 / 有状态流式 / 请求回填的 287+ 处逻辑，且映射到我们不同的 plugin（provider vs responses agent）。故**不并入本轮工具闭环**，需单独立项 + 定 opaque/signed thinking 的保存期限、日志红线、provider 切换语义 |
| usage hosted-tool 计量 | `Usage` 只有 token 桶；server-tool 次数/费用需独立计量项 |
| `/v1/models` 的 Claude discovery 投影 | 需 connector 层专门 alias 投影，不改全局语义 |

`previous_response_id`、Responses 结构化输出等目前的 hard-reject 本身是安全且诚实的，未动。
