# OpenCode 模型契约前置修复设计

- 日期：2026-08-13
- 状态：已完成
- 范围：Desktop Provider 模型能力、Agent 扫描视图、OpenCode 接入准入、错误提示与诊断
- 不涉及：DMG、远端发布、供应商价格推断、修改 OpenCode 自身实现

## 1. 问题与第一性原理

OpenCode 通过一个静态的 `tokenstation/auto` 模型访问 Token Station。为了让 OpenCode
正确计算可用输入预算和自动压缩，Token Station 必须在写入 OpenCode 配置前证明当前路由
的每一个可达模型都具有非零 `context_window` 和 `max_output_tokens`，且输出上限不大于
上下文上限。

当前后端已经在 `plan_agent_connection` 阶段失败闭合，但 Agent 页面仍把安装显示为
“可接入”，用户点击后只看到泛化 Toast。Provider 页面虽然读取模型限制，却没有展示或
编辑入口。结果是安全校验存在，但发生得太晚，而且用户没有应用内修复路径。

本设计采用以下不变量：

1. **不可证明即不可点击**：OpenCode 的“一键接入”只有在当前运行路由模型契约完整时启用。
2. **不猜测供应商限制**：缺失的 `max_output_tokens` 不能由上下文比例或通用默认值伪造。
3. **一个事实源**：扫描视图、接入计划和 Connector 使用同一模型契约结果，不能各自判断。
4. **用户可修复**：缺失限制必须在 Provider 页面可见并可显式填写。
5. **后端二次复核**：前端禁用不能替代计划阶段的 TOCTOU 安全检查。

## 2. 目标、范围与非目标

### 2.1 目标

1. 当前路由缺少模型限制时，OpenCode 页面显示具体的“路由待完善”状态，并禁用接入。
2. Provider 页面展示每个已管理模型的上下文和最大输出限制，允许用户显式保存合法值。
3. 计划阶段返回稳定、结构化的模型契约错误码，前端提供中英文可操作提示。
4. 模型限制保存失败时不留下半写状态；运行中的代理明确提示重启后生效。
5. Direct、智能分档、额度优先继续按实际可达目标计算契约，不能只检查当前 UI 选中项。

### 2.2 非目标

- 不为未知模型自动生成或猜测 `max_output_tokens`。
- 不把 Provider 模型能力缺失升级为整个 App 的启动失败。
- 不自动重启正在服务的代理，不静默改变当前路由或上游请求行为。
- 不在本次重做完整 Provider 模型目录或价格来源系统。

## 3. 安全与数据红线

1. API Key、虚拟 Key、请求/响应正文和未脱敏配置不得进入错误提示、Agent 视图或诊断日志。
2. 模型限制保存必须验证 `context_window > 0`、`max_output_tokens > 0`、
   `max_output_tokens <= context_window`，并使用现有配置 revision/原子保存机制。
3. 目录刷新只填充缺失值，不覆盖用户已经声明的非零限制；本次不改变该规则。
4. 接入计划继续绑定安装路径、版本、运行实例、配置指纹和确认令牌。
5. 既有已接入配置不自动删除；运行态契约不足时展示需修复状态。
6. 不读取、修改或清理历史 Agent 备份文件作为本修复的隐式副作用。

## 4. 模块与接口设计

### 4.1 模型契约结果

现有 `virtual_model_contract*` 继续作为深模块入口，但错误从自由文本收口为内部结构化问题：

```rust
enum ModelContractIssue {
    ExactModelRoutingUnsupported,
    NoReachableModel { agent_id: String },
    UnknownProvider { upstream: String },
    UnknownModel { target: String },
    MissingContextWindow { target: String },
    MissingMaxOutputTokens { target: String },
}
```

每个问题提供稳定 `code()` 和脱敏 `message()`。同一个问题同时用于：

- 运行时 Agent 扫描视图中的 `connection_issue`；
- `plan_agent_connection` 的失败闭合；
- 运行实例指纹，确保能力状态变化使旧计划失效。

### 4.2 Agent 安装视图

`AgentInstallationView` 增加可选字段：

```text
connection_issue: { code, message } | null
```

只有运行时能够计算出的 Connector 接入前置问题进入该字段。Discovery/版本兼容状态不被
篡改，避免把“安装兼容”与“当前路由可接入”混成同一概念。

### 4.3 Provider 模型限制保存

新增 Desktop command：

```text
set_provider_model_limits(name, model, context_window, max_output_tokens) -> StateView
```

该接口只允许修改已经存在的 Provider 和已管理模型。保存复用 `ensure_editable`、
`observe_draft` 和 `save_draft`；失败时恢复原模型数组和配置状态。

## 5. 用户可见交互与失败处理

### 5.1 Agent 页面

当 OpenCode 当前路由缺少 `max_output_tokens`：

- 状态标签：`路由待完善` / `Route incomplete`；
- 说明包含具体的 `供应商/模型`，不包含本地路径；
- “一键接入”禁用；
- 用户完善限制并重启代理后，缓存/启动扫描重新计算状态并恢复接入按钮。

计划阶段仍可能因并发配置变化失败，此时 Toast 使用同一稳定错误码显示具体原因，而不是
“操作未能完成”。

### 5.2 Provider 页面

每个模型行显示两个数字输入：上下文上限和最大输出 Token。用户点击该行的“保存限制”后：

- 合法值保存，并提示代理运行中时需要重启才能进入服务版本；
- 缺失、非整数、非正数或输出大于上下文时就地提示，Toast 不替代字段错误；
- 保存期间该行和 Provider 其他变更操作禁用，避免并发覆盖。

### 5.3 响应式、键盘和可访问性

- 数字输入具有关联 `label`，保存按钮可通过 Tab 到达并支持 Enter/Space。
- 窄窗口允许模型限制编辑区换行，不能产生水平滚动。
- Agent 阻断原因是持久文本，不依赖 hover 或 8 秒 Toast。
- 保存中通过按钮文本和 disabled 状态表达，不移动焦点。

## 6. 公开测试 seam 与验收标准

### 6.1 后端公开行为

1. 当前可达模型缺少最大输出限制时，扫描视图返回稳定的
   `model_contract_missing_max_output_tokens`，计划返回同一错误码。
2. 模型限制保存拒绝零值、输出大于上下文、未知 Provider 和未知模型，且配置不变。
3. 合法保存持久化两个限制并保留模型其他能力字段。
4. 多目标路由中任一可达模型缺失限制即阻断；不可达孤儿模型不阻断。

### 6.2 前端公开行为

1. 带 `connection_issue` 的 OpenCode 显示“路由待完善”，按钮不可用且原因可见。
2. Provider 模型行可编辑并保存两个限制；非法值在字段附近显示。
3. 结构化模型契约错误在中英文模式下均得到具体操作建议。

### 6.3 真实 App 检查

1. 使用本机已有缺少 `max_output_tokens` 的 Kimi 路由，确认 OpenCode 不再显示“可接入”。
2. 在 Provider 页面补全经用户确认的限制，确认保存反馈和重启提示。
3. 重启代理后确认 OpenCode 变为可接入；执行接入后检查
   `~/.config/opencode/opencode.json` 只新增 `provider.tokenstation`，不展示或记录 Key。
4. 确认 1040×720 窗口下输入可见、可键盘操作、无水平溢出。

### 6.4 对抗性回归边界

1. 运行中代理即使因本地鉴权或适配器问题无法组装完整连接运行时，
   OpenCode 模型契约仍必须从 serving config 计算，不得回退到 saved config。
2. 结构化问题必须显式携带稳定 `code` 和可选 `target`；前端不得用中文展示文案
   正则恢复语义，运行时指纹不得因文案改写而变化。
3. 版本不兼容、预检失败等安装级阻断优先于路由完整性，避免用户串行修复。
4. Provider 限制编辑只对已配置模型开放；行级缺失提示只陈述“元数据不完整”，
   不得在没有路由可达性证据时声称 OpenCode 整体不可用。
5. readiness 必须在一次全局锁内投影：Running/Applying 绑定实际 serving 实例，
   Stopped/Failed 绑定下次启动会保存并服务的 current draft；Starting/Stopping 不推测中间态，
   显式失败闭合为“代理切换中”。
