# 模型限制内置预设回退设计

- 日期：2026-08-13
- 状态：已完成
- 范围：Desktop Provider 模型目录解析、模型限制来源、Kimi 官方端点精确预设、Provider 可见提示
- 不涉及：DMG、远端发布、价格同步、模糊模型名推断、任意第三方中转站预设

## 1. 问题与第一性原理

OpenCode 的静态 `tokenstation/auto` 模型必须得到非零的上下文上限与最大输出上限，
否则无法证明可用输入预算。供应商的 `/v1/models` 是首选事实源，但 OpenAI-compatible
只约定模型列表的基本形状，并不保证暴露两个限制；Kimi 当前文档只在模型对象中公开
`context_length`，不公开最大输出上限，账号还可能无权访问模型目录。

因此“从模型获取全部限制”这个前提不成立。正确的数据优先级是：

1. 用户明确保存的值；
2. 供应商实时返回的字段；
3. 官方端点 + 精确模型 ID 命中的内置预设；
4. 未知，继续失败闭合。

CC-Switch 在 OpenCode Provider 预设中采用精确模型 ID 的静态 metadata，并只在运行时
目录缺失字段时作为 fallback。参考固定在上游提交
`1f38c83826a8bca3c1a7a18d9629f05a914718fd`：

- `kimi-k2.6`：context `262144`，output `262144`；
- `kimi-k3`：context `1048576`，output `131072`。

Token Station 复用这种“精确预设兜底”机制，但增加端点约束与持久化来源，避免把社区
预设伪装成供应商实时事实。

## 2. 目标、范围与非目标

### 2.1 目标

1. 解析 Kimi `/v1/models` 的 `context_length`，实时字段优先于预设。
2. 对 Kimi 官方端点上的精确 `kimi-k2.6`、`kimi-k3`，在目录无权访问或缺字段时自动补全限制。
3. Provider 页面明确显示“供应商接口 / 内置预设 / 手动配置”等来源。
4. 用户手动保存后标记为手动配置，后续刷新不得用预设覆盖。
5. 迁移 Token Station 旧版本自动写入的 `128000 + 缺少 output` 组合，使现有用户无需手输。

### 2.2 非目标

- 不按 `kimi` 子串、上下文比例或模型家族猜测未知模型。
- 不对 OpenRouter、自建网关等非 Kimi 官方端点套用 Kimi 预设。
- 不声称 CC-Switch 预设等同于 Kimi 官方实时返回值。
- 不为没有精确预设的模型放宽 OpenCode 接入校验。
- 不静默覆盖已标记为手动配置的限制。

## 3. 安全与数据红线

1. 预设匹配必须同时满足规范化官方 Base URL 与精确模型 ID；不得前缀、后缀或模糊匹配。
2. 任何来源的 `max_output_tokens` 必须大于零且不超过 `context_window`。
3. API Key、请求正文、配置路径不得进入来源提示、错误信息或缓存。
4. 目录 401/403 仍保留原始警告；应用预设不能把鉴权失败显示成实时同步成功。
5. 实时返回只接受正整数 `u32`；溢出、零值和输出大于上下文的组合保持未知。
6. 旧配置迁移只识别本产品历史自动默认的精确形状；其他非零值按用户所有处理。

## 4. 状态与数据设计

### 4.1 限制来源

模型配置通过 `ModelCapability.extensions` 持久化两个来源字段：

```text
x-token-station-context-window-source
x-token-station-max-output-tokens-source
```

允许值：`provider`、`builtin_preset`、`operator`、`heuristic`。旧配置没有来源时，只有满足
`context_window == known_context_window(model)` 且 output 缺失的精确预设模型，才视为可迁移
的历史启发式值。

### 4.2 合并规则

- 实时目录有合法字段：填充未知值；若当前字段来源是 `builtin_preset` 或 `heuristic`，允许升级为
  `provider`；不得覆盖 `operator`。
- 实时目录缺字段或请求失败：使用精确内置预设填充未知值；历史启发式 context 可成对升级为预设。
- 手动保存两个限制：两个来源都改为 `operator`。
- 新增精确预设模型：直接写入完整预设与来源；其他模型保留现有 context 启发式且 output 未知。

## 5. 用户可见交互与失败处理

1. Provider 模型行在两个限制输入附近显示来源：
   `供应商接口`、`内置预设`、`手动配置`、`启发式默认`或`未知`。
2. 目录 401/403 且成功应用预设时，刷新状态显示“使用内置预设”，同时保留“无权读取目录”警告。
3. 内置预设不是只读值；用户可核实后修改，保存即切换为“手动配置”。
4. 未命中预设的模型继续显示缺失警告，不自动填任意数字。

## 6. 响应式、键盘与可访问性

- 来源文字与对应限制编辑器处于同一模型行，窄窗口可换行且不产生水平滚动。
- 来源不是仅靠颜色表达，必须有可读文本。
- 原有数字输入 label、Tab 顺序、Enter/Space 保存行为保持不变。
- 刷新成功降级为预设时通过持久状态文字和 warning 表达，不只依赖 Toast。

## 7. 公开测试边界与验收标准

### 7.1 目录解析 seam

1. `context_length` 被解析为 context；合法实时 output 仍优先。
2. 零、溢出与 output 大于 context 的值不进入目录事实。

### 7.2 Provider 配置 seam

1. Kimi 官方端点精确模型在目录失败时自动得到 CC-Switch 对应预设和来源。
2. 非官方端点、相似模型名、未知模型不应用预设。
3. 旧 `128000 + output 缺失` 精确迁移；其他非零手动值不覆盖。
4. 用户保存后来源变为 `operator`；后续预设/实时刷新不覆盖手动值。
5. 实时字段可升级已有预设字段，并把对应来源改为 `provider`。

### 7.3 前端 seam

1. 模型行展示限制来源；预设值不再显示“缺少最大输出上限”。
2. 目录失败但应用预设时显示“使用内置预设”，原始鉴权警告仍可见。
3. 用户保存后页面更新为“手动配置”。

### 7.4 真实 App 检查

1. 本机 Kimi Provider 的 `kimi-k2.6` 与 `kimi-k3` 自动出现完整限制与“内置预设”。
2. `kimi-k3` 路由不再因缺少 output 而显示“路由待完善”；`kimi-k2.6` 因社区预设
   `output == context` 无法证明正输入预算，OpenCode 必须继续显示阻断。
3. 1040×720 下来源、输入和保存按钮无水平溢出，键盘可达。
4. 不修改 OpenCode 配置，不暴露任何 Key。
