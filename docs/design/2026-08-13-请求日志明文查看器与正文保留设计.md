# 请求日志明文查看器与正文保留设计

> 日期：2026-08-13
> 状态：已实现并完成本地 App 验收
> 范围：Desktop 请求日志详情、独立正文文件存储、过期正文清理脚本

## 1. 问题、目标、范围和非目标

### 1.1 问题

现有 Request Receipt 只保存路由、终态、用量和转换元数据。用户展开请求日志后只能看见
Decision / Attempts / Conversions，无法核对发给 Token Station 的请求正文和 Token Station
返回给调用方的响应正文。

这不是单纯的前端缺口：`metrics.sqlite` 与 `requests.log` 按原设计不含正文，历史记录无法反推
明文输入输出。用户已明确选择让后续正文持久化到独立文件夹，并通过保留策略定期清理。

### 1.2 目标

- 在单条请求日志的 Decision / Attempts / Conversions 下方增加“明文输入 / 明文输出”内嵌查看器。
- 请求与响应区域拥有固定最大高度和独立的纵向、横向滚动能力，长 JSON、SSE 和代码不会撑开页面。
- JSON 正文以缩进格式显示；无法解析为完整 JSON 的 SSE 或文本保持原样。
- 正文不进入数据库或现有 JSONL 请求日志，按 `request_id` 写入 Desktop 私有数据目录下的独立文件夹。
- 提供默认保留 7 天、可覆盖保留天数的清理脚本；代理准备启动时也执行一次同口径清理。
- 对超出上限的正文明确显示截断状态，不伪装为完整内容。

### 1.3 范围

- 捕获 Desktop 代理接收到的原始请求 body，以及返回给调用方的 JSON body / 流式 chunk。
- 使用 `request_id` 将正文文件与持久化 Receipt 关联。
- 请求日志分页读取时，仅为当前页按 request id 读取仍存在的正文文件。
- 正文目录同时受 7 天保留期与约 1,000 个请求文件约束；每 64 次写入维护一次，达到上限时优先
  删除最旧文件，因此连续写入时最多短暂超出 63 个文件。

### 1.4 非目标

- 不恢复本功能发布前已产生的历史正文。
- 不把正文写入 SQLite、`requests.log*`、配置、系统日志或浏览器持久化存储。
- 不捕获请求/响应 header、Authorization、Provider Key 或 Token Station virtual key。
- 不提供搜索、编辑、复制按钮或导出。
- 不改变 Provider 实际收到的转换后请求，也不展示内部 Provider 原始响应。
- 不替用户安装 cron / launchd 定时任务；脚本可由用户现有调度器调用，代理启动仍会兜底清理。

## 2. 安全与数据红线

1. `RequestRecord`、`ReceiptView`、SQLite schema 和 `FileLog` 继续保持无正文；不得增加通用 JSON、
   prompt、response、header 或 key 字段。
2. 正文只写入 `<data_dir>/request-bodies/req_<32 hex>.json`。目录权限为 `0700`，文件权限为
   `0600`；文件名只接受 Gateway 生成的固定 request id，不接受路径分隔符或任意调用方文本。
3. 每个输入和输出各最多保留 256 KiB，超出部分按 UTF-8 安全边界截断并标记。目录最多保留
   1,000 个请求文件（维护间隔内最多 1,063 个），因此理论正文上界约为 532 MiB，加 JSON 结构开销。
4. 写入使用同目录临时文件加原子 rename，失败只能丢失调试正文，不得改变请求成功、失败、取消、
   超时或 fallback 语义；正文内容不得进入错误日志。
5. Tauri IPC 只能按已存在的 Receipt 页读取对应文件，不新增目录枚举、任意路径或任意文件读取接口。
6. 输入 body 可能包含用户主动提交的敏感内容。界面必须说明默认保留 7 天；不自动复制，不写入
   前端缓存。
7. 清理只允许删除正文目录内、文件名满足 `req_<32 hex>.json` 的普通文件；禁止跟随符号链接，
   禁止递归删除，禁止把空变量、Home 或数据根目录作为删除目标。

## 3. 数据格式与清理口径

单文件使用固定结构，不接受任意顶层扩展：

```json
{
  "request_id": "req_...",
  "captured_at_ms": 1786610000000,
  "input": "{...}",
  "output": "data: {...}\n\n",
  "input_truncated": false,
  "output_truncated": false
}
```

- 默认过期线：文件 `captured_at_ms` / 修改时间早于当前时间 7 天。
- `scripts/cleanup-request-bodies.sh` 接受 `--data-dir <dir>` 与 `--days <正整数>`；未提供数据目录时
  使用 Desktop 默认数据目录，未提供天数时为 7。
- 代理准备启动时使用相同的 7 天与 1,000 文件上限清理；清理失败会报告启动阶段错误，避免用户
  误以为保留策略生效。单个已消失文件按并发清理处理，不视为失败。
- 手工脚本打印扫描数、删除数和实际目录，不打印正文或 request id 列表。

## 4. 用户可见交互、状态和失败处理

展开请求日志行后，现有三段轨迹下方显示：

```text
┌ 明文输入输出 ─────────────────────── 默认保留 7 天 ┐
│ INPUT                         │ OUTPUT              │
│ ┌ 独立纵/横向滚动区域 ─────┐ │ ┌ 独立纵/横向滚动区域 ┐ │
│ │ pretty JSON / raw text    │ │ │ pretty JSON / SSE  │ │
│ └───────────────────────────┘ │ └─────────────────────┘ │
└───────────────────────────────────────────────────────┘
```

- 有正文文件：显示输入和输出；空 body 显示“空正文”。
- 无正文文件：显示“此请求没有可用明文。它可能早于本功能、写入失败或已被保留策略清理。”
- 被截断：对应标题旁显示“已截断”，正文末尾附固定截断标记。
- 正文文件格式损坏或权限错误：该行显示“明文读取失败”，但 Receipt 列表和其他行继续可用；错误不
  包含正文。
- Receipt 本身读取失败仍沿用现有页面错误。

## 5. 响应式、键盘与可访问性

- 宽屏使用等宽双栏，窄于 760px 时改为单栏堆叠，禁止页面横向溢出。
- 每个正文 `<pre>` 设置 `tabIndex=0`，键盘用户可聚焦后使用方向键、Page Up/Down 滚动。
- 聚焦态使用现有 signal 色轮廓，不能只依靠背景色变化。
- `aria-label` 分别命名为“明文输入”和“明文输出”；无正文使用 `role=status`，读取失败使用
  `role=alert`。
- 使用 IBM Plex Mono / 系统等宽字体展示数据，保留换行，不启用动画。

## 7. 实现落点、遗留项和发布要求

### 7.1 实现落点

- `apps/cli/src/bodylog.rs`：固定正文文件结构、私有目录、原子写入、读取与清理。
- `apps/cli/src/gateway.rs`：输出 emitter 包装与按 request id 写入正文文件。

- `scripts/cleanup-request-bodies.sh`：显式路径校验后的保留期清理入口。

### 7.2 已知遗留项

- 正文文件是本机调试日志，不是加密审计库；拥有当前 macOS 用户权限的进程可读取。
- 流式输出展示调用方实际收到的 SSE/JSONL 原文，不在本期重建为单一 assistant message。
- 当前设计不提供 UI 内的保留天数设置或“立即清理”按钮；清理脚本参数与代理启动默认值均为 7 天。
- 未自动创建 cron / launchd 调度。若需要严格按固定时刻清理，后续应设计用户可见的调度开关，
  而不是安装过程静默写系统任务。

### 7.3 发布要求

该改动影响 Desktop 可执行行为与界面，交付前必须执行 `scripts/install-local-desktop.sh`，完成真实
App 检查，并回写本文状态、测试结果、App 验收结果和遗留项。随后使用规定 Git 身份和中文提交说明
创建本地 commit。

## 9. 轨迹区紧凑化与转换语义优化（2026-08-13）

### 9.1 问题与目标

真实 App 验收后发现，Decision、Attempts、Conversions 使用三个等宽列，整行高度被包含四条记录的
Conversions 撑高，前两列下方出现大块无信息留白。同时，`inbound_normalize`、
`provider_request` 等内部阶段名直接作为主标题，用户无法快速判断每一步的业务含义。

本次调整目标：

- 第一行只放 Decision 与 Attempts，两列按内容自然高度排布。
- Conversions 独占下一行，并以从左到右的四步流程展示，利用原留白区域并降低整体高度。
- 转换步骤以用户动作作为主标题，内部阶段名和协议映射保留为次级诊断信息。
- 不修改 Receipt 数据结构、正文存储、路由或转换行为。

### 9.2 用户可见语义

四个已知阶段显示为：

1. `inbound_normalize`：收到调用方请求。
2. `provider_request`：转为供应商格式。
3. `provider_response`：解析供应商响应。
4. `outbound_render`：返回调用方格式。

未知阶段不猜测含义，主标题直接显示原始阶段名。每一步仍显示 `source_protocol → target_protocol`、
内部阶段名和成功、失败或取消状态，避免为了易读损失诊断信息。

### 9.3 响应式、可访问性与失败处理

- 宽屏时 Decision / Attempts 为两列，Conversions 为全宽横向流程；窄于 900px 时转换步骤改为两列，
  窄于 620px 时全部改为单列。
- Conversions 使用有序列表语义；每一步的可访问名称包含用户动作，状态不只依赖颜色。
- 缺少 Decision、Attempts 或 Conversions 时继续显示原有明确空态，不制造占位步骤。
- 已有诊断错误块继续位于轨迹区顶部并跨越全宽。

## 10. 语义解析视图与原文切换（2026-08-14）

### 10.1 问题与目标

正文文件保存的是调用方协议原文。即使 JSON 已缩进，用户仍需理解 `messages`、`content_block_delta`、
`choices[].delta` 等协议字段后才能找到真正的系统提示词、用户输入和模型输出。用户需要的是按业务语义
提取后的内容视图，而不是单纯的 JSON 美化；同时仍需保留原文用于逐字核对。

目标：

- 明文查看器默认显示“解析视图”。输入按消息顺序提取系统提示词、开发者提示词、用户输入、历史助手
  消息、工具返回，并单独概括工具定义；输出将流式增量合并为助手思考、助手输出和工具调用参数。
- 同时兼容当前主要协议形态：Anthropic Messages、OpenAI Chat Completions / Responses，以及它们的
  SSE 增量。未知但合法的 JSON 不猜测业务含义，显示“未识别结构”并提供格式化内容。
- 标题栏提供“解析视图 / 原文”切换，同时控制输入与输出面板；原文模式必须逐字显示正文文件中的
  `input` 与 `output` 字符串，不做 JSON 格式化或 SSE 重组。
- 切换只影响当前展开记录的前端展示，不修改正文文件、数据库、Receipt 或保留期限。

### 10.2 安全与数据红线

- 解析仅允许 `JSON.parse`、字段读取和字符串拼接，不执行正文中的代码、HTML、链接、指令或事件内容。
- 不新增复制、下载、搜索、上传、外部请求或浏览器持久化。
- 解析失败不能丢弃数据：无法识别的完整 JSON、SSE 事件或普通文本均显示明确的兜底区块；用户始终
  可以切换到原文查看完整内容。
- 继续沿用后端 256 KiB 单项上限，前端不创建正文副本到持久化存储。

### 10.3 交互、响应式与可访问性

- 使用两个原生按钮组成紧凑的单选式控件，当前模式通过 `aria-pressed` 与视觉状态同时表达。
- 控件可使用 Tab 聚焦、Enter 或 Space 切换；焦点轮廓沿用现有 signal 色。
- 宽屏位于“明文输入输出”标题栏右侧；窄屏标题信息和切换控件允许换行，不造成横向溢出。
- 解析视图中的每个语义区块显示中文类型、可选序号或角色，以及保留换行的正文；输入、输出面板继续
  保持各自独立滚动。切换模式后滚动位置可由浏览器自然重置，不承诺跨模式保持。

## 11. 原文视图 JSON 格式化修正（2026-08-14）

### 11.1 问题、目标与范围

完整 JSON 正文当前在“原文”模式按存储字符串直接展示。调用方发送压缩 JSON 时，所有字段挤在单行，
无法利用已有的多行代码区阅读。原文的核心价值是保留字段和值，而不是保留无业务语义的 JSON 空白。

本次仅调整前端展示：输入或输出正文若能作为一个完整 JSON 值解析，则用 2 空格缩进显示；SSE、JSONL、
截断 JSON 和普通文本无法作为完整 JSON 解析，继续逐字展示。正文文件、API 返回、数据库、保留策略和
解析视图均不修改，也不新增复制、下载或持久化能力。

### 11.2 安全、失败处理与交互约束

- 只允许使用 `JSON.parse` 和 `JSON.stringify` 做展示层格式化，不执行正文中的代码、HTML、URL 或指令。
- 格式化失败必须回退到原字符串，不能清理首尾空白、重组 SSE 或丢弃任何字符。
- “解析视图 / 原文”按钮、键盘操作、可访问名称、双面板独立滚动和响应式行为保持不变。
- 空正文继续显示既有空态；格式化不得改变截断标记或正文读取错误处理。
