# 路由策略调研:Claude Code 模型选择机制 + 可借鉴的路由器

> 调研日期:2026-07-14。方法:多信源扇出检索 + 对抗式核查(81 条主张 →
> 核查 25 条 → 22 条确认、3 条被推翻)。本文标注了「已确认 / 存疑 / 被推翻」。
>
> **背景与目的:** token-station 的目标是做一个**与 agent 无关的智能路由
> 代理**,在**不降质**的前提下把每个请求路由到**更便宜的模型**,给企业省
> token/成本,替代只服务 Claude Code 的 cc switch,并覆盖 opencode / openclow
> 等更多 agent。本调研回答:Claude Code 自己是怎么选模型的?我们能抄什么?

---

## 一句话结论

**Claude Code 里没有「看请求内容判难度、再选 Opus/Sonnet/Haiku」的分类器。**
模型选择只有两种机制:①**人 / 配置定的**(别名、`/model`、env 变量、subagent
配置);②**按内部任务类型定的**——一组固定的后台操作被送去 Haiku。所有「自动
切换」都是按**交互模式/状态**切的,**没有一个按难度切**。而「按难度自动路由」
是 Anthropic 自己仓库里**反复被请求、但一直没做**的功能。

> 对我们的意义:**任务类型分法**是被 Anthropic 和头部开源路由器验证过的稳妥
> 起点(照抄即可);**难度分类器**是我们真正的差异化护城河,而这条路唯一的
> 生产级范本是 **RouteLLM**(不是给 coding agent 做的),值得重点借鉴。

## 一、Claude Code 的模型选择机制(已确认)

### 1.1 没有难度分类器

官方文档模型选择严格按优先级:`/model <别名>` → `claude --model` →
`ANTHROPIC_MODEL` → settings 的 `model` 字段。别名:`default / sonnet / opus /
haiku / opusplan / fable / sonnet[1m] / opus[1m]`。全文无「难度分类器」。

**反证(最硬):** Anthropic 自己的 GitHub issue 反复求这个功能但未做——
- #43326:「用户现在必须手动 `/model` 和 `/effort` 适配任务复杂度」,提议**加
  一个轻量分类器评估 prompt**。
- #44976:「按任务类型自动路由模型」。
- #67898:「按任务复杂度自动路由模型」。
- #39551 / #16620:关成 not planned / duplicate。

> **我们要做的,正是 Anthropic 官方都还没做、社区一直在要的空白。**

### 1.2 Haiku 小快模型:按「任务类型」不是按难度

`ANTHROPIC_SMALL_FAST_MODEL`(已废弃)→ `ANTHROPIC_DEFAULT_HAIKU_MODEL`,
官方定义「用于 haiku 或**后台功能**的模型」。后台任务是**固定清单**:
- 对话摘要(`claude --resume` 压缩历史)
- 命令处理(如 `/usage`)
- 其他后台 job / `model: haiku` 的 subagent

**证明是「按任务身份」而非「按难度」:** Bedrock 上没配 Haiku 时,后台任务会
**往上掉到 Sonnet** 跑——难度没变只是换大模型顶上。选择键是「哪个任务」。

### 1.3 唯一的「自动切换」都是按模式/状态,不是难度

| 自动机制 | 触发条件 | 是难度吗 |
|---|---|---|
| `opusplan` | 进/出 **plan 模式**(计划 Opus,执行 Sonnet) | ❌ 模式 |
| 可用性 fallback 链 | 上游过载/报错 | ❌ 可用性 |
| 配额 fallback | 用量到阈值(Opus→Sonnet) | ❌ 配额 |
| Fable-5 安全 fallback | **安全分类器**(网络安全/生物内容) | ❌ 安全 |

`/fast` 快速模式正交:保持 Opus 只是服务端出得更快,**从不降级到小模型**。

### 1.4 Subagent 模型:继承 + 显式覆盖

解析顺序:`CLAUDE_CODE_SUBAGENT_MODEL` env > 单次调用 model 参数 > subagent
frontmatter 的 `model` 字段 > 继承主对话。取值:`haiku|sonnet|opus|fable|<id>|
inherit`。**选哪个 subagent** 由 LLM 按描述做任务类型匹配,但**用哪个模型是
人配的**,不是难度判断。

### 1.5 提取出的系统提示:按任务类型组织,无按模型分

社区提取(Piebald-AI/claude-code-system-prompts、asgeirtj/system_prompts_leaks)
文件名全按**任务**:标题生成器、对话摘要、后台 job agent、后台状态分类器、
workflow 子 agent、worker-fork。README 明说「没有任何文件按 Haiku/Sonnet/Opus
命名」。

⚠️ 唯一叫 classifier 的是**幌子**:`background-agent-state-classifier` 读转录
尾巴输出 `working|blocked|done|failed` **决定要不要通知用户**——不选模型、不判
难度。

> ⚠️ 局限:以上来自官方文档 + 提取的系统**提示**,**不是**对混淆 `cli.js`
> 逐行反编译。能证明的最强表述是「文档与提取的提示里没有难度分类器,且厂商
> 自己把它当未实现功能」,而非「审计了字节码确认没有」。

## 二、别人怎么做(可借鉴)

### 2.1 claude-code-router(最主流开源 CC 路由器)—— 仍是规则

- 按**命名场景**路由:`default / background / think / longContext / webSearch`,
  各映射一个配好的模型。
- `background`=便宜快模型(diff 摘要、commit message);`think`=计划/推理模式;
  `longContext`=**token 数超阈值**触发(默认 ~60000)。
- 引擎是**同步 first-match-wins 策略循环**,返回 `TDecision|undefined`——
  **结构上 await 不了 LLM/embedding**,条件全是 header/body 字符串匹配。
- 有 legacy `CUSTOM_ROUTER_PATH` 后门允许用户塞 async 自定义路由,但出厂引擎
  只做字符串匹配 + token 阈值。

### 2.2 RouteLLM(LMSYS)—— 唯一「学出来」的难度路由器,重点借鉴 ⭐

- **核心:** 训练模型预测「**强模型在这条 query 上赢过弱模型的概率**
  `P(strong wins | query)`」,> 用户设的**成本阈值 α** 就走强模型,否则走弱。
- **一个旋钮 α:** 调它即在「省钱 ↔ 保质」间滑动;α 越高越省。
- **四种实现**(都从偏好数据训练):相似度加权排序、**矩阵分解(官方推荐)**、
  BERT 分类器、Llama-3-8B 因果 LLM 分类器。
- **训练数据:** Chatbot Arena 人类偏好票 + **用 LLM-judge 打标签扩充**。
- **效果:** 最好情况(MT-Bench)**省 85% 成本、保 95% GPT-4 表现**;矩阵分解
  版只对 26% query 调 GPT-4 即达 95%,LLM-judge 扩充后降到 14%。
  ⚠️ MMLU/GSM8K 省得少得多(~45%/~35%),**85% 是最好情况,非通用数字**。

### 2.3 存疑(本轮未拿到可核查证据)

Martian、OpenRouter auto-router、NotDiamond、Unify、cc-switch —— **未下结论**,
后续需专门补查。

## 三、对 token-station 的启示

### ✅ 该抄

1. **任务类型 + 阈值预过滤**(抄 CC / claude-code-router):便宜、确定、本地、
   零 LLM。连 Anthropic 和头部开源路由器都只做到这层。作为**第一层,立刻做**。
   CC 的 Haiku 后台任务清单(摘要/命令处理/标题/commit)可直接白嫖成任务类型表。
2. **胜率预测 + 单一成本旋钮 α**(抄 RouteLLM):把难度层建模成「`P(strong
   wins) > α ?`」二分问题,天然映射到现有 `heuristic.threshold`——**把手工权重
   换成学出来的胜率,阈值换成 α**,架构几乎不用动。
3. **训练方式**:偏好数据 + LLM-judge 扩充标签——即我们的**口径B Oracle**。
   被 ICLR 2025 + 生产系统验证。
4. **便宜分类器**:矩阵分解 / BERT / 小 embedding,热路径延迟可忽略。

### ❌ 该避免

1. **别在热路径上每请求调 LLM-judge 选模型**——铁证:连 Anthropic 都没这么干、
   claude-code-router 刻意保持规则化,就是因为延迟和成本。LLM 只在**离线打标签**
   时用。
2. **别信单一 benchmark 最好数字**(85% 是 MT-Bench 最好情况),自建评测集要
   覆盖真实 coding 分布。
3. **用户显式钉了模型时,分类器不许覆盖。**

### 落到四层架构

```
第1/2层  任务类型 + 长上下文阈值        ← 抄 CC / claude-code-router(先做)
第3层    胜率分类器 P(strong wins) > α   ← 抄 RouteLLM(护城河)
         └─ 训练数据来自离线 Oracle(LLM-judge 扩充)
第4层    兜底
```

**方向判断:** 我们的路线有 ICLR 论文 + 生产系统背书,同时踩在 Anthropic 都没
填的空白上。第一层任务类型可马上照抄;第三层胜率分类器是相对 cc switch /
claude-code-router 的真正差异化——**它们全停在规则,只有 RouteLLM 跨过去,而
RouteLLM 又不是给 coding agent 做的。**
