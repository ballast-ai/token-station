> 调研日期：2026-07-08
> 项目地址：https://github.com/farion1231/cc-switch （官网 ccswitch.io）
> 许可证：MIT，开源

## 一、项目定位

CC Switch 是 Tauri 2 + Rust + React 的桌面应用，核心是为七个 AI 编码工具（Claude Code、Claude Desktop、Codex、Gemini CLI、OpenCode、OpenClaw、Hermes Agent）做**统一配置管理与供应商切换**：用户不再手工编辑各工具的 JSON/TOML 配置，在 GUI 或系统托盘里点一下即可切换供应商。

功能模块：

- 供应商管理（50+ 内置预设、拖放排序、导入导出）
- 本地代理服务（热切换、故障转移、熔断器、健康监测、格式转换）
- MCP / 提示词 / 技能统一面板（跨工具双向同步、Deep Link 导入、GitHub/ZIP 一键装技能）
- 会话管理器与工作区编辑器
- 用量统计仪表板（支出 / 请求数 / token、趋势图、请求日志、自定义模型定价）
- 云同步（用户自备 Dropbox / OneDrive / iCloud / 坚果云 / NAS / WebDAV）

## 二、配置切换机制

- **单一事实源**：`~/.cc-switch/cc-switch.db`（SQLite）存供应商、MCP、提示词、技能等可同步数据；`settings.json` 存设备级偏好；双层存储。
- **切换即写回**：切换供应商时直接改写各工具的原生配置文件（如 Claude 的 `ANTHROPIC_BASE_URL`、Codex 的 `base_url`），临时文件 + rename 原子写入，自动备份最近 10 份。
- Claude Code 支持热切换，其余工具切换后需重启终端；开启代理路由后所有切换即时生效（见 §三）。

## 三、本地代理模式（与本产品重叠的核心区域）

代理是可选模式：开启后 CC Switch 把工具配置里的 API 端点改指到本地 `127.0.0.1:15721`，请求经本地转发。

### 路由粒度：按应用、非按请求

这是与本产品最关键的差异点，据其用户手册（docs/user-manual/zh/4-proxy/4.2-routing.md）确认：

- 路由开关按**应用**维度（Claude 路由 / Codex 路由 / Gemini 路由，可同时开多个）；
- 转发逻辑是「识别请求来源应用 → 查该应用**当前启用的供应商** → 转发」——同一时刻一个应用只有一个活跃供应商；
- **无按模型名 / 按规则的请求级分流**：不存在「同一应用内 claude-* 走 A 上游、gpt-* 走 B 上游」的混合路由，供应商级选择就是其全部粒度。

### 故障转移与熔断（4.3-failover.md）

- 每个应用独立配置**故障转移队列**（备用供应商按优先级排序），主供应商失败按序重试；
- 三态熔断器（关闭 / 开启 / 半开），失败阈值、错误率阈值、恢复等待、半开试探均可配，Claude 有独立宽松默认值（失败阈值 8、恢复等待 90s）；
- 流式首字节超时 / 静默超时 / 非流式超时、最大重试次数分应用可配；
- 供应商卡片显示健康徽章（🟢/🟡/🔴），故障转移事件进请求日志。

### 其他代理能力

- 请求格式转换（跨供应商 API 格式适配）；
- 代理自报延迟增加通常 < 10ms；
- 关闭代理时自动把工具配置恢复到路由前状态。

## 四、用量统计与云同步

- **用量仪表板**：跨供应商聚合支出、请求数、token 用量，趋势图、详细请求日志、自定义模型单价——前提是走本地代理（不走代理的流量不可见，这点与本产品指标库同理）。
- **云同步 = 文件同步**：用户把配置目录指向自己的 Dropbox / WebDAV 等，**无中心化账号体系、无服务端**。同步的是配置数据（SQLite 中可同步部分），不是用量归集——多设备用量汇总视图并非其形态。

## 五、分发与商业模式

- MIT 开源，匿名自由下载：Homebrew cask、MSI/DMG/DEB/RPM/AppImage、Arch AUR；
- 无注册、无账号、无付费点、无平台侧——纯工具，靠社区驱动（11 万+ star 说明该需求的受众规模）。

## 六、与个人模式本地客户端的对比

| 维度 | cc-switch | 个人本地版（[需求文档](../features/个人模式本地客户端需求.md)） |
|------|-----------|------------------------------------------------|
| 产品原点 | 配置切换器（改写各工具配置文件），代理是增强项 | 本地路由数据面（「本地的 OpenRouter」），路由是本体 |
| 路由粒度 | 应用级：一个应用一个活跃供应商 + 故障转移队列 | 请求级：按模型/供应商混合路由，三类上游并存分流 |
| 上游类型 | 任意 OpenAI/Anthropic 兼容端点（含中转站） | BYOK 直连①、本地模型②、平台账户③，隐私分级 L1/L2/L3 |
| 管理面 | GUI + 系统托盘（Tauri 桌面应用） | 命令行唯一本地管理面 + 云端网页管非机密配置 |
| 用量数据 | 本地 SQLite + GUI 仪表板 | 本地指标库默认开启 + 账号制云同步（字段白名单、仅元数据） |
| 云同步 | 文件级配置同步（用户自备网盘），无账号 | 账号制元数据归集，多设备用量在平台网页查看 |
| 对账 | 无 | 命令行对账：平台只读账单 vs 本地指标库 diff |
| 隐私承诺 | 开源即证明，无显式隐私工程 | 闭源信任验收：网络边界可查、离线可用、同步白名单、本地审计输出 |
| 分发 | MIT 开源、匿名下载 | 注册下载、闭源，注册前置漏斗 |
| 商业角色 | 无（纯社区工具） | 获客漏斗 + 平台端点转化触点 + 信任资产 |

### 竞争判断

1. **对人群 1（BYOK 多上游开发者）构成实质竞争**。cc-switch 的「代理 + 故障转移队列 + 用量仪表板」已覆盖这类用户的大部分诉求，且开源、免费、有 GUI、零注册门槛、11 万 star 的社区信任。本产品对这类人的差异化收窄为：请求级混合路由（vs 应用级切换）、多上游统一在一条数据面内并存、对账核验。
2. **对人群 2（本地模型玩家 / 隐私敏感者）的威胁来自「开源 vs 闭源」**。cc-switch 本身不主打 L3 叙事，但隐私敏感用户在「开源的 cc-switch」与「闭源 + 信任验收机制的本产品」之间大概率选前者——这放大了闭源分发口径（需求文档 §五）对人群 2 的获客摩擦，是已知取舍的一个现实注脚。
3. **人群 3（平台转化漏斗）不受影响**。cc-switch 无平台侧、无账号体系，平台账户上游 + 转化路径是本产品独有赛道，也是商业上最重要的一类人群。
4. **形态上的反向参照**：cc-switch 以 GUI 为核心且大获成功，而本产品已拍板「命令行唯一本地管理面、无本地 Web 界面」。两者目标人群画像不同（cc-switch 服务的是「怕编辑配置文件」的广谱用户，本产品人群 1/2 是命令行原生受众），该拍板暂无需因此重开，但若后续发现人群 3 的转化受管理面形态拖累，cc-switch 是「GUI 降低门槛→做大漏斗」的现成证据。

### 跟踪信号（触发重估的条件）

- **代理模式出现按模型 / 按规则路由**（如同一应用内按模型名分流到不同供应商）——重叠面将从「切换级」扩大到「路由级」，本产品对人群 1 的核心差异化被削弱；
- 出现中心化账号 + 多设备用量归集——侵入本产品云同步价值点;
- 出现商业化 / 平台侧动作（托管端点、订阅）——从工具竞品升级为业务竞品。

建议每季度复核其 CHANGELOG 与 release notes（https://github.com/farion1231/cc-switch/releases）。

## 七、技术架构：Rust 与 TypeScript 分工

典型 Tauri 架构且比一般 Tauri 应用更「重后端」：**Rust 承担全部业务逻辑与数据面，TypeScript 只做界面层**。

### Rust 侧（`src-tauri/src/`）——所有有状态、碰系统、碰网络的事

| 职责 | 对应模块 |
|------|---------|
| 七个工具的配置文件适配器（读写各工具原生 JSON/TOML、原子写入、备份恢复） | `claude_desktop_config.rs`、`codex_config.rs`、`gemini_config.rs`、`hermes_config.rs`、`openclaw_config.rs`、`opencode_config.rs`，每工具一个模块 |
| SQLite 单一事实源 | `database/`、`store.rs`、`app_store.rs` |
| **本地代理数据面（最重的部分，约 30 个模块）** | `proxy/`：`server.rs`、`forwarder.rs`、`hyper_client.rs`（基于 hyper 的 HTTP 转发）、`sse.rs`（流式）、`circuit_breaker.rs`、`failover_switch.rs`、`provider_router.rs`、`health.rs`、`model_mapper.rs`、格式转换与响应处理、thinking 参数矫正器、`usage/` 计量 |
| 系统集成 | `tray.rs`（托盘）、`auto_launch.rs`、`deeplink/`、`linux_fix.rs` |
| 对前端暴露的 IPC 命令层（约 30 个命令模块） | `commands/`：provider、proxy、failover、mcp、skill、oauth、s3_sync、订阅余额查询等 |
| 杂项后端能力 | OAuth 流程、S3/WebDAV 同步、模型列表拉取（`model_fetch.rs`）、用量事件（`usage_events.rs`） |

### TypeScript 侧（`src/`）——纯视图层

React 18 组件（`components/`）、hooks、contexts、i18n、图标；`lib/` 主要是对 Tauri IPC 的封装（`api/`）、zod schema 校验（`schemas/`）、TanStack Query 数据层（`query/`）、updater / 剪贴板 / 平台探测等薄工具。**前端不直接碰文件系统和网络**，所有操作经 `invoke` 走 Rust 命令。

### 边界与跟踪提示

- 两侧边界即 Tauri IPC：前端发命令 → Rust 执行 → 返回结果/事件。连模型列表拉取、OAuth、云同步这类「前端也能做」的事都在 Rust 侧——前端是可替换的薄壳。
- `proxy/` 中的 `provider_router.rs` 与 `model_mapper.rs`：从命名看 `model_mapper` 是模型名改写（把请求模型名映射为目标供应商的模型名），配合应用级供应商选择，仍非按模型分流到不同上游——与 §三 判断一致。但这两个文件正是「演进出按模型路由」（§六 跟踪信号）最可能发生的位置，复核 release notes 时可顺带盯这两个模块的变更。
