> 日期：2026-07-17
>
> 状态：M0 调研完成，待评审
>
> 适用基线：token-station `develop` @ `5cc6101`
>
> 参考基线：cc-switch `main` @ `edea624a27d6a94678e0a5c2ddaa674876d9d186`；OpenRouter 官方公开文档（2026-07-17）
>

## 1. 执行结论

1. cc-switch 最新 `main` 已支持 **8 个 Agent**，比任务说明多出 **Grok Build**。A 线目标不能再只按 7 个 Agent 计算；应在 Claude Code、Codex、Gemini CLI、Grok Build、OpenCode、OpenClaw、Hermes、Claude Desktop 八项中逐项给出“已支持 / 待接入 / 暂不支持”结论。
2. token-station 已覆盖 Claude Code、Codex、OpenCode；新增目标实际为 Gemini CLI、Claude Desktop、OpenClaw、Hermes、Grok Build。
3. Gemini CLI 使用 Google Gemini `generateContent` / `streamGenerateContent`，需要 `agent-gemini`；OpenClaw 和 Hermes 可配置为 OpenAI Chat Completions，优先复用 `agent-openai`。
4. Grok Build 默认使用 OpenAI Responses，普通 `/v1/responses` 可复用 `agent-openai-responses`；它还会使用 `/v1/responses/compact`，当前 token-station 未声明该子协议已兼容，不能只加 connector 就宣称完整支持。
5. Claude Desktop 可以覆盖自定义 Base URL，但不是 Claude Code 的环境变量方案。cc-switch 使用 macOS/Windows 的 3P inference profile；token-station 必须单独实现、测试并限制平台，不能复用 `~/.claude/settings.json` connector。
6. 当前 `catalog.ts` 已有 OpenAI、DeepSeek、GLM、Kimi、百炼/Qwen、Groq；任务指定的 OpenAI-compatible 组仍缺 MiniMax、NVIDIA NIM、Mistral、xAI、BytePlus/Ark。
7. OpenRouter 值得采纳的是两段式模型命名、请求扩展的可选字段布局、能力元数据、稳定错误分类，以及“首字节后不再换上游”。其默认忽略不支持参数、任意错误触发模型 fallback、调试回显上游请求体，与 token-station 红线冲突，不能照搬。
8. OpenRouter 当前视频接口已经是异步 `POST /api/v1/videos → GET job → GET content`，与任务说明指定的同步 `/v1/video/generations` 基线冲突。实现前必须在多模态设计评审中明确选择；在评审改变规格前，任务说明的同步基线仍然有效。

| Agent | 配置文件 | cc-switch 写入/管理的关键字段 | token-station 推荐入站 |

| Claude Code | `~/.claude/settings.json` | `env.ANTHROPIC_BASE_URL`、鉴权 token、`ANTHROPIC_DEFAULT_*_MODEL` 等 | Anthropic Messages |
| Claude Desktop | macOS `~/Library/Application Support/Claude[-3p]/claude_desktop_config.json` 与 `Claude-3p/configLibrary/<profile>.json`；Windows 对应 `%LOCALAPPDATA%/Claude[-3p]` | `deploymentMode=3p`、`inferenceGatewayBaseUrl`、`inferenceGatewayApiKey`、`inferenceGatewayAuthScheme=bearer`、`inferenceModels` | Anthropic Messages；仅 macOS/Windows 3P profile |

| Hermes | macOS/Linux `~/.hermes/config.yaml`；Windows `%LOCALAPPDATA%/hermes/config.yaml` | `custom_providers[].name/base_url/api_key/api_mode/models/model`；顶层 `model.default/provider` | 选择 `api_mode=chat_completions`，复用 Chat Completions |

连接器实现不能只写字段，还必须沿用本仓库的约束：写前确认对应入站 Adapter 已挂载、非法配置不覆盖、保留无关字段、备份、同目录临时文件替换、重复接入幂等。

### 3.3 不能照抄的坑

| 发现 | 判定 | token-station 处理 |
|---|---|---|
| Claude Desktop 与 Claude Code 配置完全不同，且 3P profile 仅支持 macOS/Windows | 改造采纳 | 独立 connector；Linux 明确返回“不支持”，不得写 Claude Code 配置冒充 |
| Gemini 同时修改 `.env` 和 `settings.json` | 改造采纳 | 按多文件变更处理；先快照，任一步失败恢复 |
| OpenClaw 是 JSON5，Hermes 是 YAML，均保留未知字段 | 直接采纳原则 | 使用语法正确的 round-trip/结构化修改，禁止字符串替换 |
| Grok Build 是 release 后新增项，且包含 `responses/compact` | 改造采纳 | 纳入范围；先增加协议能力测试，再决定仅 connector 还是扩 Adapter |
| cc-switch 的 additive/switch 模式是供应商切换产品语义 | 不采纳 | token-station Agent 长期指向本地网关，不按上游切换反复重写 Agent |
| cc-switch 预设含大量商业聚合站和推广入口 | 不采纳为默认目录 | 只把任务矩阵中的官方直连供应商纳入默认目录；聚合站不因 cc-switch 有预设就自动加入 |

## 4. cc-switch 预设库与 catalog 缺口

### 4.1 预设结构

cc-switch 不是一个统一的扁平预设文件，而是按 Agent 分开维护：

| 文件 | 顶层预设数 | 主要形状 |
|---|---:|---|
| `claudeProviderPresets.ts` | 70 | `env.ANTHROPIC_BASE_URL` + token + 三档模型别名 |
| `claudeDesktopProviderPresets.ts` | 67 | gateway 凭证 + Claude-safe route 映射 |
| `codexProviderPresets.ts` | 63 | TOML 模板 + auth + Responses/Chat 方言 |
| `geminiProviderPresets.ts` | 20 | `env.GOOGLE_GEMINI_BASE_URL` + `GEMINI_API_KEY` |
| `opencodeProviderPresets.ts` | 59 | AI SDK package + `options.baseURL/apiKey` + models |
| `openclawProviderPresets.ts` | 59 | `baseUrl/apiKey/api/models` |
| `hermesProviderPresets.ts` | 60 | `base_url/api_key/api_mode/models` |

计数按固定提交中各 `*ProviderPresets.ts` 顶层数组项机械统计。不同 Agent 的预设集合并不完全相同，不能把某一文件的 Base URL 无条件复制到另一协议；同一供应商可能分别提供 Anthropic、OpenAI-compatible、Gemini 或 Coding Plan 子路径。

Grok Build 是刚进入 `main` 的独立 Agent，目前通过专用表单生成 `config.toml`，没有与上述七个文件对等的静态 `grokbuildProviderPresets.ts`；不能把“Agent 已支持”误写成“已有完整供应商预设库”。

### 4.2 与 token-station `catalog.ts` 的对齐

任务 §3.0 指定的 OpenAI-compatible 官方家族对齐如下：

| 供应商 | 当前 catalog | cc-switch 可借鉴值 | M1 动作 |
|---|---|---|---|
| OpenAI | 已有 | Codex 官方预设 | 保留，官方文档复核模型与 Base URL |
| DeepSeek | 已有 | OpenClaw/OpenCode: `https://api.deepseek.com/v1` | 复核即可 |
| GLM / 智谱 | 已有 | `https://api.z.ai/api/coding/paas/v4` 等多种计划路径 | 区分普通 API 与 Coding Plan，不能混写 |
| Kimi / Moonshot | 已有 | `https://api.moonshot.cn/v1`；Coding Plan 为另一地址 | 区分普通 API 与 Coding Plan |
| 阿里百炼 | 已有 | `https://dashscope.aliyuncs.com/compatible-mode/v1` | 复核即可 |
| Groq | 已有 | cc-switch 主预设未覆盖 | 以 Groq 官方文档复核 |
| MiniMax | **缺失** | CN `https://api.minimaxi.com/v1`；Global `https://api.minimax.io/v1` | 新增两个区域预设或一个可选区域预设 |
| NVIDIA NIM | **缺失** | `https://integrate.api.nvidia.com/v1` | 新增 |

| Mistral | **缺失** | cc-switch 主预设未覆盖 | 按 Mistral 官方 API 新增 |
| xAI | **缺失** | cc-switch 新增的是 Grok Build Agent，不等于 xAI Provider 预设 | 按 xAI 官方 API 新增 |

`LOCAL_STATIC_EVIDENCE`：当前 catalog 另外已有 SiliconFlow、OpenRouter、Ollama；它们不替代上述任务必选项。

### 4.3 预设采纳规则

1. Base URL、鉴权方式必须再由供应商官方文档确认；cc-switch 只作为真实客户端配置形状的第一参考。
2. Coding Plan、普通按量 API、国内站、国际站必须使用不同预设或显式区域选择，不能因品牌相同合并地址。
3. 推荐模型属于易变数据；M1 应允许用户编辑，并记录核实日期。
4. 默认目录只收官方直连或任务明确要求项，不批量搬运商业聚合站。

## 5. OpenRouter 六项对照

### 5.1 总表

| 借鉴点 | OpenRouter 当前做法 | token-station 现状 | 判定 |
|---|---|---|---|
| 模型命名 | `author/model` 两段式 ID；托管 Provider 另建模；支持 `:free`、`:nitro`、`:floor`、`:exacto` 等 suffix | 上游名与模型名分离，桌面模型常是裸 ID | **改造采纳**：任务基线使用 `provider/model`，但模型身份和部署 Provider 仍须分层；suffix 解析为路由约束 |
| 请求超集 | 标准字段外增加顶层 `models`、`provider`、`plugins`、`debug`、`user`；均为可选 | Canonical IR 没有这些公共扩展 | **改造采纳**：未来扩展保持可选、顶层、向后兼容；逐项进设计 |
| 供应商差异 | 工具会转换；默认可把请求路由给不支持全部参数的 Provider，并忽略其未知参数；`require_parameters=true` 才强过滤 | 红线要求无法无损映射时显式 capability error | **不采纳默认忽略**；采纳能力预过滤和可证明无损的转换 |
| 错误 | `error.code/message/metadata`；另有稳定 `error_type`；首字节前可 fallback，首字节后只发流内错误 | 已有 `ErrorEnvelope` / `StreamEvent::Error` | **改造采纳**：保留状态、`Retry-After` 和稳定分类；首字节后禁止换模型 |
| 模型元数据 | `id/canonical_slug/context_length/architecture/pricing/top_provider/supported_parameters/default_parameters/expiration_date` 等 | `ModelCapability` 只有 tool/vision/json_schema/context_window/supported_parameters/extensions | **改造采纳**：在目录设计中补字段与来源，不直接塞进 Router 特判 |
| 多模态 | Chat 支持多模态输入；另有 `/embeddings`、`/images`、`/audio/speech`、`/audio/transcriptions`、异步 `/videos` | 只有 chat ABI；任务已规定自己的 OpenAI 风格端点 | **改造采纳**：借鉴数据模型和能力元数据，外部路径以任务基线/设计评审为准 |

### 5.2 模型命名与 suffix

OpenRouter 严格使用的是 `author/model`：前半段表示模型作者或组织，实际托管 Provider/Endpoint 由另一层路由选择。任务说明规定 token-station 使用 `provider/model`，因此这里只能采纳“两段式全局命名”的接口形状，不能宣称两边语义完全相同。

token-station 采用任务基线 `provider/model` 的理由：

- 消除不同供应商同名模型冲突；
- 模型目录、路由决策和观测记录可以使用同一个稳定标识；
- 非对话模态同样适用，例如 `openai/gpt-image-*`、`google/veo-*`。

suffix 不应成为 Provider Adapter 收到的真实模型 ID。`:nitro`/`:floor`/`:exacto` 本质是路由偏好；`:free` 可能选择不同部署池。token-station 若支持 suffix，应在控制面解析为显式策略，再把规范模型 ID 交给 Provider。

### 5.3 请求超集和兼容性

OpenRouter 把自有扩展放在请求顶层，且全部可选，因此老 OpenAI 客户端不传时仍兼容：

- `models: string[]`：模型级 fallback；
- `provider: {...}`：供应商顺序、允许/排除、参数强校验、隐私、价格、延迟、吞吐等约束；
- `plugins: [...]`：上下文压缩等请求/响应变换；
- `debug.echo_upstream_body`：流式回显转换后的上游请求；
- `user`：终端用户稳定标识。

任务说明提到的 `transforms` 已不是当前公开文档的主入口；上下文压缩现在通过 `plugins: [{id: "context-compression"}]` 表达。后续设计应引用当前字段，不继续把 `transforms` 当既定事实。

采纳边界：

- `models`、`provider` 可以作为未来自有扩展的格式参考，但必须先定义 IR 和审计语义；
- `debug.echo_upstream_body` **不采纳**，因为它可能回显 prompt/工具参数，与内容不进日志和决策记录的红线冲突；
- 自动上下文压缩会有损删除消息，默认 **不采纳**；只有调用方显式请求且协议契约允许时才能另案设计。

### 5.4 参数兼容

OpenRouter 默认 `require_parameters=false`，不支持的参数可能在 Provider 侧被忽略；设为 `true` 才只选支持全部参数的端点。它还会把 OpenAI tools 转换为其他供应商的工具格式。

token-station 应采用更严格的固定语义：

1. Router 先依据 `ModelCapability.supported_parameters` 和工具/模态能力过滤；
2. Provider Adapter 只做可证明无损的字段转换；
3. 无法表达 `tool_choice`、`response_format`、thinking、缓存签名等关键语义时，在访问上游前返回 capability error；
4. 不提供“默认忽略未知关键参数”的宽松模式。

### 5.5 错误与重试

建议采纳：

- 稳定机器分类与协议皮肤分离：内部保留统一错误类型，Chat/Messages/Responses 各自渲染；
- 429/503/504 等保留 `Retry-After`；
- 首字节前才允许同模型其他 Endpoint fallback；
- 首字节后 HTTP 状态已提交，只能发送流内错误并终止；
- 上游原始 code 可作为脱敏扩展保留，500 类错误隐藏供应商内部详情。

不采纳：

- OpenRouter 的模型 fallback 默认可由上下文长度、内容审核、限流、宕机等“任意错误”触发。token-station 必须按错误分类白名单决定是否重试，鉴权、参数、能力、内容策略错误不能跨 Provider 重放。

### 5.6 模型元数据差距

| OpenRouter 字段 | 本地对应 | 缺口/动作 |
|---|---|---|
| `id` | `ModelCapability.model` | 改为/补充全局 `provider/model` |
| `canonical_slug` | 无 | 增加稳定 ID 与 alias 分离 |
| `architecture.input_modalities/output_modalities` | `vision` 布尔值 | 需要模态集合，布尔值不足以表达音频、视频、图像输出、嵌入 |
| `context_length` | 已有 | 保留“未知为 0”的保守语义 |
| `supported_parameters` | 已有 | 进入真实路由与 Adapter 执行链，不能只展示 |
| `pricing` | 无 | 目录/部署级定价；不得放进纯 Router 的 IO 路径 |
| `top_provider` / Endpoint 详情 | 无 | Provider 与 Deployment 分层 |
| `default_parameters` | 无 | 仅作显式配置来源，不能静默改变调用方语义 |
| `expiration_date` | 无 | 生命周期/下线提示 |
| `supported_voices` | 无 | TTS voice 能力元数据 |
| 来源与更新时间 | 无 | 增加 provenance、fetched_at、手工覆盖优先级 |

## 6. 多模态接口采纳基线

### 6.1 任务基线

除视频争议外，后续设计直接以任务说明固化的接口为输入：

| 能力 | token-station 对外端点 |
|---|---|
| Chat | `/v1/chat/completions` |
| Anthropic Messages | `/v1/messages` |
| Responses | `/v1/responses` |
| Embeddings | `/v1/embeddings` |
| 图像 | `/v1/images/generations` |
| TTS | `/v1/audio/speech` |
| ASR | `/v1/audio/transcriptions` |
| 视频 | 暂按任务基线 `/v1/video/generations`，同步 facade |

### 6.2 与 OpenRouter 当前接口的差异

OpenRouter 当前提供：

- `POST /api/v1/embeddings`；
- `POST /api/v1/images`，不是 OpenAI 的 `/images/generations`；
- `POST /api/v1/audio/speech`，返回音频字节；
- `POST /api/v1/audio/transcriptions`，当前公开指南使用 JSON + base64 `input_audio`，不等同于任务要求的 OpenAI multipart；
- `POST /api/v1/videos` 返回 202 和 job ID，随后轮询 `GET /api/v1/videos/{jobId}`，再下载 content。

因此不能声称“OpenRouter 全部直接采用 OpenAI 标准端点”。可采纳的是请求字段、能力元数据、异步 job 状态和错误模型；token-station 对外 wire shape 仍须按任务基线实现。

### 6.3 视频设计冲突

`DECISION_REQUIRED`：

- 任务基线要求网关内部轮询、对外同步；
- OpenRouter 当前成熟实现选择对外异步 job，并明确视频通常需要 30 秒到数分钟；
- 同步 facade 会带来长连接超时、客户端断线后结果无法领取、网关并发槽长期占用等问题；
- 异步 job 更可靠，但改变了已经指定的公开契约。

`docs/design/多模态网关设计.md` 必须对两者做正式 ADR。评审改变规格前，不得擅自把任务端点改成 OpenRouter 的异步形状。

## 7. 三选一采纳清单

### 直接采纳

- Connector 与协议 Adapter 分离；
- OpenClaw/Hermes 配置保留未知字段；
- 能力元数据中明确 input/output modalities、supported parameters 和生命周期；
- 首字节后不再静默 fallback；
- 视频 job 的 pending/in_progress/completed/failed 状态与退避思路，作为设计参考。

### 改造采纳

- cc-switch 的 Agent 配置路径、字段、备份与原子写入模式；
- OpenRouter 两段式全局模型 ID 的形状；token-station 按任务基线落为 `provider/model`，同时保持模型身份与部署 Endpoint 分层；
- Claude Desktop 3P profile；
- OpenRouter 顶层可选请求扩展；
- 模型/Endpoint 两层 fallback；
- 统一错误分类和 `Retry-After`；
- OpenRouter 多模态请求字段与目录元数据；
- cc-switch 预设中的官方 Base URL，必须再经官方文档复核。

### 不采纳

- 默认忽略 Provider 不支持的参数；
- 自动、有损的上下文压缩；
- 任意错误都触发模型 fallback；
- 流式输出开始后切换模型；
- 回显完整上游请求体的 debug 能力；
- 把商业聚合站预设批量加入 token-station 默认目录；
- 让 Agent 持有上游真实 Key 或随上游切换反复改 Agent 配置；
- 在 Router 中增加 Agent/厂商特判。

2. OpenClaw：`api=openai-completions` connector。
3. Hermes：`api_mode=chat_completions` connector。
4. Claude Desktop：macOS/Windows 3P profile connector；Linux 明确不支持。
5. Grok Build：先验证 `/v1/responses` 与 `/v1/responses/compact`，再确定改动范围。

- `provider-anthropic`、`provider-gemini` 的实现 PR 必须引用本文的严格参数边界、错误语义和元数据差距；
- Bedrock SigV4 仍需独立设计，不在 M0 里假定 WASM 内签名可行。

### 多模态

- 先提交设计文档；
- 明确扩 WIT ABI 与宿主 Rust 模块两案；
- 对视频同步/异步冲突形成评审决定；
- 内容零落盘、密钥仅宿主注入、Router 不感知模态细节。
