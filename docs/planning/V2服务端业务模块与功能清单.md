# Token Station V2 服务端业务模块与功能清单

> 本文是 V2 **Server 版**的产品拆分视图，供产品范围、服务端领域划分和排期沟通使用。Server 版指同一服务端镜像支持的 **平台 SaaS、Team 私有部署与 Enterprise 私有部署**；不包含 C1–C3 本地客户端本体。客户端相关能力只保留服务端配套（设备授权、同步接收、远程配置、发布分发）。
>
> 需求语义以 [完整功能需求清单](../features/token-station功能需求清单.md) 为准；阶段和验收以 [V2 阶段需求清单](./V2阶段需求清单.md) 为准。本文不新增加需求。

## 1. 产品边界与关键口径

| 项目 | 结论 |
|---|---|
| 产品定位 | 统一 Token API 服务 + 智能模型路由器，可独立销售、独立计费。|
| 上游边界 | `glm5.2-platform` 与 OpenAI、Anthropic 等一样，都是普通上游；不共享账户、钱包或账本。|
| 交付形态 | SaaS、Team、Enterprise 共用服务端代码；差异由运行时套餐/license 控制，不能继续依赖编译期 feature 分叉。|
| BYOK 边界 | **服务端 BYOK** 是用户主动托管给网关的凭证，网关加密保管并代理请求；这不代表平台看不到请求内容。客户端本地 BYOK 永不上传，不属于本清单。|
| 路由边界 | 质量侧路由回答「请求该用哪个模型」；供给侧路由回答「该模型由哪个 provider/channel/credential 服务」。两者必须分域，不能用现有供给路由硬替代。|
| 透明边界 | 不建设通用 LLM 可观测平台；仅交付路由可解释、用量和账单所需的可观测能力。|

## 2. 领域模块与核心业务对象

原来的 M01–M11 只有中文功能分类，无法成为代码、表结构和 Service 的稳定边界。现将其改为**领域模块**：每个模块有一个不可变的英文标识（建议作为目录、Service 或未来 crate 的候选名）、一个明确的主职责，以及自己拥有的业务对象。

这里的“拥有”指该模块定义对象的生命周期、不变量和写入规则；其他模块只引用对象 ID 或读取已发布的领域事件，不能直接改写其状态。

| # | 领域模块名称 | 稳定标识 | 核心职责 | 核心业务对象（聚合根优先） | 主阶段 |
|---|---|---|---|---|---|
| M01 | 接入网关 | `api-access` | 接住 Agent/SDK 请求，完成协议识别、标准化、鉴权上下文和响应渲染 | `ApiRequest`、`RequestContext`、`ProtocolBinding`、`AgentProfile`、`StreamSession` | V1 基线 + P1 |
| M02 | 模型供给目录 | `model-supply` | 管理可售模型、上游、渠道与服务端托管凭证 | `Model`、`ModelVariant`、`Provider`、`Channel`、`ProviderCredential`、`ProviderHealth`、`ModelCapability` | V1 基线 + P1 |
| M03 | 路由策略 | `routing-policy` | 定义“请求应使用哪个模型”的质量侧策略 | `RoutingPolicy`、`RouteRule`、`MatchCondition`、`RouteAction`、`ModelPool`、`AgentHint`、`Preset` | P2–P4 |
| M04 | 供给派单 | `provider-dispatch` | 在候选供给中选择实际 provider/channel/credential，并处理失败 | `DispatchPlan`、`CandidateSet`、`RoutingConstraint`、`ProviderPreference`、`FallbackChain`、`DispatchAttempt`、`CircuitBreaker` | V1 基线 + P2 |
| M05 | 路由决策账本 | `decision-ledger` | 记录可解释的路由过程、结果与反事实成本 | `RoutingDecision`、`DecisionStep`、`DecisionFeature`、`DecisionReason`、`CostQuote`、`CounterfactualQuote`、`TraceLink` | P1–P2 |
| M06 | 租户与治理 | `tenant-governance` | 管理主体、组织层级、访问授权、Key 与治理规则 | `UserAccount`、`Organization`、`Team`、`Membership`、`RoleAssignment`、`VirtualKey`、`KeyPolicy`、`Budget`、`DataPolicy` | P0 + P3 |
| M07 | 商业计费 | `commerce-billing` | 管理定价、用量结算、钱包、订阅和收付款 | `PriceBook`、`UsageRecord`、`BillingRoute`、`Wallet`、`LedgerEntry`、`Subscription`、`Payment`、`RedemptionCode`、`Invoice` | V1 基线 + P1/P3 |
| M08 | 准入与安全 | `admission-safety` | 在请求进入与出站前执行限流、安全和内容策略 | `RateLimitPolicy`、`RateLimitState`、`AdmissionDecision`、`GuardrailPolicy`、`GuardrailResult`、`SecurityIncident` | P0 + P3/P4 |
| M09 | 开发者工作台 | `developer-workspace` | 提供接入、试验与自助查询体验；以组合其他领域数据为主 | `PlaygroundSession`、`SdkPackage`、`DocumentationPage`、`ApiExample`、`SavedQuery` | P1–P4 |
| M10 | 部署与扩展管理 | `deployment-extensions` | 管理 license、部署档位、插件、企业能力和客户端云端配套 | `License`、`Entitlement`、`DeploymentProfile`、`PluginPackage`、`PluginVersion`、`PluginEnablement`、`DeviceGrant`、`RemoteProfile`、`ReleaseArtifact`、`AuditEvent` | P3 |
| M11 | 路由学习 | `routing-intelligence` | 在元数据边界内采集反馈、评测并发布学习型路由能力 | `FeedbackSignal`、`TelemetryEvent`、`EvaluationRun`、`ClassifierVersion`、`ModelRollout`、`TrainingDatasetManifest` | P4 |

### 2.1 对象归属与依赖规则

| 对象 | 唯一拥有模块 | 可被哪些模块引用 | 不能发生的设计 |
|---|---|---|---|
| `ProviderCredential` | `model-supply` | `provider-dispatch`、`commerce-billing`、`decision-ledger` | 由路由规则或插件直接读取、修改密钥明文 |
| `RouteRule` / `Preset` | `routing-policy` | `api-access`、`decision-ledger`、`tenant-governance` | 由控制台页面、派单器或计费模块直接更新规则 |
| `RoutingDecision` | `decision-ledger` | `commerce-billing`、`developer-workspace`、`routing-intelligence` | 用 `UsageRecord` 反推完整决策过程 |
| `VirtualKey` / `Budget` | `tenant-governance` | `api-access`、`admission-safety`、`commerce-billing` | 在计费模块内另建一套 key 或预算真相来源 |
| `UsageRecord` / `LedgerEntry` | `commerce-billing` | `decision-ledger`、`developer-workspace` | 从仪表盘聚合结果回写账本金额 |
| `PluginPackage` / `PluginEnablement` | `deployment-extensions` | `api-access`、`model-supply` | 将插件启用状态散落在 provider 或 API 路由配置中 |
| `GuardrailResult` | `admission-safety` | `provider-dispatch`、`decision-ledger` | 将内容策略错误伪装成通用 provider 故障 |

### 2.2 核心业务对象目录

对象类型说明：**聚合根**是外部命令唯一可直接修改的业务一致性边界；**实体**有稳定身份但随聚合根管理；**值对象**只表达不可变的业务值；**记录/投影**用于事实留存或查询，不能作为业务规则的真相来源。

#### M01 接入网关（`api-access`）

| 对象 | 类型 | 完整描述 |
|---|---|---|
| `ApiRequest` | 瞬时命令对象 | 单次北向 API 调用的标准化入口，包含请求方法、目标模型、正文、流式标志和已脱敏 header 摘要。它从接收开始到响应完成有效，不作为原始内容持久化载体；成功后只把 ID、摘要和结果关联给 `RoutingDecision`、`UsageRecord`。 |
| `RequestContext` | 值对象 | 由认证和入口解析生成的不可变执行上下文，至少含 request/trace ID、调用主体、tenant/key、协议、地域与时间。后续模块只能读取它，不能在链路中篡改主体或租户归属。 |
| `ProtocolBinding` | 配置实体 | 将入口 path、协议版本、header 特征或 Agent 工具绑定到某个 `agent-adapter` 版本。生命周期为配置、启用、灰度、停用；插件本身不拥有该绑定。 |
| `AgentProfile` | 配置实体 | 描述一种 Agent/SDK 的协议能力、模型命名约定和可提取 hint，不保存用户会话或密钥。用于选择入口 adapter 和校验兼容性。 |
| `StreamSession` | 短生命周期实体 | 单次 SSE/流式响应的状态容器，跟踪已发送片段、终止原因与最终 usage 是否已结算。必须在客户端断连、上游结束和网关停机三种路径上完成结算或补偿。 |

#### M02 模型供给目录（`model-supply`）

| 对象 | 类型 | 完整描述 |
|---|---|---|
| `Model` | 聚合根 | 对用户可见的逻辑模型，例如 `gpt-4.1` 或 `auto` 的具体候选目标；拥有展示名、上下文长度、能力、定价引用和可用状态。它不等于某 provider 的某个 endpoint。 |
| `ModelVariant` | 实体 | 某逻辑模型的可派发变体，如推理强度、量化精度、区域或 provider 专有模型 ID。它归属 `Model`，用于让后缀解析和路由约束选择精确供给。 |
| `Provider` | 聚合根 | 上游服务商或自建推理系统的业务身份，如 OpenAI、Anthropic、Ollama。拥有支持的认证方言、适配器绑定和平台级治理属性，不直接承载单个 URL 或密钥。 |
| `Channel` | 实体 | 一个 provider 下实际可调用的供给通道，包含 endpoint、模型映射、权重、优先级、容量标签和启用状态。派单、健康检查和熔断以 channel 为主要粒度。 |
| `ProviderCredential` | 聚合根 | 平台凭证或服务端 BYOK 的归属、凭证槽位、类型、加密密文引用、校验状态和 fallback/账路策略。密钥明文只在宿主注入瞬间出现；删除后保留不可逆的归因快照，不保留明文。 |
| `ProviderHealth` | 状态实体 | 对 channel/credential 的近期可用性观测，含探测结果、失败类型、延迟、熔断状态和恢复时间。它是可重建运行状态，不能被当作模型或租户的永久配置。 |
| `ModelCapability` | 值对象 | 描述模型或变体是否支持 tool、vision、JSON Schema、最大上下文及参数集合。它是候选集过滤依据，不应由前端自由声明后直接信任。 |

#### M03 路由策略（`routing-policy`）

| 对象 | 类型 | 完整描述 |
|---|---|---|
| `RoutingPolicy` | 聚合根 | 一个 scope（平台/org/team/user/key）下完整的质量侧路由策略集合，定义规则顺序、默认模型池、启发式阈值与成本偏好。发布新版本时必须原子生效，避免一次请求读到半套规则。 |
| `RouteRule` | 实体 | `RoutingPolicy` 内一条按优先级求值的声明式规则；由多个 `MatchCondition` 和一个 `RouteAction` 构成，命中即终止。记录来源 request ID 才能支持“从决策覆写”闭环。 |
| `MatchCondition` | 值对象 | 可组合的匹配条件，例如 token 阈值、代码块、tool、JSON Schema、轮数、header、时段和预算余量；条件之间默认 AND。不得保存 prompt 原文，只保留可审计的元数据条件。 |
| `RouteAction` | 值对象 | 规则命中后的动作：选择模型/模型池，并可覆写 provider 偏好；不能直接指定密钥或绕过预算、限流和治理。 |
| `ModelPool` | 聚合根 | 可被策略引用的一组逻辑模型及其排序/权重语义，用于表达“便宜池”“代码池”等可维护目标。成员变化应版本化，保证历史决策可回放当时的候选定义。 |
| `AgentHint` | 值对象 | Agent 以协议 header 或入口特征声明的步骤类型、任务类型或能力信息；它是第二层路由输入，不是最终模型/provider 的强制指令。来源必须记录，未受信任 hint 不得提升权限。 |
| `Preset` | 聚合根 | 命名配置 `@preset/xxx`，封装模型、生成参数、provider 偏好和路由策略引用。它有 scope、版本、套餐门槛、发布/回滚历史；客户端引用别名而不是复制配置。 |

#### M04 供给派单（`provider-dispatch`）

| 对象 | 类型 | 完整描述 |
|---|---|---|
| `DispatchPlan` | 短生命周期聚合根 | 一次请求从逻辑模型到实际 channel/credential 的可执行派单计划。它冻结当时的候选、约束和 fallback 顺序，执行完成后形成 `RoutingDecision` 的供给侧步骤。 |
| `CandidateSet` | 值对象 | 经模型能力、租户治理、健康度、价格和数据策略过滤后的可选 channel 列表，以及每个候选的保留/剔除原因。必须持久化摘要以解释“为什么没选某家”。 |
| `RoutingConstraint` | 值对象 | 请求或策略提出的硬约束，如 `max_price`、quantization、ZDR、data collection 与必需参数；不满足的候选不能进入派单。 |
| `ProviderPreference` | 值对象 | 用户显式的 `order`、`only`、`ignore` 偏好，定义候选排序或排除边界。它低于平台治理约束，不能放行被禁 provider。 |
| `FallbackChain` | 配置聚合根 | 按容量、能力、内容策略三种失败语义定义的独立兜底链。链条成员是模型/池或 channel 选择规则，不能只用一条“失败重试列表”混淆错误语义。 |
| `DispatchAttempt` | 事实记录 | 对一个候选的单次上游调用，记录开始/结束、请求目标、结果、错误分类、退避和是否切换。多次 attempt 共同构成一次派单，不可被后续重写。 |
| `CircuitBreaker` | 状态实体 | 某 channel 或 credential 的 open/half-open/closed 状态机，依据失败窗口控制是否接收新请求。P3b 应将其共享状态外置，不能依赖单个进程内存。 |

#### M05 路由决策账本（`decision-ledger`）

| 对象 | 类型 | 完整描述 |
|---|---|---|
| `RoutingDecision` | 聚合根/事实记录 | 每个 API 请求唯一的、不可变的决策事实：请求模型、最终模型/provider/凭证归属、原因码、成本和结果。创建后只允许补齐异步终态（如流式 usage），不允许重写路由理由。 |
| `DecisionStep` | 实体 | 决策路径中的一个步骤，例如规则未命中、启发式得分、候选过滤、派单或 fallback。按时间和层级排序，构成用户可查看的决策时间线。 |
| `DecisionFeature` | 值对象 | 决策实际读取的元数据特征及值，如 token 数、是否含 tool、hint、预算水位和复杂度分值。用于证明路由没有偷读原始内容，并为分类器解释提供依据。 |
| `DecisionReason` | 值对象 | 稳定、受控的原因码及其参数，如 `rule_matched`、`hint_applied`、`capacity_fallback`。它是 API 响应头、前端文案和统计口径的共同契约，不允许使用自由文本代替。 |
| `CostQuote` | 值对象 | 本次实际执行的可计价成本快照，含价格表版本、输入/输出/缓存用量、币种和账路。账本据此记账，不能在价格表更新后重新按新价计算历史金额。 |
| `CounterfactualQuote` | 值对象 | 按统一基准计算的“未采用本次路由时”的可比较成本快照，用来计算节省金额。必须明确基准模型和适用账路，BYOK 路由费不能伪装成节省。 |
| `TraceLink` | 值对象 | request ID、trace ID、usage record、dispatch attempt 和审计事件之间的关联键。它只建立可追踪性，不复制各对象内容。 |

#### M06 租户与治理（`tenant-governance`）

| 对象 | 类型 | 完整描述 |
|---|---|---|
| `UserAccount` | 聚合根 | 可登录的人或服务主体，拥有认证身份、状态和个人设置；不是预算、凭证或账本的容器。用户停用后历史用量和决策仍按合规策略保留。 |
| `Organization` | 聚合根 | 资源隔离与商业归属的顶层租户，拥有套餐、治理默认值、成员和团队。所有可隔离资源都必须可追溯到组织或平台公共 scope。 |
| `Team` | 聚合根 | Organization 内用于协作、预算分配和配置隔离的工作空间。它不能跨 Organization 引用成员、规则或凭证。 |
| `Membership` | 实体 | 用户加入组织/团队的关系，含状态、加入时间和可见范围；离开团队不等于删除用户或历史责任归属。 |
| `RoleAssignment` | 实体 | 将固定角色（V2 为 admin/member）授予一个 membership 的授权事实。Enterprise 后续的细粒度权限应扩展此模型，不能在各 API 中散落角色判断。 |
| `VirtualKey` | 聚合根 | 对外调用用的可轮换凭证，拥有一次性展示的 secret、状态、过期、IP 白名单、preset 绑定和限流引用。完整 key 不可再次读取，轮换通过新 key 与历史链实现。 |
| `KeyPolicy` | 值对象 | 绑定到 Virtual Key 的模型/provider 访问范围、IP 白名单、默认 preset 与专属限制。它不是路由规则本身，只约束该 key 可提出什么请求。 |
| `Budget` | 聚合根 | 在 org/team/user/key scope 下定义金额上限、周期、soft 阈值和当前消费窗口。预算扣减必须与计费账本协作保持一致，不能只靠异步报表。 |
| `DataPolicy` | 聚合根 | 数据留存、ZDR、允许的数据收集与 provider 使用限制等强制治理规则。它高于用户 provider 偏好，并被候选集过滤和审计消费。 |

#### M07 商业计费（`commerce-billing`）

| 对象 | 类型 | 完整描述 |
|---|---|---|
| `PriceBook` | 聚合根 | 某时间段生效的模型成本价、售价、倍率、缓存价和服务费规则集合。发布后版本不可变，历史 `CostQuote` 必须引用当时版本。 |
| `UsageRecord` | 事实记录 | 已完成或已结算请求的计量结果，含 token 分类、模型、账路和关联决策 ID。它回答“用了多少”，不独自解释“为什么这样路由”。 |
| `BillingRoute` | 值对象 | 说明一次消费属于平台代采购转卖、BYOK 转卖或 BYOK 路由服务费。它决定扣款方、费率、账单分列和节省统计边界。 |
| `Wallet` | 聚合根 | 某商业主体的可用 credits 余额及币种语义；余额是 `LedgerEntry` 的派生结果或受其强一致性维护，不能被支付页面直接覆盖。 |
| `LedgerEntry` | 不可变事实记录 | 钱包发生的每笔充值、消费、调整、奖励或退款，带金额、方向、幂等键和业务来源。它是财务真相来源，禁止 UPDATE 金额或删除。 |
| `Subscription` | 聚合根 | 套餐合同状态，含计划、周期、续费、权益和成本旋钮档位。周期变化驱动预算重置与 entitlement 更新，但不直接修改历史账本。 |
| `Payment` | 聚合根 | 对 Stripe、易支付等支付渠道的一笔收款流程，含创建、待支付、成功、失败、退款和外部交易号。支付成功后通过幂等流程生成账本入账。 |
| `RedemptionCode` | 聚合根 | 可兑换余额或套餐的受控凭证，含批次、适用范围、有效期、次数和已兑换记录。兑换是一次业务命令，必须防并发重复使用。 |
| `Invoice` | 聚合根 | 面向客户的应收凭证，包含开票期间、金额快照、状态和文件引用；其金额来自账本/订阅结算结果，不能成为重新计算成本的来源。 |

#### M08 准入与安全（`admission-safety`）

| 对象 | 类型 | 完整描述 |
|---|---|---|
| `RateLimitPolicy` | 聚合根 | 定义某 key/tenant/model 的 RPM、TPM、窗口和超限行为。优先级和继承规则应显式，防止 key 与组织策略互相覆盖却无法解释。 |
| `RateLimitState` | 状态实体 | 某限流维度在当前窗口内的计数、重置时间和算法状态。它是可过期状态：P3a 可驻内存，P3b 必须外置到 Redis 或等价共享存储。 |
| `AdmissionDecision` | 事实记录 | 请求在认证、预算、限流和治理检查后的允许/拒绝/降级结果及原因码。它在拒绝时也应关联 request ID，避免失败调用不可审计。 |
| `GuardrailPolicy` | 聚合根 | PII、内容审查、注入检测、输出 schema 校验等策略及动作定义，包含拦截、只记录和内容策略 fallback。它与 `DataPolicy` 不同：前者判断内容风险，后者约束数据与供应商使用。 |
| `GuardrailResult` | 事实记录 | 一次 guardrail 执行的规则命中、风险等级、脱敏动作和后续处置；原始内容依留存策略处理，不默认写入该对象。 |
| `SecurityIncident` | 聚合根 | 对密钥泄漏、异常认证、插件越权、策略绕过等安全事件的处置单，含发现、分级、证据引用、状态和关闭结论。它不是普通请求错误日志。 |

#### M09 开发者工作台（`developer-workspace`）

| 对象 | 类型 | 完整描述 |
|---|---|---|
| `PlaygroundSession` | 聚合根 | 用户在体验场发起的一段临时测试会话，保存可复现的模型选择、参数和脱敏后的展示历史。实际调用仍产生 M05/M07 的决策和用量事实，不能只记录在会话中。 |
| `SdkPackage` | 发布实体 | 官方 SDK 的语言、版本、包地址、兼容 API 版本和示例引用。它是开发者分发元数据，不包含支付或租户授权。 |
| `DocumentationPage` | 内容聚合根 | 可版本化的接入、错误码、路由约束和 SDK 文档页面，具有发布状态和适用版本。文档描述业务规则，但不拥有这些规则。 |
| `ApiExample` | 内容实体 | 归属某文档或 SDK 的可执行/可复制请求示例，声明所需权限和预期响应。示例不得嵌入真实平台密钥或真实用户数据。 |
| `SavedQuery` | 聚合根 | 用户保存的用量、决策或日志筛选条件，包含 owner、scope 和查询定义。它只保存查询条件和展示偏好，不复制查询结果。 |

#### M10 部署与扩展管理（`deployment-extensions`）

| 对象 | 类型 | 完整描述 |
|---|---|---|
| `License` | 聚合根 | 由平台签发、可在线或 air-gap 校验的授权文件，包含签名、客户/部署绑定、有效期和允许的 entitlement。license 是授权凭证，不是套餐或支付流水。 |
| `Entitlement` | 值对象 | License 或 SaaS 套餐授予的能力开关与容量限制，如 OIDC、审计、PG/Redis、多副本、离线插件导入。网关在运行时判定它，禁止用编译期 SKU 分叉替代。 |
| `DeploymentProfile` | 聚合根 | SaaS、self-hosted、managed-hosting 等部署形态及其默认依赖、运维入口和安全限制。它不等于 license 档位：profile 说明在哪里运行，entitlement 说明能用什么。 |

| `ReleaseArtifact` | 聚合根 | 客户端或企业部署包的版本、签名、checksum、兼容矩阵和发布通道。它连接发布/下载流程，不等于 PluginPackage。 |
| `AuditEvent` | 不可变事实记录 | 对管理操作、授权、配置变更、插件启停和安全敏感行为的审计事实，含主体、对象、动作、时间、前后摘要和 trace。不能被业务管理员修改或删除。 |

| `EvaluationRun` | 聚合根 | 对某策略、LLM router 或分类器版本进行离线质量/成本/延迟评测的一次可复现实验，保存数据集版本、指标、阈值和结论。未达门槛不能触发上线。 |
| `ClassifierVersion` | 聚合根 | 可部署的学习型路由模型版本，含权重引用、特征 schema、训练来源摘要、评测引用和兼容性。它必须能解释输入特征，不能作为不可审计黑箱直接替换规则。 |

| `TrainingDatasetManifest` | 不可变清单 | 训练/评测数据集的来源、字段、脱敏规则、opt-in 范围、版本和保留期限清单。保存的是可审计元数据，不应把未经批准的内容样本隐藏在其中。 |

### 2.3 一个必要的边界修正

`developer-workspace` 不是承载所有业务数据的“大后台模块”。仪表盘、用量页、模型目录、决策页和管理后台大多是其他模块对象的查询投影或命令入口；它只拥有 Playground 会话、文档和保存查询等交互对象。否则 M09 会膨胀成所有领域的绕过通道，租户隔离、账本一致性和路由审计都会失控。

## 3. 模块功能清单

### M01 接入网关（`api-access`）

- OpenAI 兼容 `/v1/chat/completions`、`/v1/responses`、流式响应与 `/v1/models`。
- Anthropic Messages 原生端点；Gemini 原生端点及 OpenAI/Claude/Gemini 跨格式互译为差异化能力。
- 模型后缀解析（如 `-thinking`、`-high`）、Agent hint header 消费。
- 统一认证、请求 ID/trace ID、稳定错误码；对外 API 只加不改，错误对象外形保持兼容。
- Python/JavaScript SDK、OpenAI SDK `base_url` 接入说明，以及工具调用/MCP passthrough（后置）。

### M02 模型供给目录（`model-supply`）

- 多 provider/channel 接入：官方 API、自建端点、订阅型上游和普通上游。
- 模型统一目录：价格、上下文、吞吐、延迟、精度、参数能力、数据收集/ZDR 标签；未登录可浏览。
- 平台凭证池：渠道分组、优先级、权重、标签、健康探测、自动禁用与恢复。
- 服务端 BYOK：用户/租户归属、加密存储、API Key 与 OAuth 订阅凭证、校验和刷新。
- BYOK 派单模式：`always-use`、`fallback`、默认回退；`always-use` 时不得使用平台凭证。
- 模型语义别名（`fast`/`smart`/`cheap`）和后续按套餐解析。

### M03 路由策略（`routing-policy`）

- 第一层声明式规则：按 token 数、代码块、tool、JSON Schema、会话轮数、header/hint、时段、预算余量匹配；顺序求值、命中即终止。
- 规则作用域：P2 的 user/key，P3 扩展为 org/team/key；支持即时启停、优先级、命中统计和从决策页一键覆写。
- 第二层内建启发式复杂度评分：阈值、目标模型池和 Agent 步骤类型可配置。
- `auto` 逻辑模型：第一、二层的默认组合。
- P4：Preset（`@preset/xxx`）集中管理、版本/回滚/导出；LLM-as-Router 冷启动、学习型分类器、客户端小模型分发、成本旋钮与非流式级联兜底。

### M04 供给派单（`provider-dispatch`）

- 请求级 provider 偏好：`order`、`only`、`ignore`；按 price/throughput/latency 排序。
- 候选集过滤：参数能力、最高价格、量化精度、数据收集和 ZDR 约束。
- 多 key 分摊与负载均衡，支持默认加权派单。
- 三层正交容灾：熔断、冷却、模型锁定；失败按容量、能力、内容策略分类走独立 fallback 链。
- 细分重试、指数退避和 jitter、open/half-open 熔断状态机。
- 后置：配额感知 fill-first、Canary 灰度。

### M05 路由决策账本（`decision-ledger`）

- 每请求记录候选集、逐层路径、最终模型/provider/credential、原因码、失败与 fallback 轨迹。
- 响应头输出 `X-Routed-Model`、`X-Routed-Reason`、`X-Cost`，并支持按 `request_id` / `trace_id` 查询。
- 决策详情展示：规则命中、启发式特征与分值、候选过滤原因、实际费用和反事实费用。
- 路由透明三件套：为何路由、若不路由的成本、本次决策一键生成覆写规则。
- 用量、账单、仪表盘按模型/provider/凭证归属/账路汇总；结构化 JSON 日志和全链路 trace 关联。

### M06 租户与治理（`tenant-governance`）

- P0 认证加固：Argon2id、session 哈希、Secure/`__Host-` cookie、CSRF 与常量时间比较。
- Virtual Key 生命周期：创建、撤销、软删、过期、轮换、IP 白名单、preset 绑定。
- P3 租户模型：org → team → user → key，workspace 隔离，固定角色 RBAC（admin/member）。
- 每租户隔离 routing、preset 与 BYOK 配置。
- 治理 guardrail：模型/provider 白黑名单、支出上限、数据策略强制。
- Enterprise：OIDC；SCIM、细粒度 RBAC、审批流明确不在 V2 验收范围。

### M07 商业计费（`commerce-billing`）

- 逐请求 token/多模态计量、成本计算、倍率/按量/按次/缓存命中计费，外置定价表。
- 自有 credits/钱包与账本；token-station 独立充值、扣费、订阅和账单，不依附任一上游。
- BYOK 双账路：平台代采购转卖（resale）与仅路由服务费（routing fee，可为 0）；两类用量、账单和节省口径必须分列。
- 分层预算与周期重置：org/team/user/key，soft 告警与 hard 拒绝。
- P3 商业化：运行时计费模式、套餐/订阅、Stripe/易支付、兑换码、发票。
- 计费可信性：流式断连仍完整入账、溢出检查、守恒性质测试。

### M08 准入与安全（`admission-safety`）

- 按 key/租户/模型的 RPM、TPM 准入限流，返回 `limit`/`remaining`/`reset` 响应头。
- P3a 单机内存状态；P3b Redis 共享状态，保障多副本限流与熔断一致。
- Secrets 使用 `secrecy` 封装，配置拒绝未知字段，错误不回显内部细节。
- 内容 guardrail（P4，优先复用开源）：PII 脱敏、内容审查、越狱/注入检测、Regex/JSON Schema 校验；动作可拦截、记录或触发内容策略 fallback。
- Prompt caching 透传；精确缓存、语义缓存、幂等去重均后置。

### M09 开发者工作台（`developer-workspace`）

- 用户侧：仪表盘、Playground、API Key、自带上游、模型目录、规则、Preset、决策记录、用量、账单、组织与设置。
- 运营侧：平台概览、请求日志、套餐计费、额度、组织/用户、provider、模型、供给路由、智能路由、飞轮、License。
- 模型选型、快速接入、SDK 示例、错误目录、hint/路由约束文档。
- 开发者体验边界：不做 Prompt 管理/A-B/partials 等 LLMOps 能力；Webhook 与状态页后置。

### M10 部署与扩展管理（`deployment-extensions`）

- Team：单二进制、Docker、SQLite、单机运行。
- Enterprise：Ed25519 签名 license、air-gap 离线激活、Postgres、Redis、OIDC、管理审计日志、Kubernetes/Helm、多副本部署。
- 同一镜像由 license 开启 Team/Enterprise 能力；Team 完成后可售，Enterprise 全量销售必须在 P3b 后。
- 客户端服务端配套：设备码授权、云同步接收（字段白名单）、多设备用量报表、非机密 profile 远程配置（版本/回滚/导出）、客户端发布与签名流水线。
- 明确不做：第一版自助托管控制面与实例管理；托管交付由人工运营流程完成。

### M11 路由学习（`routing-intelligence`）

- 采集 Feedback、重试/重新生成等**元数据**；条款只预留 opt-in，不采集内容训练。
- LLM 路由与学习型分类器必须有离线质量/成本评测门槛；不达标不得替换线上策略。
- 分类器的输入特征、版本与路由理由可查询；P4 后才考虑将蒸馏模型用于客户端。

| 阶段 | 服务端可交付价值 | 关键出口 |
|---|---|---|
| P0 | 可信运行基线 | 计费不丢失、认证安全、CI、健康检查、优雅停机。|
| P1 / M1 | 可接入、可归因的统一网关 | 请求有路由响应头和决策记录；BYOK 能请求且按路由费结算。|
| P2 / M2 | 可解释的智能路由 | 规则即时生效、hint 分流、账单显示节省金额。|
| P3a / M3 Team | 可售的团队商业闭环 | org/team 独立预算；同一镜像按 license 起 Team 形态。|
| P3b / M3 Enterprise | 可规模部署的企业基座 | 双副本下限流/熔断一致，具备 PG/Redis/OIDC/审计/K8s。|
| P4 / M4 | 可演进的路由护城河 | Preset 可跨客户端回滚；飞轮在元数据与离线评测约束下启用。|

## 5. 跨模块不变式与范围裁决

- 路由决策必须能回答「路由到谁、为什么、不路由花多少」。
- SaaS 与客户端的隐私承诺不能混写：服务端 BYOK 会经过服务端；客户端 BYOK 不上传。
- 个人/企业形态的路由决策应在本地/企业边界完成，客户端请求/响应原文不得上传。
- 原始内容不得进入数据飞轮；内容画像功能不应在平台 SaaS 默认启用。
- V1 存量 API 兼容性与每阶段可发布性是硬约束。

## 6. 当前需要持续警惕的结构性问题

1. 决策记录是 P1 的纵切地基；若后置，路由、账单与透明页面都会返工。
2. BYOK 必须引入凭证归属和双账路，不能复用「平台全局凭证池」的旧模型硬拼。
3. 多租户不是后台页面改造，而是数据归属、授权、配置隔离与预算扣减的整体改造。
4. Team 与 Enterprise 的分界是状态和部署模型：单机 SQLite 可服务 Team，PG/Redis 才能支撑多副本 Enterprise。
5. 质量侧路由和供给侧路由职责不同；混合实现会导致规则、解释和故障链无法正确表达。

## 7. 与社区版共用 API / Provider Adapter 的插件机制

### 7.1 结论

服务端与社区版本地客户端应当共用**同一套协议内核和插件机制**，而不是各自维护 API/provider 适配代码。共用的不是一套无边界的业务代码，而是稳定的 Canonical IR、双端 Adapter ABI、WASM runtime、manifest 格式和 conformance 准入标准；两端各自实现宿主能力。

| 层级 | 社区版 | Server 版 | 复用关系 |
|---|---|---|---|
| Canonical IR、`AgentHint` | 本地请求标准化与本地路由输入 | 网关请求标准化与服务端路由输入 | 共用 |
| `agent-adapter-v1` | 接入 IDE、CLI、SDK | 接入 SaaS/私有网关的 Agent 请求 | 共用插件 ABI 与插件包 |
| `provider-adapter-v1` | 接入用户 BYOK、本地 Ollama/vLLM 等上游 | 接入平台凭证、服务端 BYOK、企业上游 | 共用插件 ABI 与插件包 |
| WASM runtime / manifest / 签名 | 本地插件加载与校验 | 服务端插件安装、启用与校验 | 共用基础实现与格式 |
| Conformance suite / fixtures | 开发、安装和升级前验收 | 开发、安装、升级与灰度前验收 | 共用 |

### 7.2 两端必须分开的宿主职责

适配器只能做协议转换；密钥、网络与业务策略必须留在各自宿主中。因此不能将服务端的 host 实现直接复制进社区版，也不能让插件自行联网。

| 职责 | 社区版宿主 | Server 版宿主 |
|---|---|---|
| 凭证存储与注入 | 本地 keychain/主密码密文；客户端 BYOK 永不上传 | 平台凭证与服务端 BYOK 加密保管；按用户/租户归属注入 |
| HTTP 发起 | 本地进程向用户配置上游或本地模型发起 | 网关向已授权 provider endpoint 发起 |
| 路由与策略 | 本地规则、启发式与本地配置 | 租户规则、预算、provider 偏好、fallback 与治理策略 |
| 计量与审计 | 本地指标库和文件日志 | 逐请求计量、账本、限流、审计、决策记录 |
| 插件运营 | 本地安装、版本锁定与回滚 | 签名校验、按 global/org/team/key 启用、灰度、熔断与回滚 |

### 7.3 两类 Adapter 必须隔离

- `agent-adapter` 是北向入口：把 Claude Code、Codex CLI、Cursor、OpenAI SDK 等协议规范化为 Canonical IR，并把结果渲染回入口协议。
- `provider-adapter` 是南向出口：把 Canonical IR 变为 OpenAI、Anthropic、Gemini、Bedrock、Azure OpenAI、Ollama/vLLM 等上游 HTTP 方言，并解析响应、流和错误。
- 两者不可合并为“万能 adapter”。`provider-adapter` 可请求 host 代为签名或注入指定凭证，`agent-adapter` 不应拥有这项能力；合并会让入口插件获得本不需要的凭证能力。

### 7.4 安全和业务边界

- 插件默认无网络、无文件系统、无密钥明文；Provider adapter 只声明 `secret_ref` 与认证方言，host 负责校验目的地、注入凭证并发送 HTTP。
- 认证、租户识别、候选集选择、预算、限流、计费、fallback、日志和审计均不可插件化，避免插件绕过平台治理。
- 服务端在注入凭证前必须校验 adapter 给出的 URL 位于配置的 `base_url` 授权范围内，否则恶意 adapter 可以通过伪造目的地外泄密钥。
- 同一 adapter 包可同时发布 Agent 与 Provider 两个 role，但必须是两个独立 manifest 与 WASM component，分别运行对应 conformance；单个 manifest 只能表示一个 role。

### 7.5 实施状态与落点

- 已定义：`crates/protocol` 的 Canonical IR，`crates/plugin-api` 的 `agent-adapter-v1` / `provider-adapter-v1` WIT ABI，官方样板插件与 `crates/conformance` 的验收入口。
- 待实现：WASM component 实际加载、资源限制、签名校验、安装流程、服务端按租户启用/灰度/回滚，以及完整 runtime host functions。当前 `crates/plugin-runtime` 仍只是 adapter 元数据骨架。
- 分期：上述插件地基属于 P1；服务端插件 registry、管理、租户 scope 与审计属于 P3。社区版与服务端均应消费同一 `plugin-runtime` 和 conformance 标准。
