# V1 需求清单与业务模块（cloud_ai_gateway 基线）

> 场景：V1 = 现有 [cloud_ai_gateway](https://github.com/second-state/cloud_ai_gateway)。本文把 V1 **已实现的能力反推为需求基线文档**：业务模块划分 + 各模块需求清单 + 已知缺陷。用途有三：① V2 开发的现状基线（哪些需求「已满足」不必重做）；② V1 存量运营期间的功能面口径；③ 与 [V2 阶段需求清单](./V2阶段需求清单.md) 形成「基线 → 增量」的对照。
>
> 整理日期 2026-07-08。能力证据见 [功能清单（源码盘点）](../research/cloud-ai-gateway-自研网关功能清单.md)；已知缺陷源自 [规范符合性审计](../architecture/cloud-ai-gateway开发规范符合性审计.md)。需求编号 `V1-<模块>-<序号>`。
>
> **2026-07-08 修订（对照源码核实）**：制作 [V1 设计原型](../design/v1-prototype/index.html) 时逐页对照源码，修正四处口径并补录一个漏记的域——① key 前缀实为 `gw-`（连字符）；② 模型白名单在用户/团队级，**不存在 key 级白名单**；③ 管理看板 CSV 导出仅模型定价一处（/admin/models.csv）；④ 迁移数已是 64 个；⑤ **补录团队治理域**（teams/team_quota_rules/team_allowed_models，新增 V1-M6-4/5），此前 M4 边界「无 team」的说法有误。

## 零、V1 产品定位与业务模块总览

V1 是一个**平台运营者视角**的多上游 LLM 网关：管理员配置上游与路由，用户注册、充值、拿 key 调用。单 Rust 二进制 + SQLite，三种计费形态按编译期 feature 出包。

```
┌───────────────────────── V1 业务模块地图 ─────────────────────────┐
│  M1 协议接入      M2 路由与容灾     M3 上游与凭证                    │
│  M4 鉴权与账号    M5 计费与计量     M6 配额与准入                    │
│  M7 WASM 插件     M8 可观测与日志   M9 用户画像                     │
│  M10 控制台与 i18n                 M11 部署与运维                   │
└──────────────────────────────────────────────────────────────────┘
```

| 模块 | 一句话职责 | 在 V2 中的走向 |
|------|-----------|---------------|
| M1 协议接入 | 三协议入口 + 互译 + 多模态端点 | 协议能力保留，生产可用前需 P0/P1 加固（SSE 计费、错误码、request_id）|
| M2 路由与容灾 | 供给侧路由：谁来服务这个模型 | 保留 + P2 升级（质量侧路由是 V2 新增域）|
| M3 上游与凭证 | 35 种 provider + 平台凭证池 | 保留 + P1 改造（增加 BYOK 用户归属维度）|
| M4 鉴权与账号 | key/会话/管理员 | P0 安全加固 + P3 重构为多租户 RBAC |
| M5 计费与计量 | 分桶计量 + 三模式计费 | 内核保留 + P3 运行时化/产品化 |
| M6 配额与准入 | 花费配额窗口 + 团队治理（配额/模型继承与覆盖） | P3 扩展为层级预算 + RPM/TPM 限流 |
| M7 WASM 插件 | 可编程请求改写/路由 | 降级为 Enterprise 扩展点（拍板见升级方案 §三）|
| M8 可观测与日志 | 请求日志 + 用量统计 + 看板 | 保留 + P1 叠加决策记录纵切 |
| M9 用户画像 | 行为画像 + LLM 深度画像 | **平台形态默认下线**（信任叙事冲突）|
| M10 控制台与 i18n | 全套 Web UI + 五语言 | 保留直用 |
| M11 部署与运维 | 单二进制/Docker/TLS | 保留 = V2 Team 档形态；P3 增 Enterprise 档 |

## 一、M1 协议接入模块

| 编号 | 需求 | 实现位置 |
|------|------|---------|
| V1-M1-1 | OpenAI 兼容聊天端点（含流式 SSE）：`/v1/chat/completions`、`/v1/responses` | routes/proxy_chat.rs、proxy_responses.rs |
| V1-M1-2 | Anthropic Messages 原生端点 `/v1/messages`（Claude Code 可直连） | routes/proxy_anthropic.rs |
| V1-M1-3 | Gemini 原生端点 `/v1beta/models/*`（generateContent/stream/operations/Interactions） | routes/proxy_gemini*.rs |
| V1-M1-4 | 模型目录端点 `/v1/models`（OpenAI SDK 兼容） | routes/models.rs |
| V1-M1-5 | 跨格式互译：OpenAI⇄Anthropic⇄Gemini⇄Responses⇄Bedrock Converse，请求/响应/SSE 逐帧三向翻译 | proxy/translate/*、streaming.rs |
| V1-M1-6 | Embeddings 端点 `/v1/embeddings`（含 OpenAI⇄Gemini 翻译） | routes/proxy_embeddings.rs |
| V1-M1-7 | 图像生成/编辑端点（OpenAI/Gemini/MiniMax/Ideogram/Stability/xAI/百炼/GMI 多后端） | routes/proxy_images/ |
| V1-M1-8 | 音频端点：转录/翻译/TTS + ElevenLabs 原生 TTS | routes/proxy_audio.rs、proxy_elevenlabs.rs |
| V1-M1-9 | 视频生成端点（网关内部轮询异步任务，一次调用进出）+ Kling/百炼原生任务生命周期 | routes/proxy_video.rs、proxy_kling.rs、proxy_bailian.rs |
| V1-M1-10 | 音乐生成端点（MiniMax） | routes/proxy_music.rs |
| V1-M1-11 | Reve 原生图像 create/edit/remix 直通 | routes/proxy_reve.rs |
| V1-M1-12 | 主流 coding agent CLI 兼容（Claude Code / Codex / pi 指向即用，有集成测试） | tests/test_cli_agents.sh |

**已知缺陷**：SSE 无网关心跳、断连不记账（→ V2 P0#1）；错误响应缺 request_id/稳定 code（→ P1）。因此 M1 只能视为「协议覆盖已具备」，不能按生产交付口径无改造直用。

## 二、M2 路由与容灾模块

| 编号 | 需求 | 实现位置 |
|------|------|---------|
| V1-M2-1 | 管理员配置的路由组：逻辑模型名 → 多候选上游 channel（routing_groups/routing_channels） | proxy/routing.rs |
| V1-M2-2 | 五种选路策略：single / weighted_random / round_robin / lowest_latency / fallback | 同上 |
| V1-M2-3 | channel 级 RPM 上限，达限自动跳下一优先级 | proxy/rpm_tracker.rs |
| V1-M2-4 | 故障转移：可重试状态码（5xx/401/408/429）沿 failover 链轮换凭证与 channel，max_retries 封顶 | proxy/retry.rs、dispatch.rs |
| V1-M2-5 | fallback 熔断冷却（fallback_cooldown_secs） | proxy/routing.rs |
| V1-M2-6 | 后台健康探测循环，按凭证写 channel_health（p50 延迟/错误率） | proxy/health_probe.rs |
| V1-M2-7 | legacy 模型别名重写（model_aliases，无 channel 归因的回退路径） | proxy/routing.rs |

**已知缺陷**：failover 无退避 jitter；熔断无 open/half-open 状态机；失败类型不分语义（容量/能力/内容策略同链）（→ P2#5）。**边界**：V1 路由全部是供给侧 + 管理员配置，无任何用户侧质量路由。

## 三、M3 上游与凭证模块

| 编号 | 需求 | 实现位置 |
|------|------|---------|
| V1-M3-1 | 约 35 种 provider_type，覆盖 OpenAI 兼容 / Anthropic / Responses / Gemini / 媒体专用四类 wire | config.rs |
| V1-M3-2 | 订阅型上游：Claude Code / Codex / Copilot / Kiro / GLM Coding Plan 当凭证，OAuth token 自动刷新 | proxy/claude_code.rs、kiro.rs、token_refresh.rs |
| V1-M3-3 | AWS 系上游：SigV4 签名 + eventstream 解析（Bedrock/Bedrock-Claude/Bedrock-OpenAI） | proxy/aws_sigv4.rs、aws_eventstream.rs、bedrock.rs |
| V1-M3-4 | 平台级凭证池：多 key 权重轮换、credential_strategy、分组、启停 | proxy/provider_pool.rs、credential_store.rs |
| V1-M3-5 | providers/models 目录 config 权威、启动时 reconcile 进 DB；模型完整定价（分桶 token 价 + 多模态计价 + 阶梯） | proxy/config_seed.rs |

**边界**：凭证只有平台全局维度，**无用户归属（BYOK 不存在）**（→ P1#4）。

## 四、M4 鉴权与账号模块

| 编号 | 需求 | 实现位置 |
|------|------|---------|
| V1-M4-1 | 网关 API key（`gw-` 前缀，SHA-256 哈希存储）发放/停用/软删，key 级 WASM 绑定（模型白名单在用户/团队级，见 M6，无 key 级白名单） | middleware/auth.rs、routes/keys.rs |
| V1-M4-2 | magic-link 注册/登录（Resend 邮件），gw_session cookie 会话 | routes/auth.rs |
| V1-M4-3 | 管理员会话（admin 密码 → cookie），注册开关配置 | routes/admin.rs |

**已知缺陷（高危，→ P0#2）**：admin 密码 SHA-256 非 Argon2id 且 `==` 比较；session token 明文存库；cookie 缺 Secure/`__Host-`；零 CSRF。**边界**：有团队维度（治理归 M6，见 V1-M6-4/5），但无 org/workspace 层级、无角色化 RBAC，团队亦无自助管理入口（成员分配/规则全部由管理员操作）（→ P3#1）。

## 五、M5 计费与计量模块

| 编号 | 需求 | 实现位置 |
|------|------|---------|
| V1-M5-1 | 三种计费形态（编译期 feature）：余额（微美元+Stripe+首充奖金）/ 配额 / 配额+系统信用池 | config.rs、routes/billing.rs、system_credits.rs |
| V1-M5-2 | 分桶 token 计量：input/output/cached/cache_creation/cache_read 各自单价 | proxy/token_counter.rs |
| V1-M5-3 | 多模态计量：视频秒 / TTS 字符 / 图片张 / 信用点，支持 price_tiers | 同上 |
| V1-M5-4 | 每用户 markup 加价倍率 | db/billing.rs |
| V1-M5-5 | 余额流水账本（balance_transactions，含 Stripe session/收据） | db/billing.rs |
| V1-M5-6 | 上游对账测试：xAI cost ticks / Kimi 余额 diff / OpenAI+Anthropic Admin API 聚合 | tests/test_billing.sh |

**已知缺陷**：流式断连丢账（→ P0#1）；无 overflow-checks 与 proptest 守恒测试（→ P0#7）。**边界**：无订阅/兑换码/发票/易支付/soft 告警/层级预算（→ P3）；无成本响应头回显（→ P1#1）。

## 六、M6 配额与准入模块

| 编号 | 需求 | 实现位置 |
|------|------|---------|
| V1-M6-1 | 用户级花费配额窗口（limit_amount/window_seconds，超限 429） | quota.rs |
| V1-M6-2 | 座位上限 max_seats（quota 模式控制新用户创建） | 同上 |
| V1-M6-3 | 每用户可用模型白名单（user_allowed_models） | db/ |
| V1-M6-4 | 团队（teams）：管理员建团队、分配成员；团队级配额规则（team_quota_rules）与模型白名单（team_allowed_models）；成员默认继承，可按人独立覆盖配额、模型两个维度 | db/teams.rs、templates/admin_teams_pages.rs |
| V1-M6-5 | 生效规则解析：effective_user_quotas / effective_allowed_models（个人覆盖 > 团队继承 > 未入队自有规则；空团队白名单 = 全拒而非全放） | db/teams.rs、routes/models.rs |

**边界**：无按 key/租户的 RPM/TPM 准入限流（channel RPM 是供给侧概念）（→ P3#5）；团队仅一层（无嵌套/org），预算只有规则窗口、无层级预算汇总。

## 七、M7 WASM 插件模块

| 编号 | 需求 | 实现位置 |
|------|------|---------|
| V1-M7-1 | 两级 WASM 链（管理员全局 → key 绑定），插件可改写请求体与目标模型 | wasm_chain.rs |

## 十二、V1 基线小结

- **需求总数 54 条**，其中在 V2 中「保留直用」约 38 条、「保留但需改造」约 12 条（含团队治理 M6-4/5，将被 P3 多租户 RBAC 重构吸收）、「默认下线」3 条（M9）、「机制降级」1 条（M7 链）。
- **V1 的产品性缺口**（不是缺陷，是定位差异）：全部配置权在管理员、无用户侧质量路由、无 BYOK、多租户只到团队一层（无 org/RBAC/自助管理）、无路由透明——这正是 [V2 阶段需求清单](./V2阶段需求清单.md) 的增量主体。
- **7 项高危缺陷**全部收口在 V2 开发计划 P0 期（[规范审计 §二](../architecture/cloud-ai-gateway开发规范符合性审计.md)）。
