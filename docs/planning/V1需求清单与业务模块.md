## 零、V1 产品定位与业务模块总览

V1 是一个**平台运营者视角**的多上游 LLM 网关：管理员配置上游与路由，用户注册、充值、拿 key 调用。单 Rust 二进制 + SQLite，三种计费形态按编译期 feature 出包。

```
┌───────────────────────── V1 业务模块地图 ─────────────────────────┐
│  M1 协议接入      M2 路由与容灾     M3 上游与凭证                    │
│  M4 鉴权与账号    M5 计费与计量     M6 配额与准入                    │
│  M7 WASM 插件     M8 可观测与日志   M9 用户画像                     │
│  M10 控制台与 i18n                 M11 部署与运维                   │
└──────────────────────────────────────────────────────────────────┘
```

| 模块 | 一句话职责 | 在 V2 中的走向 |
|------|-----------|---------------|
| M1 协议接入 | 三协议入口 + 互译 + 多模态端点 | 协议能力保留，生产可用前需 P0/P1 加固（SSE 计费、错误码、request_id）|
| M2 路由与容灾 | 供给侧路由：谁来服务这个模型 | 保留 + P2 升级（质量侧路由是 V2 新增域）|
| M3 上游与凭证 | 35 种 provider + 平台凭证池 | 保留 + P1 改造（增加 BYOK 用户归属维度）|
| M4 鉴权与账号 | key/会话/管理员 | P0 安全加固 + P3 重构为多租户 RBAC |
| M5 计费与计量 | 分桶计量 + 三模式计费 | 内核保留 + P3 运行时化/产品化 |
| M6 配额与准入 | 花费配额窗口 + 团队治理（配额/模型继承与覆盖） | P3 扩展为层级预算 + RPM/TPM 限流 |
| M7 WASM 插件 | 可编程请求改写/路由 | 降级为 Enterprise 扩展点（拍板见升级方案 §三）|
| M8 可观测与日志 | 请求日志 + 用量统计 + 看板 | 保留 + P1 叠加决策记录纵切 |
| M9 用户画像 | 行为画像 + LLM 深度画像 | **平台形态默认下线**（信任叙事冲突）|
| M10 控制台与 i18n | 全套 Web UI + 五语言 | 保留直用 |
| M11 部署与运维 | 单二进制/Docker/TLS | 保留 = V2 Team 档形态；P3 增 Enterprise 档 |

### V1 实际数据表清单

> V1 使用 SQLite；以下是最终 schema 中的 **18 张业务表**，不含迁移运行器维护的 `schema_migrations`。字段级事实和 V2 增量设计见 [数据库设计：V1 基线与 V2 增量](../architecture/数据库设计-V1基线与V2增量.md)。

| # | 业务域 / 对应模块 | 数据表 | 用途 | 关键关联或注意点 |
|---|---|---|---|---|
| 1 | 账号与鉴权 / M4 | `users` | 用户、余额、消费累计、登录会话、Stripe 映射、团队归属与个人覆盖开关 | `team_id → teams`；magic/session token 明文存储是 P0 安全缺陷 |
| 2 | 账号与鉴权 / M4 | `api_keys` | `gw-` 网关 API Key 的哈希、状态、软删和 key 级 WASM 绑定 | `user_id → users`；无 key 级模型白名单 |
| 3 | 团队治理 / M4、M6 | `teams` | 管理员创建的单层团队及团队级 WASM 文件名 | 名称全局唯一；V2 挂 org 后需改为 org 内唯一 |
| 4 | 计量与审计 / M5、M8 | `usage_records` | 每个成功请求的用量、成本、耗时、上游状态、channel/团队归因 | 关联 `api_keys`、`users`、`routing_channels`；`request_id` 列实际未写入 |
| 5 | 余额账本 / M5 | `balance_transactions` | 用户余额变动、Stripe 充值关联和收据 | `user_id → users`；用户付款记录是此表的过滤视图，不是独立表 |
| 6 | 系统信用池 / M5 | `system_credit_transactions` | 配额+信用池编译形态下的全局信用池账本 | 全局单池，无用户分配；`stripe_session_id` 兼作幂等键 |
| 7 | 个人配额 / M6 | `user_quotas` | 用户级花费上限和滑动窗口规则 | 用户加入团队后可由 `quota_override` 决定是否覆盖团队规则 |
| 8 | 团队配额 / M6 | `team_quota_rules` | 团队级花费上限和滑动窗口规则 | `team_id → teams`；成员默认继承 |
| 9 | 个人模型治理 / M6 | `user_allowed_models` | 用户可使用的模型白名单 | 空集默认全允许；`__deny_all__` 才代表全拒 |
| 10 | 团队模型治理 / M6 | `team_allowed_models` | 团队可使用的模型白名单 | 空集代表全拒；与个人表的空集语义相反，属于既有设计风险 |
| 11 | 上游目录 / M3 | `providers` | provider 实例、类型、端点、区域、协议能力和凭证轮换策略 | 被模型与凭证配置共同使用 |
| 12 | 平台凭证池 / M3 | `provider_credentials` | 平台 API Key、OAuth、AWS 凭证、权重和启停状态 | 只有平台全局归属；无 BYOK 用户归属，且秘密字段明文存储 |
| 13 | 模型目录与定价 / M3、M5 | `models` | 逻辑模型、上游模型名、上下文、token/多模态/阶梯定价与协议元数据 | config 为权威来源，启动时 reconcile 入库；价格非负由触发器约束 |
| 14 | 模型别名 / M2 | `model_aliases` | legacy 源模型名到目标模型名的改写 | 无 channel 归因，是旧回退路径 |
| 15 | 供给路由 / M2 | `routing_groups` | 逻辑模型的候选池、选路策略、重试和健康策略 | 仅管理员配置的供给侧路由，不是 V2 用户质量路由 |
| 16 | 供给路由 / M2 | `routing_channels` | 路由组内的候选模型、权重、优先级和 channel RPM 上限 | `group_id → routing_groups`；`upstream_model` 实际存 `models.name` 字符串，非真正上游模型 ID |
| 17 | 渠道健康 / M2 | `channel_health` | 按凭证保存探测时间、状态、P50 延迟和错误率 | `provider_credentials_id` 为主键；不含吞吐指标 |
| 18 | 系统状态 / M11 | `gateway_state` | 通用 KV | 生产实际只使用 `system_credits_balance_microdollars`；不应扩张成业务真相来源 |

**不是数据表的存储/状态**：请求日志写入 `request_logs/{user}/{key}/requests.jsonl`；WASM 模块保存为文件、表中只存文件名；RPM、轮询与熔断计数在进程内存；管理员会话也没有独立表。这些状态在 V2 设计中不能被误判为可直接迁移的关系数据。

## 二、M2 路由与容灾模块

| 编号 | 需求 | 实现位置 |
|------|------|---------|
| V1-M2-1 | 管理员配置的路由组：逻辑模型名 → 多候选上游 channel（routing_groups/routing_channels） | proxy/routing.rs |
| V1-M2-2 | 五种选路策略：single / weighted_random / round_robin / lowest_latency / fallback | 同上 |
| V1-M2-3 | channel 级 RPM 上限，达限自动跳下一优先级 | proxy/rpm_tracker.rs |
| V1-M2-4 | 故障转移：可重试状态码（5xx/401/408/429）沿 failover 链轮换凭证与 channel，max_retries 封顶 | proxy/retry.rs、dispatch.rs |
| V1-M2-5 | fallback 熔断冷却（fallback_cooldown_secs） | proxy/routing.rs |
| V1-M2-6 | 后台健康探测循环，按凭证写 channel_health（p50 延迟/错误率） | proxy/health_probe.rs |
| V1-M2-7 | legacy 模型别名重写（model_aliases，无 channel 归因的回退路径） | proxy/routing.rs |

**已知缺陷**：failover 无退避 jitter；熔断无 open/half-open 状态机；失败类型不分语义（容量/能力/内容策略同链）（→ P2#5）。**边界**：V1 路由全部是供给侧 + 管理员配置，无任何用户侧质量路由。

## 三、M3 上游与凭证模块

| 编号 | 需求 | 实现位置 |
|------|------|---------|
| V1-M3-1 | 约 35 种 provider_type，覆盖 OpenAI 兼容 / Anthropic / Responses / Gemini / 媒体专用四类 wire | config.rs |
| V1-M3-2 | 订阅型上游：Claude Code / Codex / Copilot / Kiro / GLM Coding Plan 当凭证，OAuth token 自动刷新 | proxy/claude_code.rs、kiro.rs、token_refresh.rs |
| V1-M3-3 | AWS 系上游：SigV4 签名 + eventstream 解析（Bedrock/Bedrock-Claude/Bedrock-OpenAI） | proxy/aws_sigv4.rs、aws_eventstream.rs、bedrock.rs |

| V1-M3-5 | providers/models 目录 config 权威、启动时 reconcile 进 DB；模型完整定价（分桶 token 价 + 多模态计价 + 阶梯） | proxy/config_seed.rs |

**边界**：凭证只有平台全局维度，**无用户归属（BYOK 不存在）**（→ P1#4）。

## 四、M4 鉴权与账号模块

| 编号 | 需求 | 实现位置 |
|------|------|---------|
| V1-M4-1 | 网关 API key（`gw-` 前缀，SHA-256 哈希存储）发放/停用/软删，key 级 WASM 绑定（模型白名单在用户/团队级，见 M6，无 key 级白名单） | middleware/auth.rs、routes/keys.rs |
| V1-M4-2 | magic-link 注册/登录（Resend 邮件），gw_session cookie 会话 | routes/auth.rs |
| V1-M4-3 | 管理员会话（admin 密码 → cookie），注册开关配置 | routes/admin.rs |

**已知缺陷（高危，→ P0#2）**：admin 密码 SHA-256 非 Argon2id 且 `==` 比较；session token 明文存库；cookie 缺 Secure/`__Host-`；零 CSRF。**边界**：有团队维度（治理归 M6，见 V1-M6-4/5），但无 org/workspace 层级、无角色化 RBAC，团队亦无自助管理入口（成员分配/规则全部由管理员操作）（→ P3#1）。

## 六、M6 配额与准入模块

| 编号 | 需求 | 实现位置 |
|------|------|---------|
| V1-M6-1 | 用户级花费配额窗口（limit_amount/window_seconds，超限 429） | quota.rs |
| V1-M6-2 | 座位上限 max_seats（quota 模式控制新用户创建） | 同上 |

| V1-M6-4 | 团队（teams）：管理员建团队、分配成员；团队级配额规则（team_quota_rules）与模型白名单（team_allowed_models）；成员默认继承，可按人独立覆盖配额、模型两个维度 | db/teams.rs、templates/admin_teams_pages.rs |

## 七、M7 WASM 插件模块

| 编号 | 需求 | 实现位置 |
|------|------|---------|

## 十二、V1 基线小结

- **需求总数 54 条**，其中在 V2 中「保留直用」约 38 条、「保留但需改造」约 12 条（含团队治理 M6-4/5，将被 P3 多租户 RBAC 重构吸收）、「默认下线」3 条（M9）、「机制降级」1 条（M7 链）。
- **V1 的产品性缺口**（不是缺陷，是定位差异）：全部配置权在管理员、无用户侧质量路由、无 BYOK、多租户只到团队一层（无 org/RBAC/自助管理）、无路由透明——这正是 [V2 阶段需求清单](./V2阶段需求清单.md) 的增量主体。
- **7 项高危缺陷**全部收口在 V2 开发计划 P0 期（[规范审计 §二](../architecture/cloud-ai-gateway开发规范符合性审计.md)）。
