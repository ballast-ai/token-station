# 企业订阅凭证归集：把成员订阅接成网关上游

> 场景：企业购买 N 个成员订阅（Claude Code / Codex / Copilot 等），汇入自己控制的[私有部署网关（交付物②）](./业务模式与定价划分.md#零核心结论七个模式收敛为三个交付物)，内部成员经统一端点使用；token-station 收 license / 席位费，**不对外提供、不赚 token 价差**。
>
> 整理日期 2026-07-09。上位文档：[业务模式与定价划分](./业务模式与定价划分.md)（交付物②与 Team/Enterprise 档）、[token-station 功能需求清单 §六](./token-station功能需求清单.md)（计费口径）。
>
> **本文的核心主张只有一句**：这不是一个新原语，而是 [V2-P1-7「自带订阅」并入 BYOK](../planning/V2阶段需求清单.md) 在组织尺度上的展开；它的成败**不取决于能不能做出来，而取决于额度是否可跨成员互换**（§二）。

---

## 零、先划清它不是什么

「订阅凭证转 API」这个动作，在市场上有四种做法，法律与信任后果天差地别。本文只涵盖第 ④ 种。

| # | 做法 | 谁的账号 | 卖给谁 | 是否赚价差 | 本文是否涵盖 |
|---|------|---------|--------|-----------|------------|
| ① | 平台采购订阅账号池，对外以 API 转售 | 平台的 | 第三方 | ✅ 是 | ❌ **明确排除** |
| ② | 用户把自己的订阅凭证托管给我方 SaaS 网关 | 用户的 | 用户自己 | ❌ 否 | 🟡 相邻（=服务端 BYOK，[V2-P1-4](../planning/V2阶段需求清单.md)） |
| ③ | 个人客户端绑定自己的订阅作上游 | 用户的 | 用户自己 | ❌ 否 | 🟡 相邻（=[V2-P1-7](../planning/V2阶段需求清单.md)） |
| ④ | **企业把自购的成员订阅汇入自有私有网关，供内部成员用** | 企业的 | 企业自己的员工 | ❌ 否 | ✅ **本文** |

**排除 ① 的理由不是道德，是产品自洽性。** [TeamoRouter 竞品调研 §五.3](../research/TeamoRouter-竞品调研.md) 已经论证：中转站的转售差价模型与「让用户独立核验账单」天然冲突——费率随上游成本浮动，用户无从核账。而「本地独立计量 + 对账命令可独立核验平台账单」是 [个人模式本地客户端需求 §零](./个人模式本地客户端需求.md) 明写的**三重商业角色之一（信任资产）**。做 ①，等于亲手拆掉自己的信任资产。

④ 不赚价差，所以对账逻辑不破；请求从企业控制的网关发出，所以 L2 不破。**这是四种里唯一与既有承诺自洽的。**

## 一、能力定义

在交付物②（私有部署网关）内，允许**订阅凭证**与 API key 一样，作为一类上游凭证被注册、绑定与路由。

- 凭证类型：Claude Code / Codex / Copilot 等厂商的**订阅授权凭证**（通常经该厂商官方客户端的 OAuth 流程取得），而非 API key；
- 凭证归属：**企业**（由企业为其员工购买），存放在企业自己控制的网关服务器上；
- 使用方式：成员经网关的统一 OpenAI 兼容端点发起请求，网关按成员身份选择凭证并转发；
- 计费：token-station 按 **license / 席位**收费（[业务模式 §四](./业务模式与定价划分.md#四交付物-team-vs-enterprise-license-差异设计2026-07-08-拍板初版)、[§五](./业务模式与定价划分.md#五人数档位是收费口径不是架构分界2026-07-08-拍板)），**不参与 token 结算**。这与[功能需求清单 §6.1](./token-station功能需求清单.md#61-唯一交汇点路由到-glm5-2-platform-时怎么结算) 的**方式 B（用户 BYOK，token-station 只收路由服务费）**是同一条账路。

**不新增原语。** 它复用的是已有的四条需求：

| 既有需求 | 在本能力中的角色 |
|---|---|
| [V2-P1-4](../planning/V2阶段需求清单.md) 服务端 BYOK：凭证托管给网关，归属用户/租户 | 凭证托管与加密保管机制 |
| [V2-P1-5](../planning/V2阶段需求清单.md) BYOK 三态 fallback：always-use / fallback / 默认回退 | 订阅额度耗尽后是否允许回退到企业的 API key |
| [V2-P1-6](../planning/V2阶段需求清单.md) 双账路结算：代采购转卖 or 仅收路由服务费 | 本能力**只走后者**，前者在此场景下不得启用 |
| [V2-P1-7](../planning/V2阶段需求清单.md) 「自带订阅」并入 BYOK 模型 | 本能力就是它的组织尺度版本 |

> ⚠️ **勿与「上游④企业网关」混淆**。[个人模式本地客户端需求 §一](./个人模式本地客户端需求.md#一三类当前上游--一类远期观察2026-07-08-四次修订) 把「个人客户端内挂企业网关」降为**远期观察项**。那说的是「个人客户端把企业网关当上游」；本文说的是「企业网关把成员订阅当上游」。方向相反，互不依赖，本能力不受该降级影响。

## 二、决定生死的设计岔路：凭证绑定 vs 额度池化 ⚠️

**成员 A 的请求，消耗的是谁的订阅额度？**

这个问题看起来是实现细节，实际决定了这个能力是「企业软件」还是「账号共享工具」。

| | **方案 甲：凭证绑定**（推荐） | **方案 乙：额度池化** |
|---|---|---|
| 机制 | 网关按成员身份绑定其**本人**的订阅凭证；A 的请求只走 A 的凭证 | 凭证进池子，按可用额度 / 轮询 / fallback 派单；A 的请求可能消耗 B 的额度 |
| 网关角色 | 路由 + 观测 + 审计层 | **额度池** |
| 协议性质 | 每个成员使用自己获授权的订阅 | **跨账号共享订阅额度** |
| 厂商条款 | 可辩护（见 §五.1 的未决项） | 消费级订阅条款普遍禁止 |
| 席位归属 | 清晰：每条请求可归因到具体成员与其凭证 | **破坏**：用量与成本无法归因 |
| 对账 | 成立：每席位用量可与厂商账单逐项核对 | 不成立：厂商侧只见账号，不见成员 |
| 封号影响 | 单个成员凭证失效，其余不受影响 | **全池连坐**，企业供给瞬间归零 |
| 超额行为 | A 用超了就是 A 用超了，配额治理可用 | A 用超了烧的是 B 的额度，配额治理失效 |

### 拍板建议

**默认且唯一实现方案甲。方案乙不做。**

三条理由，按重要性排序：

1. **责任性质不同。** 中转站做池化，被封号是它自己死。我们做池化，是把「账号共享」这个风险**打包成企业软件，卖给有法务部门的客户**。客户被封号时，合同责任在我们。这不是更轻的风险，是更重的。
2. **它砸掉本能力自己的卖点。** 企业买网关买的是**归属、配额、审计**（[业务模式 §四](./业务模式与定价划分.md#四交付物-team-vs-enterprise-license-差异设计2026-07-08-拍板初版) 的 Enterprise 档整列都是这些）。池化恰好把归属打散——用量归不到人、配额管不住人、审计查不到人。**为了省订阅费而砸掉治理，是本末倒置。**
3. **它与对账承诺冲突。** 池化后厂商账单只显示账号级用量，企业无法把它 diff 到成员。而对账是我们的信任资产。

> 若未来确有客户要求池化，正确的做法是**显式开关 + 合同免责 + 产品内明示警告**，而非默认行为；且必须在文档中与「凭证绑定」严格区分命名，不得混称为「订阅归集」。

### 一个反向的产品洞察

开源竞品 [AIClient2API](../research/AI编码工具配置切换器竞品全景.md)（8,401★，GPL-3.0）的核心特性正是**多账号轮询 + 跨类型 fallback 链**——也就是方案乙。它对个人套利用户是特性，**对企业是缺陷**。

**把它的核心特性反过来做（绑定而非轮询），才是企业形态。** 这是本能力真正的差异化所在，而不是「能把订阅转成 API」——后者已被开源商品化（§四）。

## 三、计费口径

| 项 | 口径 |
|---|---|
| token-station 收什么 | Team / Enterprise **license + 席位费**（[业务模式 §四/§五](./业务模式与定价划分.md)） |
| token-station 不收什么 | **不按 token 计费、不加价、不代采购转卖** |
| 依据 | [功能需求清单 §六](./token-station功能需求清单.md) 原则「谁看得见请求，谁才能按量收费」——请求从企业网关发出，平台看不见，故不参与按量结算 |
| 对应账路 | [§6.1 方式 B](./token-station功能需求清单.md#61-唯一交汇点路由到-glm5-2-platform-时怎么结算)（用户 BYOK，token-station 仅收路由服务费，0 费率亦可配） |
| 明确禁止 | 在本场景启用 [V2-P1-6](../planning/V2阶段需求清单.md) 的「平台代采购转卖」账路 |

订阅费直接由企业付给模型厂商，token-station 不在这条资金链上。**这正是它能同时保住 L2 与对账的原因。**

## 四、竞品参照：原语已商品化，差异化不在这里

「订阅额度转 API」这个原语在开源世界已经免费可得（详见 [AI 编码工具配置切换器竞品全景](../research/AI编码工具配置切换器竞品全景.md)）：

| 项目 | ★ | 相关能力 |
|---|---|---|
| AIClient2API | 8,401 | 把只能在客户端用的订阅额度封装成本地 OpenAI 兼容接口；多账号轮询、跨类型 fallback 链 |
| CCS | 2,675 | 支持 Codex / Kiro / Claude / Kimi 的 OAuth 登录，用订阅额度而非 API key |
| cc-switch-cli | 4,074 | 托管 OAuth 账号复用 |

**结论：不要把「支持订阅凭证作上游」当卖点写进销售材料。** 它是入场券。

可辩护的差异化只有三项，且全部建立在方案甲之上：

1. **凭证与成员身份的强绑定**（归属可追溯）；
2. **审计线索**（管理操作审计、日志导出 / SIEM，Enterprise 档已规划）；
3. **对账**（席位用量 vs 厂商账单逐项 diff）。

## 五、风险与未决事项

### 5.1 ⚠️ 厂商条款未核实（阻塞项）

本文所有「方案甲可辩护 / 方案乙被禁止」的判断，依据的是**行业常识，不是引证**。截至 2026-07-09，**我方尚未核对 Anthropic、OpenAI、GitHub 三家当前订阅条款的原文**。

必须在本能力进入 V2 计划前完成：

- 逐条抓取三家条款原文，重点看「账号共享 / seat 转让 / 程序化访问 / 企业代持成员账号」的表述；
- 注意 **Claude 的 Max 订阅与 Team 订阅口径不同**，不能混为一谈；
- 注意条款会变，需记录抓取日期与版本，并纳入定期复核。

**在此之前，本文的合规结论不得写入任何对外销售材料。**

### 5.2 技术脆弱性：OAuth 客户端身份

订阅额度通常只能经厂商**官方客户端的 OAuth 流程**取得。网关要使用它，就得以官方客户端的身份出现。

这正是 [Veridrop 与 CISPA 论文](../research/TeamoRouter-竞品调研.md#三-一手证据本人经-github-api--whois-直接核实2026-07-09)所检测的「逆向 / 冒充客户端端点」类别。含义：

- **能跑，但不稳。** 厂商随时可以通过客户端指纹、证书绑定、请求签名等手段掐断；
- **掐断时企业供给瞬间归零**，且无降级路径（除非配了 [V2-P1-5](../planning/V2阶段需求清单.md) 的 fallback 到企业 API key）；
- 这条风险**必须写进企业合同的责任划分**，不能藏在文档里。若我们承诺 SLA，就要为一个我们不控制的授权通道背书。

**建议**：将「订阅凭证上游」在产品内标注为 **best-effort 通道**，SLA 只覆盖 API key 上游；并默认开启 fallback 到企业 API key。

### 5.3 其他

| 风险 | 说明 |
|---|---|
| 席位与订阅数不匹配 | 企业买 20 个订阅、30 个席位，方案甲下必然有 10 人无凭证可用——产品需明确此时的行为（拒绝 / fallback / 提示） |
| 成员离职 | 凭证轮换与吊销策略（Enterprise 档已有「key 到期与轮换策略」，需覆盖订阅凭证） |
| 凭证加密保管 | 复用 [V2-P1-4](../planning/V2阶段需求清单.md) 的服务端 BYOK 加密保管机制；须在管理界面明示「此凭证由网关加密保管」 |
| 隐私文案 | [V2-NF-2](../planning/V2阶段需求清单.md) 已要求「服务端 BYOK 必须在 UI、隐私文案与审计记录中与客户端本地 BYOK 显式区分」，订阅凭证同此约束 |

## 六、验收要点（V2 清单条目草案）

供后续并入 [V2 阶段需求清单](../planning/V2阶段需求清单.md)，编号待定：

| 需求 | 等级 | 验收要点 |
|------|------|---------|
| 订阅凭证作为一类上游凭证注册与加密保管 | 🟡 | 管理员可为成员录入订阅凭证；界面明示由网关加密保管 |
| **凭证与成员身份强绑定**（方案甲） | 🔴 | 成员 A 的请求只能消耗 A 绑定的凭证；无绑定则按配置拒绝或 fallback，**任何情况下不得消耗他人凭证** |
| 决策记录含凭证归属 | 🔴 | 复用 [V2-P1-1](../planning/V2阶段需求清单.md)：每请求决策记录中「最终凭证」可归因到成员 |
| 订阅上游标注为 best-effort | 🔴 | 产品内与合同中明示不覆盖 SLA；默认开启 fallback 到企业 API key |
| 席位用量可导出并与厂商账单 diff | 🟡 | 支撑对账；厂商侧账单接口可得时纳入 |
| 凭证吊销与轮换 | 🟡 | 成员离职后凭证即刻失效 |
| **不得启用代采购转卖账路** | 🔴 | 本场景下 [V2-P1-6](../planning/V2阶段需求清单.md) 的转卖模式在配置层不可选 |
