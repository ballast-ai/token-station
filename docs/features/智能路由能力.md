# 智能路由能力：简单请求给便宜模型，复杂请求给 SOTA

> 场景：**三种服务模式（个人 / 企业·小 Team / 平台）都要支持 OpenFugu 式智能路由 + 用户自定义切换规则**
> 核心结论：**路由能力分四层叠加——用户规则最高优先、客户端 hint 次之、学习型路由器兜底、级联仅限非流式场景。且三种模式不能共用同一套路由器：BYOK/企业模式的路由决策必须在本地/企业边界内完成，否则隐私承诺（L2）即破；只有平台模式有资格养学习型路由器的数据飞轮。**
>
> 整理日期 2026-07-05。配套：[glm-5.2-服务模式定位.md](../../../glm5.2-platform/docs/business/glm-5.2-服务模式定位.md)（三种模式与隐私梯度的定义）、[glm-5.2-计费接入架构.md](../../../glm5.2-platform/docs/architecture/glm-5.2-计费接入架构.md)（网关准入与溢出，路由是其中的模式映射环节）。

## 零、参照系：OpenFugu 是哪一档

[OpenFugu](https://github.com/trotsky1997/OpenFugu) 是对 Sakana Fugu 的开源复刻：对外只暴露一个 OpenAI 兼容端点，内部用一个训练出来的小型路由器（Conductor）按 query 把请求分发到一池前沿模型。它属于下文方法谱系的第 ③ 档（学习型小模型路由器），其 query 级路由声称比池内最强单模型还高 ——

> **路由的目标函数不只是「难度分档省钱」，还有「每域最优提质」**：不同模型各有擅长域，路由器选对模型可以同时省钱和提高质量。这是超出「简单给便宜、复杂给 SOTA」框架的一个补充视角。

## 一、方法谱系：六类实现路径

按「确定性 → 学习型」「事前判断 → 事后验证」排列。

### ① 静态规则路由（用户自定义规则的载体）

用户写声明式规则，网关/客户端按优先级匹配，命中即终止：

```yaml
rules:
  - match: { context_tokens: ">32k" }          → glm-5.2        # 长上下文给自营
  - match: { tools_present: true }             → claude-sonnet   # 带工具调用给强模型
  - match: { endpoint: "/summarize" }          → cheap-pool
  - match: { keywords: ["证明","推导","架构"] }  → sota-pool
  - default:                                    → glm-5.2
```

可用匹配维度：请求 token 数、是否含代码块/数学、是否带 tool 定义、是否要求 JSON schema 输出、会话轮数、客户端声明的任务类型 header、时间段/预算余量。

- **优点**：零延迟、零成本、行为可预期、可审计——企业客户最信这个。
- **缺点**：只能捕捉表层特征，「看起来短但很难」的请求会漏。
- **定位**：「让用户自己设定切换规则」的直接实现，**必须做，且永远是最高优先级层**。

**交付形态：规则应服务端集中管理，而非散在客户端 header（借鉴 OpenRouter Presets）**

上面的规则若只能靠客户端每请求传 header 表达，用户改一次策略就得动一次代码，且规则散落无从审计。更好的形态是把「模型选择 + 生成参数 + provider 偏好 + 上述路由规则」打包成一个**服务端命名配置（Preset）**，客户端用一个别名引用整套策略：

```
model: "@preset/code-review"     # 引用「代码审查」这套预设：默认 sota-pool、带 tool 给 claude、长上下文给 glm-5.2
```

- 用户在仪表盘创建/修改/**版本化**预设，客户端代码不动即可切模型、改参数、调路由偏好——「应用代码与路由配置解耦」；
- Preset 天然是**套餐差异化载体**：低档套餐对同一别名解析出偏便宜的档位，Pro 档解析出可调的完整策略（与后文 [四·2 阈值套餐参数化](#四产品化细节) 同一逻辑）；
- 与第 2 层的**模型语义别名**（`fast/smart/cheap`，plano 范式）是同一思路的两种粒度：语义别名是「单个模型的抽象引用」，Preset 是「一整套路由策略的抽象引用」。

> 这一形态取自 OpenRouter Presets 与 Portkey Conditional Routing 的产品实践，详见 [闭源商业token服务功能面调研 §1.3](../research/闭源商业token服务功能面调研.md)。它同时解决了 [路由透明与用户信任](./路由透明与用户信任.md) 的「可覆写兜底」——用户覆写路由决策，本质就是编辑自己的 Preset，改动可见、可回退、可审计。

### ② 启发式打分（规则的连续版）

不做硬匹配，给每个请求算复杂度分：

```
score = f(长度, 代码密度, 约束数量, 推理动词, 会话深度, 历史重试次数)
```

超阈值给 SOTA。比规则平滑，仍然零模型成本。适合作规则层的兜底默认策略。

### ③ 小模型分类器路由（OpenFugu / RouteLLM 这一档）

训练一个小模型（BERT 级或 embedding + 浅层网络），预测「弱模型能不能答好这个 query」：

| 实现 | 思路 | 关键数据 |
|------|------|---------|
| [RouteLLM](https://github.com/lm-sys/routellm)（LMSYS） | 用 Chatbot Arena 偏好数据训练，预测强/弱模型胜率差，**一个阈值旋钮直接调「成本 vs 质量」** | 论文数据：保持 95% GPT-4 质量省 ~85% 成本 |
| OpenFugu Conductor | query 级路由到模型池，「每域最优」而非单纯难度分档 | 声称超过池内最强单模型 |
| embedding kNN | query 向量化，在「历史上哪个模型答好过哪类问题」标注库找近邻 | 冷启动简单，随数据积累变准 |

- **优点**：单次推理 <10ms、成本忽略不计、能捕捉语义级难度。
- **缺点**：需要训练数据（冷启动难）、分布外请求不可靠、需持续再训。

### ④ LLM-as-Router（便宜大模型当调度员）

拿便宜快模型（自营 GLM 小档或 Haiku 级）先做一次分类调用：「这个请求的难度/领域/建议模型是什么」。

- **优点**：零训练、prompt 即策略、用户甚至能自己改路由 prompt。
- **缺点**：每请求多 100–300ms 和一次调用成本，分类器自己也会判错。
- **定位**：③ 的冷启动替身，数据攒够后换成 ③。

### ⑤ 级联 / Cascade（事后路由，FrugalGPT 路径）

前四种是「先猜难度再派单」（pre-hoc），级联反过来：**先让便宜模型答，再判断答得行不行，不行升级到 SOTA**。判断信号：

1. **logprob / 熵**：便宜模型输出的平均置信度。⭐ **自营 GLM-5.2 拿得到完整 logprobs，这是自营算力相对纯 API 转售的独特优势**——纯官方 API 用户拿不到这个信号；
2. **自一致性**：便宜模型采样 2–3 次，答案不一致 → 升级；
3. **可验证任务直接验证**：代码跑测试、数学验算、JSON 校验 schema，失败即升级；
4. **小验证器模型**打分。

- **优点**：难度是实测的不是预测的，准确率上限最高。
- **缺点**：升级时延迟翻倍；流式 UX 很难做（吐了一半发现不行怎么办）；计费要想清楚失败的那次便宜调用谁付。
- **定位**：适合非流式、批处理、agent 内部步骤；**不适合聊天首响应**。

### ⑥ 会话 / Agent 级路由（按步骤而非按请求）

agent 场景里难度天然由**步骤类型**决定：规划/架构给 SOTA，执行/改文件给中档，摘要/标题/意图识别给最便宜的（Claude Code 自己就是这么干的）。

**架构含义**：客户端（个人模式）比网关更知道「这是 agent 的第几步、什么类型的步骤」，所以这一层路由应做在**客户端/SDK 里，把 hint 通过 header 传给网关**，网关规则层消费这个 hint。

## 二、关键约束：三种模式不能用同一套路由器

**路由器本身也在数据路径上**——这是服务模式定位下最重要的推论：

| 模式 | 隐私约束 | 可用方法 | 数据飞轮 |
|------|---------|---------|---------|
| **个人（本地客户端）** | BYOK 直连承诺「内容不经平台」→ **路由决策必须在本地完成**，不能把内容发给云端分类器 | ①② 本地执行 + ③ 的**本地小模型**（几十 MB，随客户端本体分发）+ ⑥ | 默认无；仅用户开启云同步时上传元数据白名单 |
| **企业 / 小 Team（闭源网关）** | 内容不出企业出口 → 路由器跑在企业网关内 | ①②⑥ + ③（模型文件随 license 分发、定期更新）+ ⑤（企业自己付双份调用） | 企业内部可选 |
| **平台（SaaS）** | 内容本来经过平台 | 全部 ①–⑥，且**只有平台模式有资格养学习型路由器** | 有——但受「不用内容训练」承诺约束 |

两个尖锐点：

1. **如果个人 BYOK 模式的路由用了云端分类器，L2 隐私承诺就破了。** 路由分类器看 query 全文 = 内容经过平台。所以个人本地客户端里的智能路由只能是：本地规则 + 本地启发式 + 内嵌本地小分类器。客户端已按开核开源执行（Apache-2.0，2026-07-09 口径统一）——路由引擎与同步路径源码公开、可复现构建，「内容不出设备」可被任何人验证；网络边界、同步字段白名单、本地审计输出与离线可用保留为纵深验收（见[个人模式本地客户端需求 §二](./个人模式本地客户端需求.md#二密钥边界平台批发-key-永不下发到本地)）。
2. **平台的数据飞轮和「不用用户内容训练」条款冲突。** 三条出路：
   - 只用**元数据**训练（token 数、任务类型、用户是否点了重试/重新生成——不含内容）；
   - **opt-in 换折扣**（愿意贡献路由训练数据的套餐便宜 10%）;
   - 只用平台自有合成/公开数据（RouteLLM 就是拿 Arena 公开偏好数据训的）。

   **条款里要提前留好口子，别等做飞轮时发现自己承诺死了。**

## 三、落地方案：四层叠加，按序上线

```
第 1 层  用户规则（①）          ← 命中即终止，用户主权最高
第 2 层  客户端/Agent hint（⑥） ← header 声明步骤类型
第 3 层  学习型路由（③）        ← 冷启动期用启发式 ② 或 LLM 判官 ④ 顶替
第 4 层  级联兜底（⑤）          ← 仅非流式 / agent 内部步骤 / 特定套餐开启
```

上线顺序：

| 阶段 | 内容 | 说明 |
|------|------|------|
| 1 | **① 规则 + ② 启发式先行** | 周级工作量，覆盖 ~70% 价值，企业可审计 |
| 2 | ④ LLM 判官顶替冷启动 | prompt 即策略，快速验证路由收益 |
| 3 | 攒数据后训 ③ 替换 ④ | 平台模式先行；蒸馏出本地小模型分发给个人本地客户端和闭源网关 |
| 4 | ⑤ 级联仅限批处理与 agent 场景 | 结合自营 GLM logprob 信号 |

> 不要一上来就对标 OpenFugu 的 Conductor——它的前提是有训练数据和评测基建，那是第 3 阶段的事。

## 四、产品化细节

1. **路由要出现在账单上**：每条请求记录「路由决策原因 + 实际模型 + 如果没路由会花多少」，让用户看到「本月智能路由为你省了 $X」。**省钱不可见就等于没省**，这是订阅续费的关键展示位。
2. **阈值做成套餐参数**：RouteLLM 式单旋钮（0 = 全便宜，1 = 全 SOTA）天然适合分层订阅——低档套餐旋钮偏便宜侧，Pro 档用户自己调。**路由策略本身是套餐差异化维度，而不只是后台成本优化。**
3. **路由决策可解释、可覆写**：任何一条请求，用户都能看到为什么路由到该模型，并能用 ① 层规则强制覆写——这是对「智能路由判错」的用户侧兜底。
