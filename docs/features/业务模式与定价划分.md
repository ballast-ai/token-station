# 业务模式与定价划分

> 场景：收口 token-station 的业务场景划分——原始素材（todo.md 草稿）列出七种模式，本文将其收敛为**三个交付物 × 三条数据路径 × 两档 license**，并拍板个人形态的管理面口径（控制面在云端、数据面在本地）与 Team / Enterprise 的差异设计。
>
> 整理日期 2026-07-08。上位文档：[token-station 功能需求清单 §十一](./token-station功能需求清单.md#十一企业--部署--🟡-归-token-station独立交付)（企业/部署功能面）。姊妹文档：[个人模式本地客户端需求](./个人模式本地客户端需求.md)（个人形态的完整需求，本文 §三对其 §四 有一处修订，见 §七同步表）。隐私梯度 L1/L2/L3 术语沿用既有口径（L1 平台可见并计费 / L2 元数据可见内容不可见 / L3 零外发）。

## 零、核心结论：七个"模式"收敛为三个交付物

原始草稿的七种模式（个人模式 / 个人服务版 / 小团队私有 / 企业私有 / 个人平台租用 / 小团队平台租用 / 大团队平台租用）实为两个正交维度的笛卡尔积：**部署位置**（本地 / 自有服务器 / 平台代租 / 平台共享端点）×**用户规模**（个人 / 小团队 / 大团队）。按积展开会导致 SKU 爆炸且相互矛盾。

按**数据路径**归并，全部场景只有三种，对应三个交付物：

| 交付物 | 数据路径 | 隐私等级 | 覆盖原草稿的模式 | 商业形态 |
|--------|---------|---------|----------------|---------|
| **① 本地客户端** | 请求从用户本机发出，直连官方 API / 本地模型 / 平台端点 | L2 / L3 / L1（按上游） | 个人模式、个人服务版 | 免费、开核开源（Apache-2.0，注册解锁云功能的漏斗 + 转化触点，见客户端需求 §零/§五，2026-07-09 口径） |
| **② 私有部署网关** | 请求从一台客户控制的网关服务器发出，直达官方 API | L2（对 token-station 平台而言） | 小团队私有、企业私有、个人/小团队平台租用 | Team / Enterprise 两档 license 订阅（§四）；托管选项另收托管费（§六②） |
| **③ 平台 SaaS 端点** | 请求从 token-station 平台端点发出，平台保障数据归属与使用权 | L1 | 大团队平台租用 | 平台订阅 / credits 按量 |

三条收敛判定（2026-07-08 拍板）：

1. **"个人服务版"不是独立模式**——与个人模式是同一个本地程序（CLI + API 端口），区别仅是跑在桌面还是 headless 服务器上，管理面统一在云端（§三），降级为交付物①的一行部署说明。
2. **"平台租用"不是独立模式**——"自有服务器"与"平台代租服务器"跑的是同一个交付物②镜像，区别只是谁执行部署、谁负责运维，是交付物②的**托管选项**（managed hosting），不是第四个产品。**2026-07-08 拍板：托管选项进第一版商业范围**（§六②），定价为 license 费之上另收托管费。
3. **"大团队平台租用"名实不符**——其定义（请求从平台端点发出）就是共享 SaaS，正名为交付物③；"租用"一词保留给交付物②的托管选项。

## 二、三个交付物的边界

- **①本地客户端**：完整需求见[个人模式本地客户端需求](./个人模式本地客户端需求.md)（三类当前上游 + 企业网关远期观察、密钥边界、指标库与云同步、开核开源与注册解锁云功能），本文不重复；仅 §三修订其管理面口径。
- **②私有部署网关**：多成员共用的 OpenAI 兼容网关，部署在客户控制的服务器上；Web 管理界面**随部署包走**（跑在客户自己的服务器上），不依赖 token-station 云端——企业买私有部署买的就是"不依赖你"，Enterprise 档支持完全离线（air-gap）激活（§四）。功能面对应[功能需求清单 §五/§十一](./token-station功能需求清单.md)。
- **③平台 SaaS 端点**：token-station 托管的多租户端点，自有完整计费体系（credits / 订阅，见功能需求清单 §六），面向偏好轻量接入、接受 L1 的用户；平台以合同与制度保障数据归属和使用权。

三个交付物共享同一路由内核（质量侧四层路由 + 路由透明，见[智能路由能力](./智能路由能力.md)与[路由透明与用户信任](./路由透明与用户信任.md)）；内核代码落点为开源仓 `crates/router-core`（2026-07-09 开核口径，见[代码仓库规划](../architecture/代码仓库规划.md)）。

## 三、个人形态管理面：控制面在云端、数据面在本地（2026-07-08 拍板）

> 本节修订[个人模式本地客户端需求 §四](./个人模式本地客户端需求.md)的"命令行是唯一本地管理面"：命令行仍是唯一**本地**管理面（本地无 Web 界面的拍板不变），但云端平台网页从"仅查看用量报表"扩展为**可管理非机密配置**。

口径：

- 本地（含 headless 的个人服务版形态）只有 CLI，**没有本地 Web 管理页面**；需要 Web 管理的功能在**云端平台网页**完成（路由规则、上游定义、配额等非机密配置的编辑），配置数据由**本地系统主动拉取**下行生效。
- 请求数据面不变：请求仍从本地发出直达上游，**不经云端**。

成立前提（两条硬约束，缺一即砸掉隐私卖点）：

1. **密钥双向不上云**。既有拍板"平台批发 key 永不下发到本地"（客户端需求 §二）之外，补充对称约束：**客户端 BYOK key 永不上传云端**。云端可管理的配置仅含非机密部分（路由规则、上游定义、配额）；key 本体只经本地 CLI 录入、本地加密存储，云端配置中仅存**引用名**。否则平台持有用户全部厂商 key，L2 承诺作废且泄露责任在平台。（2026-07-08 拍板成立，已回写[客户端需求文档 §二](./个人模式本地客户端需求.md)。服务端 BYOK 是另一种产品能力：用户主动把 key 托管给 SaaS/私有部署网关代理直连，不适用本条"不上云"承诺。）
2. **离线可用**。本地缓存最后一次拉取的配置；云端不可达时数据面照常工作，仅不能拉取新配置。直连型产品的可用性不得被云端控制面绑死。
3. **配置来源明确**。默认使用本地 profile；用户显式开启远程配置后，云端 profile 成为非机密配置的生效来源，本地只保留密钥映射与最后一次远程配置缓存。用户可随时关闭远程配置并回到本地 profile；云端配置必须版本化、可回滚、可导出，避免本地/云端互相覆盖不清。

信任面变化（有意接受，需对用户明示）：路由规则与上游列表上云意味着**平台可见用户的配置元数据**（使用哪些厂商、如何分流）。这不是内容泄漏，但较"配置全本地"退了一步，须在隐私说明中主动声明，不留给用户自己发现。

## 四、交付物② Team vs Enterprise：license 差异设计（2026-07-08 拍板初版）

设计原则：**同一个镜像/二进制，差异全部由 license 开关控制**，不维护两套代码。license 拦的是**组织能力**（SSO、RBAC、审计），不拦运维选择（外接数据库、多副本不是 Team 的技术禁区，只是 Enterprise 提供官方支持）。

| 维度 | Team | Enterprise |
|------|------|-----------|
| **部署** | 单机，docker-compose 一条命令起，内嵌 SQLite | K8s/Helm、外接 Postgres/Redis、多副本高可用、完全离线（air-gap license 激活） |
| **身份接入** | 邮箱/密码 + 邀请链接 | SSO（V2-P3b 先做 OIDC；SAML/SCIM 作为后续专项） |
| **组织结构** | 单工作区，两级角色（管理员/成员） | 多工作区（部门/项目），预算按层级下发；细粒度 RBAC 作为后续专项 |
| **治理** | 每人虚拟 key、月度配额、全局一套模型白名单 | 按团队/项目分设白名单与预算、key 到期与轮换策略；超额审批流作为后续专项 |
| **审计合规** | 请求元数据日志（本地保留） | 管理操作审计日志、日志导出 / SIEM 对接、保留期策略、敏感信息脱敏规则 |
| **支持** | 社区 + 工单 | SLA、专属支持、升级窗口协商 |
| **计费** | 按席位订阅，自助购买 | 席位 + 平台费，销售谈判制 |

设计意图：

- **SSO 归 Enterprise 档是行业惯例（"SSO tax"）**：小团队邀请链接够用，而任何有 IT 部门的公司绕不开 SSO，是私有部署产品最有效的升档杠杆。
- **"Team 架构简单"是默认形态而非承诺**：单机 SQLite 是开箱体验，不是能力上限；档位切的是收费，不是架构（§五）。

## 五、人数档位是收费口径，不是架构分界（2026-07-08 拍板）

原草稿的"10 人 / 10-50 人 / 大团队"不作为架构或数据能力的划分（单机网关抗数百人无压力，10 与 50 之间不存在技术分支点），仅作为**定价与销售动线**：

- **Team**：按席位月/年订阅，自助下单；设起售席位数与封顶席位数（如 5 席起、50 席封顶）。**封顶不是技术限制，是强制转 Enterprise 谈判的销售机制**——这就是原草稿"10-50 人"这条线的真实含义。
- **Enterprise**：席位不设上限，底价 + 席位阶梯折扣，年付合同。

具体席位数与价格待定价专项确定，本文只锁定"档位=收费口径"的原则。
