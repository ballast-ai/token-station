## 问题一：Agent 安全准入状态提示不准确

### 基本信息

- **问题类型**：状态表达错误 / 错误信息不可诊断 / 配置安全风险
- **影响位置**：左侧 `AGENTS → Claude Code → AGENT ROUTE` 顶部接入状态区域
- **当前标题**：`暂不可接入`
- **当前详情**：已改为后端返回的具体 `compatibility.message`
- **当前操作**：部分失败状态仍只显示禁用的 `一键接入`按钮
- **严重程度**：高（P1）

### 问题描述

最新版已经不再把所有失败详情统一写成“当前版本或配置未通过安全准入”，并且能够显示后端返回的具体说明；已有接管记录但运行态不一致时，也会显示“需修复”和“恢复 Agent 原始配置”。

但版本被阻止、安装入口无法执行、版本探测失败、配置读取失败和配置解析失败等不同原因，标题仍统一展示为：

> 暂不可接入

页面也没有根据 `reason_code` 提供“重新扫描”或“查看诊断”等对应操作。用户虽然能从详情中获得更多信息，但仍需理解后端技术文案，无法快速判断失败发生在版本、安装入口、探测过程还是配置文件。

### 代码位置

最新版前端状态映射位于：

```text
apps/desktop/src/pages/AgentRoutePage.tsx:60-72
```

第 71 行对所有非 `DETECTED_VERIFIED` 状态仍统一返回：

```text
label: "暂不可接入"
detail: installation.compatibility.message
```

因此详情表达已经改善，但标题和操作入口仍未按错误类型区分。

### 预期表现

界面应根据后端 `compatibility.status`、`reason_code` 和 `message` 显示具体原因，不应把所有失败归结为“安全准入”。建议至少区分：

| 后端原因 | 建议状态标题 | 建议说明或操作 |
|---|---|---|
| `BlockedVersionMatch` | 当前版本已被阻止 | 展示阻止原因，并建议升级或降级版本 |
| `VersionProbeExitFailure` | 无法检测 Claude Code 版本 | 展示探测失败摘要，提供“重新扫描”和“查看诊断” |
| `VersionProbeTimeout` | Claude Code 版本检测超时 | 提供重试和诊断入口 |
| `ExecutableNotRunnable` | Claude Code 安装入口无法运行 | 展示发现的入口位置和检查建议 |
| `ConfigReadFailed` | 无法读取 Claude Code 配置 | 展示配置路径，不展示敏感内容 |
| `ConfigParseFailed` | Claude Code 配置格式错误 | 提示 JSON 无法解析，并提供只读诊断信息 |
| 已有 ownership 但安装身份未匹配 | 检测到已有接入记录 | 提供“重新绑定已有接入”和“恢复原配置” |

对于“接入后配置被外部修改”的真实场景，建议明确显示：

> 检测到接入配置已被外部修改

并提供：

- `查看变更`
- `重新接入`
- `恢复原配置`

上述操作必须先展示目标配置和变更摘要，不能直接覆盖用户现有配置。

### 验收标准

1. 不同 `reason_code` 不再统一显示为“当前版本或配置未通过安全准入”。
2. 用户仅看页面即可判断失败发生在版本、安装入口、探测过程还是配置文件。
3. 错误状态提供可执行的下一步，而不是只显示禁用按钮。
4. 不向前端或普通日志输出密钥、完整配置和其他敏感值。
5. 已有接入记录时不显示会产生歧义的普通“一键接入”。

## 问题二：Claude Code 官方安装入口因探测环境缺少 `HOME` 被误判为不可接入

### 基本信息

- **问题类型**：版本探测缺陷 / Agent 接入阻断 / 历史 ownership 未识别
- **影响 Agent**：Claude Code
- **本机 Claude Code 版本**：`2.1.173`
- **严重程度**：高（P1）
- **关联问题**：问题一的笼统文案掩盖了本问题的真实原因

### 用户侧表现

1. 左侧 Claude Code 状态显示为 blocked。
2. Claude Code 页面显示“暂不可接入”。
3. 页面说明“当前版本或配置未通过安全准入”。
4. `一键接入`按钮不可用。
5. 用户无法从界面判断 Claude Code 实际上可以正常运行。

### 调查结论

本问题不是 Claude Code `2.1.173` 不兼容，也不是 `~/.claude/settings.json` 被修改或无法解析。

只读检查结果：

- `claude --version` 正常返回 `2.1.173 (Claude Code)`。
- 当前内置兼容目录为 `builtin-2026-07-22.1`。
- Claude Code 验证范围为 `>=2.1.0, <2.2.0`，明确包含 `2.1.173`。
- `~/.claude/settings.json` 是有效 JSON。
- token-station 仍保存着 Claude Code 的 active ownership 和加密快照记录。

真实根因是：token-station 在隔离环境执行 `claude --version` 时清空了环境变量，却没有把 Claude 官方安装入口所需的 `HOME` 加回子进程。

### 根因链路

#### 1. Registry 使用 Claude Code 官方入口

位置：

```text
apps/desktop/src-tauri/agent-registry/builtin-agents.json:12-21
```

macOS、Linux 和 WSL 的已知安装入口均为：

```text
${HOME}/.local/bin/claude
```

Anthropic 官方文档也说明原生安装入口位于 `~/.local/bin/claude`：

<https://code.claude.com/docs/en/troubleshoot-install>

#### 2. 扫描器读取了 `HOME`，但没有传给探测子进程

位置：

```text
apps/desktop/src-tauri/src/agent_integration/platform.rs:23-76
```

`HOME` 被读取到 `variables`，可用于展开 Registry 中的路径；但 `child_environment` 只写入了 `PATH`，以及 Windows 的 `SYSTEMROOT`、`WINDIR`，没有写入 `HOME`。

#### 3. 版本探测清空环境变量

位置：

```text
apps/desktop/src-tauri/src/agent_integration/discovery.rs:121-142
```

探测器先调用：

```text
env_clear()
```

随后只恢复 `child_environment` 中的变量。由于其中没有 `HOME`，本机 `~/.local/bin/claude` 启动脚本无法定位真正的 Claude Code 二进制。

#### 4. 可稳定复现探测失败

使用与 token-station 探测逻辑等价的空环境执行时：

```text
/Users/rainlu/.local/bin/claude: line 2: /local/bin/claude: No such file or directory
/Users/rainlu/.local/bin/claude: line 2: exec: /local/bin/claude: cannot execute: No such file or directory
probe_exit=126
```

因此后端将安装判定为：

```text
INSTALLED_BROKEN
VersionProbeExitFailure
```

前端再通过问题一中的统一映射，将其显示成“当前版本或配置未通过安全准入”。

### 伴随问题：历史 ownership 未被识别

现有 ownership 记录中的安装路径是：

```text
/Users/rainlu/.local/share/claude/versions/2.1.173
```

当前 Registry 发现的稳定入口是：

```text
/Users/rainlu/.local/bin/claude
```

连接状态判断位置：

```text
apps/desktop/src-tauri/src/agent_integration/commands.rs:465-504
```

当前逻辑使用 `record.canonical_path` 对 ownership 的 `installation_path` 做精确匹配。两个路径不一致时，已有 ownership 不会被识别，所以界面显示“一键接入”，而不是“已接入”或“恢复 Agent 原始配置”。

这不仅是显示问题：如果只修复版本探测并直接重新开放“一键接入”，可能为同一个 `~/.claude/settings.json` 创建第二条 active ownership，导致恢复基线、快照关系和后续断开行为产生歧义。

### 建议修复方案

#### A. 修复版本探测环境

保留 `env_clear()` 的隔离机制，但按平台向探测子进程加入经过验证的最小环境：

- macOS / Linux / WSL：加入绝对路径形式的 `HOME`。
- Windows：加入绝对路径形式的 `USERPROFILE`。
- 不应因此把完整父进程环境透传给 Agent。
- 不应把密钥、供应商凭证或代理鉴权信息带入版本探测进程。

更长期的做法是允许 Registry 为每种 `version_probe` 声明必须的非敏感环境变量，由统一白名单验证后注入。

#### B. 增加回归测试

新增官方安装形态的测试夹具：

1. 创建依赖 `$HOME` 的 `~/.local/bin/claude` 包装入口。
2. 在 `env_clear()` 后只注入允许的最小变量。
3. 执行 `--version` 并返回 SemVer。
4. 断言最终状态为 `DETECTED_VERIFIED`，而不是 `INSTALLED_BROKEN`。
5. 增加缺失 `HOME` 时返回精确 `reason_code` 的测试。

#### C. 使用稳定的安装身份管理 ownership

不要把会随 Claude Code 自动更新变化的版本二进制路径作为唯一 ownership 身份。可考虑：

- 使用稳定的官方入口路径作为 installation identity；或
- 使用 `agent_id + target_config_path` 作为 ownership 主键，再单独保存发现入口；或
- 为同一安装保存稳定入口与真实二进制路径的 alias，并在版本更新后安全迁移。

对现有 ownership 必须提供明确迁移流程。迁移前应校验：

- Agent ID 一致；
- Connector 一致；
- 目标配置路径一致；
- ownership MAC 与受管字段仍可验证；
- 基线快照存在且可恢复。

#### D. 增加历史接入恢复状态

如果发现同一 Agent、Connector 和目标配置已有 ownership，但安装路径发生变化，应返回独立状态，例如：

```text
OWNERSHIP_REBIND_REQUIRED
```

界面建议显示：

> 检测到已有 Claude Code 接入记录，但安装入口已变化。

并提供：

- `重新绑定已有接入`
- `查看记录`
- `恢复原配置`

在用户完成安全迁移或恢复之前，不应提供普通“一键接入”。

### 不建议的修复方式

1. **不要只扩大兼容版本范围**：`2.1.173` 已经在当前验证范围内。
2. **不要删除用户的 `settings.json`**：该文件当前可以正常解析。
3. **不要直接删除 ownership 或快照**：这会丢失恢复链路。
4. **不要透传完整父进程环境**：会扩大凭证和隐私数据进入探测进程的范围。
5. **不要在存在历史 ownership 时直接重新接入**：可能产生重复 ownership 和错误恢复基线。

### 验收标准

1. 官方安装入口 `~/.local/bin/claude` 在隔离探测环境中可以正常完成 `--version`。
2. Claude Code `2.1.173` 被识别为 `DETECTED_VERIFIED`。
3. 探测失败时页面展示具体 `reason_code` 对应的用户文案。
4. 既有 ownership 能在 Claude Code 自动升级或入口变化后被安全识别、迁移或恢复。
5. 同一个目标配置文件不能产生两条相互冲突的 active ownership。
6. 修复过程不修改用户未授权的配置字段，不泄露配置值或凭证。
7. 自动化测试必须使用临时 HOME 和临时配置副本，测试结束后清理临时目录，不触碰真实 `~/.claude/settings.json`。

## 问题三：无法发现自定义 npm global 路径中的 OpenClaw，且 Node 运行时错误不可见

### 基本信息

- **问题类型**：Agent 发现缺陷 / Node 运行时解析缺陷 / 错误状态不可诊断
- **影响 Agent**：OpenClaw
- **本机 OpenClaw 版本**：`2026.6.5`
- **本机 Node.js 版本**：`v22.14.0`
- **严重程度**：高（P1）
- **用户侧状态**：OpenClaw 显示“未发现”
- **关联问题**：问题一中的状态表达不足；扫描失败时用户无法区分“没有安装”和“安装在其他目录”

### 用户侧表现

OpenClaw 已经通过 npm global 安装，配置文件也存在，但 token-station 的 Agent 列表仍将其显示为“未发现”，无法进入接入流程。

实际文件位置：

```text
OpenClaw 可执行入口：/Users/rainlu/local/npm-global/bin/openclaw
OpenClaw 配置文件：/Users/rainlu/.openclaw/openclaw.json
Node 可执行文件：/Users/rainlu/local/node-v22.14.0-darwin-arm64/bin/node
```

### 调查结论

这是三个连续问题叠加，不是 `~/.openclaw/openclaw.json` 不存在。

#### 第一层：桌面 App 没有发现自定义 npm global 安装目录

OpenClaw Registry 位置：

```text
apps/desktop/src-tauri/agent-registry/builtin-agents.json:129-157
```

当前内置已知路径只有：

```text
${HOME}/.local/bin/openclaw
```

本机该路径不存在，真实入口位于：

```text
/Users/rainlu/local/npm-global/bin/openclaw
```

可执行文件候选生成位置：

```text
apps/desktop/src-tauri/src/agent_integration/platform.rs:99-130
```

扫描器只检查：

1. Registry 中的固定已知路径；
2. 启动 token-station 桌面进程时继承到的 `PATH`。

GUI 进程没有继承交互式终端中的自定义 npm global 路径时，扫描器得不到任何 OpenClaw 安装候选，于是直接返回“未发现”。配置文件存在不会让 Agent 被识别为已安装。

#### 第二层：即使发现 OpenClaw，扫描器也找不到实际 Node 运行时

OpenClaw 是以下形式的脚本入口：

```text
#!/usr/bin/env node
```

当前 Registry 的 Node 解析来源仅包括：

```text
observed_entry_sibling
known_install_locations
```

macOS 的内置 Node 路径只有：

```text
${HOME}/.local/bin/node
/opt/homebrew/bin/node
/usr/local/bin/node
```

运行时解析代码位于：

```text
apps/desktop/src-tauri/src/agent_integration/discovery.rs:324-365
```

本机 Node 位于：

```text
/Users/rainlu/local/node-v22.14.0-darwin-arm64/bin/node
```

该位置既不是 OpenClaw 入口的同级文件，也不在 Registry 的 Node 已知路径中。当前实现不会从扫描环境的其他 `PATH` 目录中解析 Node，因此即使桌面 App 找到了 OpenClaw，也可能继续返回：

```text
ExecutableNotRunnable
未找到与安装入口匹配的版本探测运行时
```

#### 第三层：本机 Node 版本不满足 OpenClaw 自身要求

通过 agent-reach 的 GitHub 通道核对 OpenClaw 官方仓库 `v2026.6.5`：

- `package.json` 声明 `engines.node` 为 `>=22.19.0`；
- 官方安装文档要求 Node 24，或 Node `22.19+`。

官方依据：

- <https://github.com/openclaw/openclaw/blob/v2026.6.5/package.json>
- <https://github.com/openclaw/openclaw/blob/v2026.6.5/docs/install/index.md>

本机直接执行 `openclaw --version` 返回：

```text
openclaw: Node.js v22.19+ is required (current: v22.14.0).
```

因此当前 `v22.14.0` 即使能被 scanner 正确找到，也无法正常运行 OpenClaw `2026.6.5`。

### 版本与配置本身的结论

- OpenClaw `2026.6.5` 符合 token-station 当前兼容范围：

```text
>=2026.6.0, <2026.7.0
```

- `~/.openclaw/openclaw.json` 确实存在。
- 当前“未发现”发生在可执行文件发现阶段，早于配置接入阶段。
- 因此不能把问题归因于 OpenClaw 版本或配置文件缺失。

### 对原最小解决方案的修正

“升级 Node 到 `22.19+` 后重新扫描”是必要条件，但不是充分条件。

如果只升级当前自定义目录中的 Node，而 token-station 仍然：

- 看不到 `/Users/rainlu/local/npm-global/bin`；或
- 不允许从实际 Node 所在目录解析 `node`；

桌面 App 仍可能继续显示“未发现”或“安装异常”。因此本问题包含需要产品代码处理的发现兼容性缺口，不能完全归类为用户本机环境问题。

### 建议修复方案

#### A. 提供“手动选择安装位置”

当自动扫描未发现 Agent 时，页面应提供：

- `选择 OpenClaw 可执行文件`
- `添加扫描目录`
- `查看扫描诊断`

用户选择后，后端仍需验证文件类型、执行权限、shebang、真实路径和版本，不应直接信任任意路径。

#### B. 支持自定义 npm global prefix

可选方案：

1. 从经过验证的 GUI 设置中读取用户额外扫描目录；
2. 安全识别常见 npm global prefix；
3. 将用户明确选择的 npm bin 目录持久化为扫描来源；
4. 展示桌面 App 实际使用的扫描路径，而不是假设它与终端 `PATH` 一致。

不建议把当前用户的绝对路径硬编码进 Registry。

#### C. 扩展安全的 Node 运行时解析来源

为 `env_shebang` 增加受约束的运行时来源，例如经过验证的 `PATH` 候选或用户明确选择的 Node 路径。继续保留以下安全校验：

- Node 必须是绝对路径；
- 必须是可执行的原生普通文件或安全符号链接；
- 启动前再次校验 canonical path，防止 TOCTOU；
- 不经过 shell 拼接命令；
- 同一优先级发现多个不同 Node 时要求用户选择，不应随机取一个。

#### D. 在 Registry 中声明运行时最低版本

OpenClaw 的 probe 可以声明：

```text
runtime: node
minimum_runtime_version: 22.19.0
```

scanner 应先执行受限的 `node --version`，再执行 `openclaw --version`，从而向 UI 返回精确状态：

> 已发现 OpenClaw 2026.6.5，但 Node v22.14.0 过低；需要 Node v22.19.0 或更高版本。

#### E. 改善“未发现”状态

建议区分：

| 状态 | 建议文案 |
|---|---|
| 没有找到任何入口 | 未发现 OpenClaw，可选择安装位置 |
| 找到入口但没有 Node | 已发现 OpenClaw，但未找到可用 Node.js |
| Node 版本过低 | Node.js 版本过低，需要 v22.19.0+ |
| OpenClaw 版本探测失败 | 已发现 OpenClaw，但无法读取版本 |
| 配置文件不存在 | 尚未生成 OpenClaw 配置，首次启动后再扫描 |

### 不建议的修复方式

1. **不要因为配置文件存在就直接判定已安装**：配置可能是历史遗留文件。
2. **不要只把本机绝对路径加入内置 Registry**：无法解决其他用户的自定义 npm prefix。
3. **不要无条件继承完整终端环境**：可能把凭证和不可信 PATH 带入探测进程。
4. **不要只升级 Node 后宣告问题解决**：当前可执行文件和运行时发现规则仍可能失败。
5. **不要把 Node 运行时失败统一显示成“OpenClaw 未安装”**。

### 验收标准

1. OpenClaw 安装在自定义 npm global prefix 时，可以通过自动扫描或手动选择被发现。
2. token-station 能为 `#!/usr/bin/env node` 入口安全解析用户实际使用的 Node。
3. Node 低于 `22.19.0` 时，页面明确显示最低版本要求和当前版本。
4. Node 满足要求且 OpenClaw 为 `2026.6.5` 时，状态进入 `DETECTED_VERIFIED`。
5. `~/.openclaw/openclaw.json` 是否存在不会错误影响可执行文件发现结论。
6. 测试使用临时 npm prefix、临时 HOME 和临时 PATH；测试完成后删除临时副本，不修改用户真实安装。
7. 不向普通日志输出 OpenClaw 配置内容、令牌或其他敏感环境变量。

## 问题四：Agent/主页路由失败后污染内存草稿，并阻断 Ollama 保存和主页配置

### 基本信息

- **问题类型**：跨功能状态污染 / 配置草稿事务缺陷 / 成功状态误导
- **影响位置**：`Agent → 独立路由`、`添加供应商 → Ollama`、`主页路由`、主页“保存并应用”
- **最新复测版本**：`e752c24`
- **严重程度**：高（P1）
- **状态**：回归，且影响范围扩大

### 用户侧表现

1. 主页上、中、下三档尚未配置时，用户进入任意 Agent 页面并切换到“独立路由”。
2. 页面生成三个尚未选择供应商和模型的空档位。
3. 用户随后添加本机 Ollama，界面会先显示“供应商已添加”。
4. 用户把主页三档配置为刚添加的 Ollama 模型后，点击“保存并应用”仍然失败。
5. 由于 Ollama 只存在于未保存草稿中，重启 App 后它会消失，用户感受是“Ollama 添加失败”或“Ollama 被回滚”。

错误信息为：

```text
配置结构不合法: invalid type: null, expected struct AgentRouteTarget
```

这个错误没有指出真正需要处理的是某个 Agent 的未完成独立路由，容易让用户错误排查 Ollama 服务、Base URL、模型名称或 API 兼容性。

### 最新版本回归表现（2026-07-28）

用户在最新 release 复现路由配置失败后，即使返回主页，也无法恢复主页路由，页面持续显示：

```text
配置结构不合法: invalid type: null, expected a sequence
```

真实 App 只读检查结果：

1. 运行包为 `/Users/rainlu/local/token-station-develop/apps/desktop/src-tauri/target/aarch64-apple-darwin/release/bundle/macos/token-station.app`，对应 `develop` commit `e752c24`。
2. 页面上的主页 high、mid、low 三档全部显示“未选择”，模型选择框也全部不可用。
3. 页面显示“有未保存更改”，且非法结构错误一直存在。
4. 同一时刻磁盘中的 `token-station.json` 仍然合法：三个 `router.pools` 都是数组，并分别保存了 `ollama / qwen2.5`。
5. 磁盘配置可以正常解析；其中的 `null` 仅出现在允许为空的价格字段，不是本次 `expected a sequence` 的来源。
6. `token-station.state.json` 显示已保存 revision 为 27，而失败操作已经把最后分配 revision 推进到 55。

因此，本次不是磁盘配置损坏，而是运行进程持有了一份非法、未保存且无法从主页自行清除的内存草稿。重启 App 会重新读取磁盘有效配置，只能作为临时恢复手段；同样的失败操作仍能再次污染草稿。

本机此前还同时运行过 watcher debug 版与最新 release 版。两个进程使用相同 bundle ID，并共享：

```text
~/Library/Application Support/com.tokenstation.desktop
```

多实例共享配置会进一步产生陈旧草稿和覆盖风险，但它不是唯一根因：当前命令自身仍缺少失败后的完整草稿回滚。

本轮错误从原来的 `expected struct AgentRouteTarget` 变化成 `expected a sequence`，说明这次被写成 `null` 的是数组型配置字段。由于非法草稿只存在于进程内存、没有写入磁盘，现有只读接口无法安全取得具体 JSON path；开发修复时应让反序列化错误携带字段路径，并补充失败前后的草稿差异测试。

### 实际结论

本问题与 Ollama 服务是否在线无关。Ollama 可以正常监听 `127.0.0.1:11434`，OpenAI 兼容入口也可以填写为：

```text
http://127.0.0.1:11434/v1
```

真正的问题是未完成的 Agent 独立路由草稿参与了全局配置物化校验，并阻断了后来无关的 Provider 保存。

最新版的 `set_tier()`、`set_agent_route_mode()` 和 `set_agent_tier()` 仍采用“先原地修改 `inner.draft`，再观察草稿”的方式，没有像策略组相关命令一样保存并恢复完整的 `previous`。同时，`observe_draft()` 只记录指纹和 revision，不执行 `ClientConfig` 完整物化校验；错误会在随后生成 `StateView.config_error` 或保存/启动时才暴露。失败操作因此能够留下跨页面持续生效的非法草稿。

### 根因链路

#### 1. 切换独立路由时生成三个空档位

位置：

```text
apps/desktop/src-tauri/src/lib.rs:1355-1373
```

`seed_agent_custom_route()` 会从主页三档复制配置。主页某档尚未配置时，对应 Agent 档位写成：

```json

```

当主页三档全空时，最终生成：

```json

  "high": null,
  "mid": null,
  "low": null
}
```

#### 2. 切换命令保留了不完整草稿

位置：

```text
apps/desktop/src-tauri/src/lib.rs:2518-2532
```

`set_agent_route_mode()` 先调用 `set_agent_route_mode_value()` 写入 `mode=custom` 和三个空档位，再调用 `observe_draft()`。当前 `observe_draft()` 只记录草稿版本和指纹，不执行完整 `ClientConfig` 物化校验，所以命令会返回成功，不完整结构继续留在全局草稿中。

#### 3. 添加 Ollama 只写入草稿，因此先显示成功

位置：

```text
apps/desktop/src-tauri/src/lib.rs:1747-1842
apps/desktop/src/pages/AddProviderPage.tsx:123-137
```

`add_provider()` 将 Ollama 写入 `draft.upstreams`，但不执行最终保存。前端收到成功的 `StateView` 后显示“供应商已添加”，形成了已经持久化的错觉。

#### 4. 最终保存会校验整份配置并被空 Agent 档位阻断

位置：

```text
apps/desktop/src-tauri/src/config_state.rs:148-169
apps/desktop/src-tauri/src/lib.rs:1101-1115
apps/desktop/src-tauri/src/lib.rs:2617-2628
```

`save_config()` 最终调用 `save_draft()`，后者通过 `materialize()` 把整份草稿解析为 `ClientConfig`。Agent 独立路由中的 `null` 无法解析为 `AgentRouteTarget`，因此即使主页三档和 Ollama 本身已经完整，保存仍然失败。

### 影响与风险

1. 一个 Agent 页面中的未完成操作会阻断完全无关的 Provider 保存，功能边界不符合用户预期。
2. 页面先提示 Ollama 添加成功，最终却无法持久化，属于严重误导。

### 建议修复方案

#### A. 切换独立路由必须具备事务性

在 `set_agent_route_mode()` 修改前保存旧值。如果初始化独立路由后无法形成可接受状态，应恢复原草稿，并返回明确错误。不能留下半完成状态影响其他页面。

#### B. 不要在主页三档为空时静默生成三个 `null`

可以选择以下产品行为之一：

- 阻止切换，并提示“请先配置主页三档”；或
- 允许进入独立路由编辑态，但将未完成内容放在与全局可保存配置隔离的 UI 草稿中；或
- 允许空档位，但在用户离开页面时明确要求“继续编辑”或“放弃草稿”。

#### C. Provider 添加成功必须区分“加入草稿”和“已持久化”

如果 Provider 尚未保存到磁盘，不能只显示“供应商已添加”。建议显示：

> Ollama 已加入草稿，保存并应用后生效。

如果全局草稿存在阻断保存的问题，应在离开添加页面前直接指出具体位置。

#### D. 错误信息必须定位到 Agent 与档位

不要向普通用户显示 `expected struct AgentRouteTarget`。建议显示：

> Codex 的独立路由尚未配置完整：high、mid、low 档为空。
>
> [继续配置] [放弃独立路由草稿]

#### E. 增加跨功能回归测试

测试必须覆盖“未完成 Agent 草稿 → 添加无鉴权本地 Provider → 配置主页三档 → 保存”的完整用户链路，而不只是分别测试 Agent 路由和 Provider 添加。

### 验收标准

1. 主页三档为空时进入 Agent 独立路由，不会留下能阻断其他功能的无效全局草稿。
2. 放弃或离开未完成的独立路由后，可以正常添加、配置并保存 Ollama。
3. 添加 Ollama 后显示的成功状态与磁盘持久化状态一致；未保存时必须明确标识为草稿。
4. 保存失败时明确指出具体 Agent 和空档位，并提供“继续配置”或“放弃草稿”。
5. 修复不能通过忽略所有 Agent 路由校验实现，完整独立路由仍必须验证供应商和模型存在。
6. 回归测试覆盖 Ollama 无 API Key、本地 Base URL、三个主页档位和未完成 Agent 独立路由的组合场景。
7. 测试在临时目录中运行，不修改真实 `token-station.json`、Ollama 配置或用户模型。
8. 任意路由编辑命令失败后，整个内存草稿、draft revision 和页面选择状态必须与操作前完全一致。
9. 从 Agent 页返回主页后，不得残留任何无法通过主页操作清除的 `null` 数组或非法 Agent 档位。
10. 错误必须指出具体字段路径和对应页面，不再只展示 `expected a sequence`。
11. 同一配置目录检测到第二个 Token Station 实例时，应阻止并发编辑，或提供可靠的 revision 冲突提示，不能静默覆盖。

## 问题五：空主页路由仍允许启动网关，并把内部错误直接暴露给用户

### 基本信息

- **问题类型**：启动前置校验缺失 / 错误信息不可操作 / Agent 独立路由语义不清
- **影响位置**：顶部代理状态区的“启动 / 重试启动”按钮、主页三档路由
- **最新复测版本**：`e752c24`
- **严重程度**：高（P1）
- **状态**：未解决

### 用户侧表现

顶部代理状态显示：

```text
重试启动
127.0.0.1:8787
Agent：未连接
```

点击“启动”后失败，页面显示：

```text
gateway_init: a router with no pools can route nothing
```

用户无法从这条英文内部错误判断 `pools` 指的是主页上、中、下三档，也不知道应该先到哪里完成配置。由于 Claude Code 的独立路由三档已经完整，用户会合理地认为网关至少可以为 Claude Code 启动。

### 本机实际状态

只读检查真实桌面配置：

```text
/Users/rainlu/Library/Application Support/com.tokenstation.desktop/token-station.json
```

结果：

- 已保存 Provider：`ollama`；
- 主页 `router.pools`：空对象；
- 主页 `default_pool`：空字符串；
- Claude Code：`mode=custom`；
- Claude Code 的 high、mid、low 三档均已配置为 `ollama / qwen3:4b-instruct`；
- `127.0.0.1:8787` 当前没有监听进程。

因此这不是 Ollama API 连接失败，也不是端口冲突。失败发生在任何网络监听和 Provider 请求之前。

### 根因链路

#### 1. router-core 明确拒绝空主页路由

位置：

```text
crates/router-core/src/config.rs:432-446
crates/router-core/src/config.rs:557
```

`RouterConfig::validate()` 在 `pools.is_empty()` 时返回：

```text
a router with no pools can route nothing
```

底层拒绝一个完全不能处理默认请求的路由器是合理的 fail-closed 行为，本问题不建议删除这项校验。

#### 2. Gateway 总是先构造主页路由器

位置：

```text
apps/cli/src/gateway.rs:1041-1050
```

`Gateway::new()` 先执行：

```text
Router::new(config.router.clone())
```

只有主页路由成功后，才继续构造各 Agent 的独立路由。因此，即使 Claude Code 的独立路由三档完全有效，空主页路由仍会阻断整个网关启动。

#### 3. “保存并应用”与“启动”使用了不一致的前置校验

位置：

```text
apps/desktop/src-tauri/src/lib.rs:2340-2351
apps/desktop/src-tauri/src/lib.rs:2560-2622
```

`save_config()` 已经显式检查主页 pools 是否为空，并能返回中文提示：

```text
请至少配置一档(供应商 + 模型)再保存
```

但顶部“启动”调用的 `serve_start()` / `begin_serve_start()` 没有复用该检查。它先物化并保存草稿，再异步调用 `prepare_server()`，最终在 `gateway_init` 阶段失败。

#### 4. 前端明知配置不完整，仍允许点击启动

位置：

```text
apps/desktop/src/components/AppShell.tsx:120-137
apps/desktop/src/pages/HomePage.tsx:198-207
```

顶部启动按钮只根据命令忙碌状态和停止状态禁用，没有接收主页路由是否可启动的信息。主页也只显示模糊提示：

> 还有档位未完成，保存时会进行完整校验。

提示没有说明“至少一档”还是“三档全部”，也没有说明空主页路由会阻断网关启动。

### 与问题四的区别

- **问题四**：未完成的 Agent 独立路由包含 `null`，污染全局草稿并阻断正常 Provider 保存。
- **问题五**：Agent 独立路由已经完整，但主页路由为空；顶部仍允许启动，并在异步阶段显示原始英文错误。

两者可以连续发生，但根因和验收入口不同，不能合并成同一问题。

### 影响与风险

1. 核心启动流程被阻断，用户无法使用本地代理。
2. 页面显示“重试启动”，会诱导用户重复执行一个必然失败的操作。
3. 英文 `gateway_init` 和 `pools` 属于内部实现术语，普通用户无法采取正确行动。
4. Agent 独立路由看起来配置完整，却无法单独支撑启动，产品语义与用户预期不一致。
5. 启动入口与保存入口采用不同校验，未来还可能出现其他“能点击启动、必然异步失败”的状态。

### 建议修复方案

#### A. 在启动前复用统一配置校验

`serve_start()` 在写盘和进入异步启动前，应运行与“保存并应用”一致的可操作校验。主页 pools 为空时直接返回结构化错误，例如：

```text
HOME_ROUTE_EMPTY
```

不要进入 `gateway_init`，也不要把必然失败的启动记录为一次运行态故障。

#### B. 启动按钮显示明确前置条件

主页没有可用档位时，可禁用顶部“启动”并显示：

> 请先在主页路由中至少配置一个档位。

同时提供“去配置”入口，定位到第一个空档位。

#### C. 明确 Agent-only 模式是否受支持

产品需要明确选择一种语义：

1. **仍要求主页路由**：即使所有 Agent 都使用独立路由，也必须至少配置一个主页兜底；UI 必须提前说明。
2. **支持仅 Agent 独立路由启动**：当至少一个已接入 Agent 拥有完整独立路由时，不强制构造空主页路由；普通 `/v1` 请求在没有主页路由时返回明确“未配置默认路由”。

在产品决策完成前，不应让用户从内部错误反推规则。

#### D. 将底层错误映射成人话

保留日志中的稳定阶段码，但 UI 应把 `ConfigError::NoPools` 映射为中文可执行提示，不直接展示：

```text
gateway_init: a router with no pools can route nothing
```

### 当前用户侧临时解决办法

当前版本下，先在主页“智能路由 · 三档”中至少选择一个 Ollama 供应商和模型，再点击“保存并应用”或“启动”。为避免不同入口行为不一致，建议把 high、mid、low 三档全部配置完整。

### 验收标准

1. 主页 pools 为空时，点击启动不会进入异步 `gateway_init` 失败状态。
2. 页面明确指出“主页路由尚未配置”，并提供直达配置位置的操作。
3. UI 不再向普通用户展示 `a router with no pools can route nothing` 等内部英文错误。
4. “保存并应用”与顶部“启动”使用同一套路由可启动性校验。
5. 产品明确说明完整 Agent 独立路由能否在主页为空时单独启动，并用自动化测试固化选择。
6. 如果仍强制主页兜底，至少一个主页档位配置完成后可以正常启动并监听 `127.0.0.1:8787`。
7. 如果支持 Agent-only 模式，Agent 请求可以命中独立路由，普通无 Agent 路由请求得到明确的未配置提示。
8. 测试使用临时配置和临时端口，不修改真实用户配置、不调用真实 Ollama 模型。

## 问题六：网关虚拟 Key 重建后未修复已接入 Claude Code，导致无限重试

### 基本信息

- **问题类型**：受管凭据生命周期缺口 / 接入状态不可操作 / 客户端错误信息不足
- **影响位置**：Claude Code 与 Token Station 的 Agent 接入链路
- **最新复测版本**：`e752c24`
- **严重程度**：高（P1）
- **状态**：未解决

### 用户侧表现

Claude Code 已经能启动，但发送内容后一直显示：

```text
Retrying in 7s · attempt 5/10
✻ Osmosing…
```

用户看不到服务器返回的真实错误，容易误以为 Claude Code 卡住、Ollama 不可用、模型不兼容或网络异常。

### 本机实际证据

本轮只读检查确认：

- Claude Code 版本为 `2.1.173`，进程正常运行；
- Token Station 桌面端正在 `127.0.0.1:8787` 监听；
- Claude 的 `ANTHROPIC_BASE_URL` 正确指向 `http://127.0.0.1:8787/agents/claude-code`；
- Claude 配置和当前网关中的虚拟 Key 都符合 `ts-` 凭据格式，但两者的值不一致；
- `~/.claude/settings.json` 最后修改于 `2026-07-25 20:12:24 +0800`；
- 当前 `virtual-key` 创建于 `2026-07-27 18:05:56 +0800`；
- 使用 Claude 配置中的凭据请求 `/health` 和 `/agents/claude-code/v1/models` 均返回 HTTP 401；
- Claude 会话的错误元数据连续记录 `authentication_error: missing or invalid local virtual key`。

未输出、复制或修改任何真实凭据。

### 根因链路

#### 1. 网关在 `virtual-key` 文件不存在时生成全新凭据

位置：

```text
apps/cli/src/virtual_key.rs:29-65
```

`load_or_create()` 会在数据目录的 `virtual-key` 缺失时生成新 Key。这项默认鉴权机制本身是合理的，但新 Key 会立即使所有仍保存旧 Key 的 Agent 配置失效。

#### 2. Claude Code 的受管配置写入了接入当时的 Key

位置：

```text
apps/desktop/src-tauri/src/agent_integration/connectors/claude_code.rs:107-128
```

Connector 在“一键接入”时将当时的虚拟 Key 写入 `env.ANTHROPIC_AUTH_TOKEN`。这是一次性投影，网关 Key 之后变化时，Claude Code 不会自动获取新值。

#### 3. 运行时能判断“未连接”，但没有将失配转化为修复流程

位置：

```text
apps/desktop/src-tauri/src/agent_integration/commands.rs:653-681
apps/desktop/src-tauri/src/agent_integration/commands.rs:1546-1596
```

扫描会用当前运行时 Key 验证已受管配置，所以能把 Agent 判为“未连接”。但产品没有明确告诉用户“网关凭据已变化”，也没有提供一个仅更新受管凭据的安全操作。已有 ownership 时普通“重新接入”还可能被当成异常状态，用户无法知道怎么恢复。

#### 4. 旧 Key 在入站鉴权阶段直接被拒绝

位置：

```text
apps/cli/src/server.rs:250-279
```

请求在路由选择和 Ollama 调用前就返回 401。因此当前故障与 Ollama API、本地模型或 Claude 启动参数无关。

### 影响与风险

1. 已经“一键接入”的 Agent 可在网关数据恢复、重装或 Key 文件缺失后静默失效。
2. Claude Code 持续自动重试，浪费用户时间，却不告诉用户可操作的原因。
3. Token Station 虽能显示“Agent：未连接”，但该状态无法区分凭据失配、网关未启动、配置被外部修改或协议适配器不可用。
4. 如果用户手动编辑敏感凭据，可能破坏 ownership 指纹或误替换自己的 Claude 配置。

### 建议修复方案

#### A. 将“受管配置与当前网关 Key 失配”设为独立状态

当 ownership 存在、其他受管字段没有外部漂移，仅虚拟 Key 与当前运行时不一致时，显示：

> 网关凭据已更新，Claude Code 仍在使用旧凭据。
>
> [修复连接] [查看详情]

不要笼统显示“未连接”或“暂不可接入”。

#### B. 提供最小范围的凭据修复事务

在用户确认后，只将当前网关 Key 重新投影到 Connector 声明的敏感 owned path，保留其他 Claude 配置，并同步更新 ownership MAC。修复失败时必须原子回滚。

#### C. 在网关 Key 新建后主动检查已受管 Agent

如果 `load_or_create()` 返回 `created=true`，且 ownership 记录仍存在，桌面端应将所有需要虚拟 Key 的 Agent 标记为“需要修复”，而不是继续当作普通未连接。不建议在无用户确认时静默改写真实 Agent 配置。

#### D. 让终端错误可导向 Token Station 修复入口

如果 Anthropic 协议返回本地虚拟 Key 错误，错误文案应在不泄露凭据的前提下明确说明：

> Token Station 本地连接凭据已失效，请在 Agent 页面修复连接。

同时避免对明确不可恢复的 401 执行多轮无意义重试。

### 当前用户侧安全处理

1. 按 `Esc` 或 `Ctrl-C` 停止当前 Claude Code 的重试。
2. 不要手动复制或修改 `ANTHROPIC_AUTH_TOKEN`，也不要连续反复点“一键接入”。
3. 当前版本需要在 Token Station Agent 页面使用明确的恢复/重新接入流程；如果页面仍只显示“暂不可接入”，先保持现状，由开发修复该凭据失配。

### 验收标准

1. 删除临时测试数据目录中的 `virtual-key`、保留已接入 Agent 的配置和 ownership，重启后稳定进入“凭据需修复”状态。
2. 状态文案明确区分凭据失配、配置外部漂移、网关未启动和协议适配器不可用。
3. 点击“修复连接”只更新必要的受管凭据，不覆盖用户其他 Claude 配置。
4. 修复成功后，使用新凭据的 `/health` 和 Claude Agent 请求不再返回 401，Agent 状态变为已连接。
5. 修复事务任一阶段失败时，Claude 配置、ownership 和加密快照均保持事务前状态。
6. UI 和日志不显示虚拟 Key 明文；自动化测试只比较是否一致。
7. 使用临时 HOME、临时数据目录和临时端口运行回归，不改写真实 Claude 或 Token Station 配置。
