# 经验教训

## 2026-08-16：不要用当前消费者数量否定前置基础设施

- 错误：把“企业版尚未消费 `token-station-south`”当成暂缓独立仓的理由，形成循环论证。
- 事实：企业版迁移到统一 provider 插件执行链，前提就是先有稳定、可独立消费的南向执行层；当前没有第二个消费者，可能是缺少该基础设施的结果，而不是基础设施没有价值的证据。
- 规则：评估共享基础设施时先画出迁移依赖图，区分“需求不存在”和“需求被缺失前置条件阻塞”。如果组件是迁移门槛，应按目标消费者的契约反向设计并提前交付最小可消费纵切。
- 审查要求：仍需验证依赖方向、Cargo package identity、发布顺序和真实双消费者编译，但不得再以“先等第二个消费者出现”为理由推迟前置组件。

## 2026-08-16：新建 Rust 仓库前先加载团队规范

- 错误：讨论 south 的仓库结构与实现切片时，先按通用 Rust 习惯推演，没有先把 `rust-coding-standards-glimpse` 作为建仓输入。
- 事实：新仓的 edition、精确 toolchain、MSRV、lint、错误类型、异步取消、测试分层、依赖审计和插件安全边界都已有团队规范；这些是 Day 0 决策，事后补会制造无意义返工。
- 规则：创建任何新的 Rust 仓库前，先确定应用 profile，完整读取该 profile 指定的规范，并把适用项落成仓库配置、CI 门禁和贡献指南；不适用项必须明确说明原因，不能静默忽略。
- south 特例：它是“共享库 + 插件包/运行时”混合 profile。核心库不得读取环境变量、数据库或密钥存储，不初始化全局 tracing；这些运行时动作由宿主注入。插件默认无网络、文件系统和密钥权限，ABI、fixture、conformance、校验和与 SBOM 是发布契约。


## 2026-09-20：共享编排不能补救宿主的阻塞与错误栅栏

- 等待接口使用异步 Future，不代表其内部同步 HTTP 可被截止时间取消。宿主网络必须实际异步；用真实慢 HTTP 验证短等待到期，不以纯时钟测试代替。
- 获取观察版本时，UPDATE 与读取返回行必须处于同一事务，否则调用者可能借到另一个执行者的版本。用两个真实 SQLite 连接在边界确定性交错，不能靠随机延时猜竞争。
- CAS 失败后的权威状态读取，不授权附带败者响应里的产物。非终态败者必须清除临时响应；已终态成功的 URL 刷新需要独立、显式条件并保持事件不重复。
- 原任务的凭证验证密钥丢失时不得生成替代值。历史元数据读取与执行恢复分开，拒绝恢复不等于禁止读取历史。
